# v0.7.1 — External Review (round 3) & Convergence Record (2026-07-19)

Records how build-spec **v0.7 → v0.7.1** was produced: a **third round** of two external human reviews (R1c, R2c) and a **Codex adversarial convergence pass**. Finding → section mapping is in the spec Appendix (round-3 tags **R1c-#/R2c-#**); this file preserves the **findings themselves** and the resolutions.

## 1. Process

1. Triaged the two round-3 external reviews (R1c, R2c) — validated each finding against the v0.7 spec text at the cited line numbers; applied the valid ones, corrected reviewer framing where a characterization overstated (there were none this round of substance) and discarded false positives (none). **The false-positive rate was again ~zero** — both reviewers were strong; every item was a real gap, contradiction, or endorsed refinement. Two items were explicitly *observations/suggestions* (R1c-4 interval-floor, R1c-5 strategic fork) and were adopted as improvements.
2. **No new venue-fact verification was required** — every load-bearing fact these findings touch was already verified 2026-07-19 (v0.7 record §2: isolated-margin add-margin endpoints, Bybit `update-sub-api` transfer-class authority, position-mode read, create-order async ack, spot-IOC+TP/SL doc-silence, SQLite WAL/`synchronous=FULL`). The findings **apply** those verified facts (mark-price liq trigger, fence-credential blast radius, `PackageDelever` fallback) or make **architectural precision** corrections (ports, topology, dispatch-sequence model). **One new account-specific verify-item was added** (R1c-3: Binance sub-account availability is tier-gated — not verifiable without the actual account; placed on the integration/verify list with a single-account fallback).
3. Applied a Codex adversarial convergence pass on the updated spec — §4.

Locked decisions from HANDOFF were **not** re-litigated. One design refinement both reviewers converged on was adopted: **signer isolation is now the *primary* `Fence`** on both venues (exchange-side disable the backup), because the exchange-side path unavoidably requires a money-moving credential (R1c-2) and is account-tier-dependent (R1c-3), while signer isolation needs no venue credential.

## 2. External-review findings & resolution (round 3)

**R1c (verdict: prose layer converged — one real contradiction, two verify-items, two suggestions; then start milestone 1).**
- **R1c-1** spec↔tutorial contradiction: tutorial §6.2 said the margin top-up has an `ExposureReduction` fallback; spec §7.1 mandates `PackageDelever` (an `ExposureReduction` on a still-neutral package creates a naked leg). **Valid, blocker-grade.** → tutorial corrected (folded into R2c-5).
- **R1c-2** the fence credential cannot be "key-disable-only": Bybit `update-sub-api` requires a transfer/withdrawal-class authority, so the exchange-side credential inherently *can move money*. **Valid** (§7.3 contradicted §7.4 + the verification record). → §7.3/§7.4 state it honestly, mandate the narrowest grant (`Sub Member Transfer`, never `Withdrawal`), and **elevate signer isolation to the primary `Fence`** on both venues; exchange-side disable is the backup.
- **R1c-3** Binance sub-account availability is unverified (tier-gated); §7.2 custody and the Binance master-key fence presuppose it. **Valid verify-item.** → §7.2 adds a verify-item + a single-account fallback (caps carry more containment; signer isolation is the sole fence; the spot≠futures-wallet segregation still holds).
- **R1c-4** *(suggestion)* the deadline-exceeded branch may compensate the **interval floor** — the residual present in every reachable state — not only de-minimis. **Valid + provably safe.** → §6.7 adds the interval-floor rule (compensate the endpoint nearest zero only when the possible-delta interval does not straddle zero).
- **R1c-5** *(observation)* the spec predicts its own flagship may fail its own gate (≈3.4% at 60% utilization vs ~4.6% hurdle). **Valid.** → §12 names the strategic fork (maker entry / regime-selective / alt niche / tuition); §8 makes **mechanically-derived thresholds the solo default** for the calibration artifact's governance.

**R2c (verdict: milestones 1–2 approved; milestone 3 credible pending model tests; live canary NOT approved (undefined loss + missing mark-price trigger); `$1K` additionally blocked on incident-available fence + explicit safety-plane topology).**
- **R2c-1 (BLOCKER)** liq-distance monitoring is not mark-price-driven — the top-up trigger (§7.1) and OMS monitor (§6) were account-event-only, but liq distance moves with **mark**, which changes with no account mutation. **Valid + important.** → §2.2/§6/§7.1 recompute liq distance on every fresh mark update + every margin/position/tier change; a stale mark blocks openings + escalates; §9 case added.
- **R2c-2 (MAJOR)** the `$1K` fence guarantee vanishes if the fence is unavailable at incident time (de-minimis-only branch can't flatten a `$1K` position). **Valid.** → §7.4 adds a **continuously-monitored `FenceReady`** health gate that (i) blocks new openings and (ii) proactively winds down open exposure on loss, so a position is wound down before reaching an incident un-fenced; the incident-time de-minimis branch is a last resort for the residual only. *(Codex Cx4-5 later differentiated this into a fence-state machine — bot wind-down if signing works, actuator takeover if the signer itself failed — since a signer outage makes the bot unable to sign the wind-down; see §4.)*
- **R2c-3 (MAJOR)** the new safety operations have no hexagonal ports. **Valid** (consistent with the spec's own §3.6 rules). → §4 adds `MarginGateway`, `FenceGateway`, `ProtectionGateway`, `EmergencyPlanStore`; `TransferCollateral` moves out of read-oriented `AccountSource` into `MarginGateway` with submit-unknown semantics.
- **R2c-4 (MAJOR)** deployment collapses failure domains (actuator + fence credential beside the web-facing control API; "single process" ambiguous). **Valid.** → §3.2/§11 define three failure domains (engine ∥ operator/control ∥ minimal actuator daemon with no dashboard/HTTP surface); "single process" = the trading engine only; `cmd/arblab-actuator` added.
- **R2c-5 (MAJOR)** the tutorial still teaches superseded unsafe behavior (top-up→`ExposureReduction`; ladder without the ambiguity classifier; universal <5 s; fsynced-IDs-alone). **Valid.** → tutorial §3.6/§6.2/§6.5/§7.7 corrected to the safety kernel (`PackageDelever`; determined/ambiguous; split <5 s / <30 s; `DispatchAuthorized` state machine).
- **R2c-6 (MAJOR)** the dispatched-ordering rule is not fully realizable (strict global raw order → cross-source head-of-line blocking; coalescing → non-1:1 mapping). **Valid.** → §3.5 decouples `IngressSeq`/`DispatchSeq` (the replay key = consumed order) from `AcceptOrdinal`/`RawIngressSeq` (raw-arrival causal order); no cross-source HOL blocking; explicit mapping; replay keys on the consumed order (still no `SourceTime` reorder).
- **R2c-7 (MEDIUM)** `EmergencyClosePackage` internal contradiction (CloseTrade called "subject to `stop-opening`" — but §5.3 makes it `OpenTrade`-only). **Valid.** → §5.3 drops the wrong rationale; the command is justified by foundation-vs-strategy authority + the delta≈0 no-op.
- **R2c-8 (MEDIUM)** the "bounded, de-minimis" canary loss is undefined. **Valid.** → §12 requires a written risk-acceptance spec (max notional/collateral; worst-case = uncovered-leg notional; BTC-only; manual-recovery RTO; independent monitoring; signed acceptance).
- **R2c-9 (MEDIUM)** durability claims undocumented controls "are documented." **Valid** (empty claim). → §11 writes the requirement (SQLite online-backup / `VACUUM INTO`, not a raw file copy; RPO/RTO; encryption; external anchor; restore-drill gate).
- **R2c-10 (MEDIUM)** the hurdle is a hardcoded, inconsistently-characterized "risk-free" ~4.6%. **Valid.** → §2.1/§8 make it **near-risk-free**, dated/sourced/haircut-adjusted, and revision-controlled like any calibration input.
- **R2c-11 (MINOR)** provenance inconsistencies (2 vs 4 Codex rounds; the v0.7 record's process said 3 rounds; tutorial date 07-18). **Valid.** → HANDOFF (2→4), v0.7 record §1.3 (3→4), tutorial dates (note 07-18 v0.6 + 07-19 v0.7) corrected.

## 3. What the round confirms

The three doc-layer blockers R2 raised at v0.7 (canary loss undefined, missing mark-price liq trigger, fence unavailable at incident, safety-plane topology) are **design-layer gaps now closed in v0.7.1**. Their residual gating — the finality-contract watermark/timeout semantics, takeover races, the model + chaos tests — remains implementation work the spec already brackets (§6.7/§7.4/§12), answerable only by code and venues, not another prose round. The reviewers' own conclusion: apply these, then start milestone 1.

## 4. Codex convergence (v0.7.1)

A five-round adversarial pass on the updated spec (same discipline as the v0.7 rounds — stop when findings narrow to nits). Each round re-reviewed only the revised artifact; every finding was validated against the spec before applying. All findings were valid (no false positives); several were latent safety bugs the R1c/R2c changes had introduced.

**Round 1 — NO-SHIP, 7 findings, all applied.** (Cx4-1) §3.5 still carried contradictory "raw arrival = replay authority" statements after the dispatch/replay decoupling → unified on `DispatchSeq` as the sole replay authority (parity = replaying the persisted dispatch log). (Cx4-2) the interval-floor action (R1c-4) had no legal command path and could be **double-issued** — for interval `[0.4, 1.0]`, two uncertain `0.4` reductions could reach `−0.4` and defeat its own proof → made it a **reserved `IntervalFloorReduction` generation** counted in `outstanding_reserved_reductions`, no blind retry. (Cx4-3) mark-driven liq lost adverse excursions to latest-wins coalescing, bypassed port discipline, and had no freshness budget → **adverse-preserving mark coalescing** + an **OMS-owned mark-risk read port** + a **per-venue mark max-age with a `Clock`-timer staleness-on-silence**. (Cx4-4) signer isolation (the primary `Fence`) had no failure-domain placement and "no venue credential" overstated it → pinned to its own actuator-fenceable boundary; corrected to "no *additional* key-management/transfer-class credential." (Cx4-5) the `FenceReady` wind-down wasn't mapped to a command and over-promised → `FenceReadyLost` arbitration through the defined verbs. (Cx4-6) the backtest `ExecutionVenue` seam couldn't exercise the new safety code, and `EmergencyPlanStore` couldn't enumerate plans after host death → seam widened; `ListActive`/generation-CAS/`Deactivate` added. (Cx4-7) deployment non-goals + tutorial still said "single process" → qualified to the engine only.

**Round 2 — NO-SHIP, 2 Major + 1 Minor, all applied.** (Major) `FenceReadyLost` delegated wind-down to the live bot, but the signer feeds `FenceReady` and holds the trade key — so if the *signer* failed, the bot is alive yet **cannot sign** the wind-down → `FenceReady` made a **differentiated state** (signing / revoke / backup / fenced) with a branch that transfers to the actuator when the bot is already un-writable. (Major) `Deactivate` wasn't terminal and normal Close never called it → terminal tombstone + Close-awaits-`Deactivate`. (Minor) two Appendix rows still called raw arrival the replay authority → reworded.

**Round 3 — NO-SHIP, 1 Blocker + 2 Major, all applied.** (Blocker) `FenceReadyLost` branch 2 rested on a **point-in-time `VerifyFence`**, so a transiently-crashed signer could restart mid-takeover and restore **two writers** → require a **durable, monotonic takeover epoch (latched revoke)** the signer honors across restart; an un-latched signer falls to branch 3. (Major) "Close awaits `Deactivate`" wasn't crash-recoverable → durable **`DeactivationPending`** + reconcile-only-boot re-drive + idempotent `Deactivate`. (Major) the single `FenceReadyLost < 30 s` RTO was unsatisfiable (branch 3 is manual; finality can exceed 30 s) → **branch-specific RTOs**.

**Round 4 — NO-SHIP, 1 Blocker, applied.** The differentiated-fence model (rounds 2–3) established "never two writers without a durable latch," but the older fence-unavailable incident branch still permitted an unfenced **de-minimis** actuator trade — and interval-floor safety proves *sign*-safety, **not exclusive-writer authority**, so a recovering bot could still collide → at **`$1K`+ with no durable latch the actuator is read-only** (alert + manual only); the unfenced de-minimis action is **confined to the pre-`$1K` canary** (a separately-signed accepted bounded loss that claims no single-writer safety).

**Round 5 — CONVERGED / SHIP.** Final confirmation, scoped to the two-writer invariant across §6.7 / §7.4 / §9 / §12: no `$1K`+ second-writer trade exists without a durable fence latch — takeover is fence-first, `VerifyFence` validates a persistent revoke epoch, uncertain fencing stays read-only, and the unfenced exception is exclusively pre-`$1K` (claims no single-writer safety). Prose layer converged at round 5.

**Meta.** As with v0.7, the rounds again deepened exactly one area — the **safety kernel** (the off-host actuator/takeover + the ambiguous-order/finality machinery), now extended by the **differentiated `FenceReady` state machine** and the **emergency-plan deactivation lifecycle**. The spec fixes the **invariants** (single classifier + finality contract; sequenced `PackageDelever`; fence-first takeover with a **durable revoke epoch**; `$1K`+ never-two-writers with the read-only fence-unavailable floor; crash-recoverable deactivation) and routes the residual — the exact per-venue watermark/timeout finality semantics and takeover mechanics — through the **model-test-before-milestone-3 + sub-`$1K` canary** path, a bounded distributed-systems subproject, not a finished-in-prose protocol.
