## §1. OMS order lifecycle `[→ X1, Y1, Y2, Z1, Z2, R2b-4, R2b-12, R2-#1]`

**Source (v0.7.1):** build-spec §5.3 (identities, order-state table, rules) + §6 steps 5–6 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §5.3 (and §6 steps 5–6); this section is the mechanism.

**Identities (core §5.3).** `ClientOrderID` — deterministic, OMS-minted, unique per submission; a **recovery correlation handle, not a venue idempotency key** (Binance permits reuse once an order is terminal); never reused within the recoverable window. `ExecutionID` — the venue's immutable fill id (Binance `tradeId`, Bybit `execId`), unique only **within** an instrument; `VenueSeq` is *not* an identity.

### States

Order state tracks **submission/finality**; the fill ledger (Invariants below) tracks **realized quantity**. Meanings are the core §5.3 state table's, verbatim:

| State | Meaning |
|---|---|

| `DispatchAuthorized` | **the crash boundary** — a single `Place` for this client ID is **fsync-committed *before* the non-transactional network write**; the send is imminent/in-flight. Recovery resolves this order **by query only** — never resubmit, never infer "not sent" `[→ R2b-4]` |
| `Submitted` | the single `Place` returned a transport result; awaiting/parsing venue ack |
| `SubmissionUnknown` | ambiguous; resolve **only** by `OrderByClientID`/`Fills`, never resubmit |
| `Acknowledged` | live on venue |
| `PartiallyFilled` | some fills applied; more possible ("`PartiallyFilled` explicitly means *more fills possible*", core §6.7) |
| `CancelPending` | cancel requested |
| `CancelUnknown` | cancel ambiguous — entered on an **ambiguous cancel transport result** (timeout/5xx/unknown ack), by symmetry with `Submitted → SubmissionUnknown` `[→ R1d-F1]` |

### Invariants

- **Orthogonal cumulative-execution fill ledger `[→ Z2]`** (core §5.3): "Fills are *not* gated by order lifecycle: a **cumulative-execution ledger** accepts any deduped fill for a *known* order regardless of its current state — so a post-cancel or post-`SubmissionUnknown` late fill still applies. Order state tracks submission/finality; the fill ledger tracks realized quantity; **net delta is recomputed from the ledger on every fill/position event, and the §6.7 classification is re-evaluated on every event that can change *either* of its inputs** — fill/position events *and* every order-lifecycle/finality transition on the hedge group" `[→ R1d-3]` (feeding the §2 classifier).
- **The ledger never closes `[→ R2b-12]`** (core §5.3): "the **fill ledger never closes for a *known* order** — any deduped fill (`UNIQUE(account,venue,product,symbol,execution_id)`) is admissible **indefinitely**, since a legitimate fill can surface after prolonged downtime. The bounded 'finality window' governs only **ambiguous-order *acceptance* resolution** (the stable-not-found rule), **not** fill admission."
- **Dedupe key `[→ Y1, Z1]`** (core §5.3): fills dedupe on `UNIQUE(account, venue, product_category, symbol, execution_id)` — **the single normative key** (spot and perp ID namespaces are independent).
- **Single `Place` `[→ Y2]`:** `Place` is called **once** per order; **transport retries forbidden**.
- **Crash recovery is defined for every pre-ack state `[→ R2b-4]`:** an order at **`DispatchAuthorized` or beyond** is resolved **only** by `OrderByClientID`/`Fills` under the venue-specific stable-not-found rule — **never resubmitted, and "not sent" is never inferred** (the single `Place` may have executed with its response lost). "`ClientOrderID` durability alone does not reveal whether the `Place` ran — the state machine does."
- **Resolution is concurrent, not blocking:** "`SubmissionUnknown`/cancel resolution runs **concurrently** with exposure management — the OMS never blocks flattening of a **determined** residual on it; an **ambiguous** residual (any counter-leg order with remaining executable quantity) is quiesced to finality **first**" (§2 here; core §6.7).
- **Resolving-query outage:** "If the resolving query is unavailable/rate-limited, new trading stays disabled and rate-limit budget is **reserved for recovery**; 'not submitted' is never inferred from a transient not-found — finality follows a **venue-specific stable-not-found rule**."
- **Bybit stable-not-found fallback `[→ R2-#1]`:** "On **Bybit**, `GET /v5/order/realtime` holds only the most-recent ~500 closed orders and is **cleared on a server restart**, so resolution MUST fall back to `GET /v5/order/history` by `orderLinkId` (a filled order is always recoverable there); never infer 'not submitted' from realtime alone."
- **One transaction `[→ Y1, Z1]`:** "Applying a fill (dedup → ledger → `PositionAllocation`), advancing the **per-instrument** REST recovery cursor, and appending journal/outbox events happen in **one transaction**"; the outbox exports at-least-once (core §6 step 6).

### Chaos & acceptance cases (§9 of the core)

From the core §9 chaos list, the clauses exercising this machine:

- **Process kill mid-IOC** — the `DispatchAuthorized` crash boundary: recovery queries, never resubmits ("never infer 'not sent'").
- **Post-cancel late fills** — the `CancelPending`/`CancelUnknown` row + the never-closing ledger: the late fill posts to the ledger.
- **Bybit realtime-cache-cleared → order-history fallback** — the stable-not-found invariant's `GET /v5/order/history` fallback by `orderLinkId`.
- **Identical spot/perp execution IDs** — the dedupe key `UNIQUE(account, venue, product_category, symbol, execution_id)`: spot and perp ID namespaces are independent, so identical IDs are distinct fills, applied once each.
- **Venue rejects · partial fills** — the `Submitted → Rejected` and `Acknowledged/PartiallyFilled` fill edges.

### Flagged ambiguities

- **[FLAG-1 — resolved v0.9 `[→ R1d-F1]`]** *Was:* the entry edge into `CancelUnknown` — and any cancel-lost-race exit — was never stated. **Ruling (round 4):** reading (i) — an **ambiguous cancel transport result** (timeout/5xx/unknown ack) enters `CancelUnknown`, symmetric with `Submitted → SubmissionUnknown`; **explicit venue-terminal cancel + the final executions sweep** enters `Canceled`; a **cancel lost to a full fill** exits to `Filled`. The transitions table above now carries all three edges.
- **[FLAG-2 — resolved v0.9 `[→ R1d-F2]`]** *Was:* the terminal state of a **stably-not-found** order was never named. **Ruling (round 4):** a new terminal **`AbsentAfterFinality`** — `Rejected` is **not** overloaded (it requires an explicit venue rejection; proved absence is a different evidence class). A discovered late execution supersedes `AbsentAfterFinality` (venue reality wins; the never-closing ledger admitted the fill anyway). Applies equally to `DispatchAuthorized`-recovery resolution (core §5.3).

## §2. Ambiguous-order classifier & the finality contract `[→ Z2, R2b-B1, R1c-4, S4, X6, Y3]`

**Source (v0.7.1):** build-spec §6 step 7 ("§6.7") + §5.3 rules & command verbs + §6 step 8 + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §6.7 (with §5.3, §6 step 8, §9); this section is the mechanism.

**Scope.** "On **every** fill/position event **and every hedge-group order-lifecycle/finality event**, recompute net delta from the fill ledger and **classify the residual as *determined* or *ambiguous* before acting** — this classification, not the raw delta, gates the compensating trade." **Classification is a function of THREE inputs and re-runs when ANY changes `[→ R1d-3, FM-6]`:** fills/position events move the *realized* delta; order-lifecycle/finality events — ack, reject, **cancel acknowledgement, terminal order status, an executions-sweep/watermark completion, a stable-not-found finality timer (a `Clock` timer, not a venue event), a resolving-query result** — collapse an order's *possible-delta interval*; **and a change to `outstanding_reserved_reductions` moves the SUBTRAHEND `[→ FM-6]`** — an entry created, amended or retired by any of its producers (§7's generation opening, amending as its perp leg confirms, completing, terminal-flattening or being superseded; an `IntervalFloorReduction` retiring; §5's protective-order leg reservation released). The machine MUST NOT wait for the next fill/position event when order state alone became conclusive (a cancel confirmed with **zero** executions emits no fill and no position event, yet fully collapses that order's interval) — **nor for an order event when the LEDGER alone changed the residual: a generation ending emits no fill and no order event, yet moves the residual by the whole reserved amount.** The two clauses are the same argument, and the second was owed to the third input: **the residual is `realized_delta − outstanding_reserved_reductions`, so the subtrahend decides the verdict exactly as the minuend does.** Found by model-checking (`docs/formal/`, model (a)); the two-input reading is control `NC19`, whose signature is a **dead end** — every interval collapsed, the verdict still `DeadlineExceeded`, its one permitted action (the floor) spent, a determined naked residual and dispatch budget in hand, and nothing enabled. The classifier runs per hedge-group residual, over the §1 fill ledger.

### States

| State | Meaning (core §6.7, verbatim in the load-bearing parts) |
|---|---|
| `Determined` | "the exposure is **fixed because no exposure-changing order on the hedge group has any remaining executable *or unobserved* quantity**: e.g. a `ForcedCloseReason` (ADL/liquidation) event definitively closed a leg with no pending counter-order, or every leg has reached a **venue-terminal state with its cumulative execution reconciled**" |
| `Ambiguous` | "**any counter-leg exposure-changing order still has remaining executable quantity or an unresolved state** (`DispatchAuthorized` / `Submitted` / `SubmissionUnknown` / `Acknowledged` / **`PartiallyFilled`** / `CancelPending` / `CancelUnknown`), so the **sign *or size*** of the true net exposure is not yet fixed — each such order contributes a **possible-delta *interval*, not a point**" `[→ R2b-B1]` |
| `DeadlineExceededAmbiguous` | the finality contract "**cannot complete within its deadline** (queries unavailable/rate-limited)" — "a **deadline-exceeded *ambiguous* state that does NOT blind-compensate** — it holds new trading, alerts the operator, and permits **only provably-safe action**". Safe-action latitude exists "because the bot is the **sole writer**: this is an ambiguous *order*, not an ambiguous *writer* — contrast the §7.4 fence-unavailable branch, where writer identity is in doubt and `$1K`+ stays read-only" (core §6.7; contrast §7.4) |

**Why acting on the observed delta is forbidden while `Ambiguous`:** "Acting on the *observed* delta is then **wrong in at least one reachable venue state**: sell the filled spot against a perp only *partially* filled (0.4 of 1.0) and the remaining 0.6 fills → **naked short**; re-hedge the perceived gap and the pending quantity fills → **doubled short** (`PartiallyFilled` explicitly means *more fills possible*; a `CancelPending` order can still fill; a `SubmissionUnknown` may be filled). `outstanding_reserved_reductions` dedups *reductions* but does **not** represent this pending exposure."

**The per-venue finality contract** (quiesce-to-finality; "integration-proven, §8/§9" of the core). Needed "because a point-in-time `not-found` cannot collapse an in-flight order — a `DispatchAuthorized` send may land *after* the query, and §5.3 admits late fills":

1. "**tear down / fence that order's dispatch path** (an IOC is immediately terminal at the venue; a still-in-flight send is waited past its max propagation/timeout so it cannot land after the query)";
2. "read **terminal order status with the authoritative final cumulative executed quantity**";
3. "sweep executions through a **venue/server watermark strictly later than the order's cancellation-effectiveness / max landing horizon** — never a synthetic stable-not-found alone";
4. "reconcile position/balance to that **same watermark**."

### Transitions

| From | Event / condition | To | Action / guard |
|---|---|---|---|
| *(any)* | every fill/position event **and every hedge-group order-lifecycle/finality event** (Scope; `[→ R1d-3]`) | `Determined` / `Ambiguous` | recompute net delta from the §1 fill ledger; **classify before acting** — the classification, not the raw delta, gates the compensating trade `[→ Z2, R2b-B1]` |
| `Determined` | residual fixed (sign *and* size) | *(reduction issued; re-classified on next event)* | **immediately** (≤5 s, core §9) issue an `ExposureReduction` (core §5.3) sized from **`realized_delta − outstanding_reserved_reductions`**, "tracked as a **fenced reduction generation** — coalesce / amend / cancel-replace it, never a fresh command per event"; "reconciliation is never a precondition for flattening, so the ≤5 s budget is not held hostage to the resolution budget" |
| `Ambiguous` | quiesce **every** unresolved counter-leg order to finality via the 4-step contract above | `Determined` | "Only when every possible-delta interval has collapsed to a **fixed** residual does it issue the state-dependent `ExposureReduction`"; quiesce-to-finality RTO < 30 s (core §9) |

**Interval-floor rule `[→ R1c-4]`** (deadline-exceeded branch **only**): "each unresolved counter-leg contributes a possible-delta *interval* `[a, b]`, so the group's net exposure lies in a summed interval; if that interval **does not straddle zero** (`a ≥ 0`, guaranteed net-long — or `b ≤ 0`, guaranteed net-short), the endpoint **nearest zero** is naked in *every* reachable state, so reducing exposure by **exactly that magnitude** can never overshoot into the opposite sign under any resolution" — it shrinks the worst-case naked window from the full **`max(|a|, |b|)`** — the interval's *worst-magnitude* endpoint (the v0.7.1 "`|b|`" phrasing was correct only for the net-*long* case; for `[−1, −0.4]` the worst exposure is `|a| = 1`, not `|b| = 0.4` `[→ R1d-2]`) — to the interval width `(b − a)` while remaining safe. Mechanically: "**The interval-floor action is a distinct, reserved fenced generation (`IntervalFloorReduction`), not a plain `ExposureReduction`** (whose precondition requires a *fixed* residual): before submission it **reserves its own generation**, which subsequent net-delta recomputation **counts in `outstanding_reserved_reductions`** — so a still-in-flight interval-floor order is **not** re-read as fresh naked exposure and the floor is **never issued twice**". **`[→ FM-7]` The single-issue rule is *defence in depth*, deliberately retained, and its justification is stated as such:** under reservation-aware sizing a second floor **cannot** reach the opposite sign, because the first is already netted out of the subtrahend — formally checked over the complete state graph (model (a) `NC20`, 1,086,199 distinct states, no violation). It is kept because the proof it protects rests on **two independent mechanisms**, and this is the one that survives a defect in the other: **if the reservation is ever not counted — the `FM-5` failure mode, an entry not backed at the instant it is read — a second uncertain reduction *does* reach the opposite sign.** The historical parenthetical (for `[0.4, 1.0]`, two uncertain `0.4` reductions could reach `−0.4` and defeat the proof) describes **exactly that world**, and is retained as **the statement of what this rule protects against** — *not* as a hazard reachable under the sizing this document mandates. It is recorded this way because the earlier phrasing offered it as the rule's *live* justification while the adjacent sentence requires the reservation to be counted, so a reader checking the reason would find it does not hold and could retire a rule that is doing real work `[→ FM-7]`. "It is the **sole** exception to 'no compensation before finality,' and only for the reachable-state-**invariant** floor, never the uncertain part. This applies **only in the deadline-exceeded branch** (normal operation waits for finality and compensates the exact residual); the §6.4 gap budget still MUST cover the un-compensated **`max(|a|, |b|)`** ceiling (core §6 step 4 `[→ R1d-2]`) — interval-floor compensation shrinks the *realized* window, it does not loosen the conservative budget, and does not assume the ≤30 s target always succeeds."

### Invariants

- **Single gate `[→ R2b-B1]`:** "**This classifier is the *single* gate for *every* compensating trade** — one-leg-failure (core §6.7), ADL/liquidation (core §6 step 8), kill-switch / panic-MARKET (core §7.4), protection-disarm (core §7.4; §5 here), `PackageDelever`/`EmergencyClosePackage` (core §5.3; §7 here), and actuator takeover (core §7.4; §4 here) all route through it; **no path compensates the *uncertain part* of an ambiguous residual before the finality barrier** (only the deadline-exceeded **interval-floor generation** may compensate the reachable-state-invariant floor)." A pre-authorized panic-MARKET / venue-native stop "does *not* bypass the §6.7 finality barrier for an ambiguous residual" (core §7.4); "any ambiguous close order routes through the §6.7 classifier" (`CloseTrade`, core §5.3).
- **One canonical boundary:** "the ADL/panic 'immediate' path is the *determined* branch (no pending exposure-changing order), and a forced close *with* a still-live/partial counter-leg order is ambiguous and quiesces first. The §6.7 **finality contract is the *one canonical* boundary**: protection-disarm's sweep, the takeover's reconcile, and `PackageDelever`'s generations all reconcile through *this* contract **and its watermark**, never a weaker cancel-ack-only variant."
- **Forced-close events (core §6 step 8):** "A `ForcedCloseReason` (ADL/liquidation) event fires an immediate `ExposureReduction` **when the residual is determined — no pending exposure-changing order on the group**; if a counter-leg order is still live/partial it routes through the §6.7 **finality barrier first** — never a next-tick reaction either way."
- **Reservation-aware sizing:** the determined branch is sized from `realized_delta − outstanding_reserved_reductions`, "which **includes reserved *generations*** — a `PackageDelever`'s in-progress reserved second leg, a protective order's leg reservation — so an intentional in-progress transient is **not** misread as a naked residual" (§7 here). **This subtraction is unconditional, which is precisely why every entry MUST be backed at the instant it is counted `[→ FM-5]`:** an entry is only ever the exposure change its reserving action has already **committed** and not yet **realized**, never a target it merely intends — because this classifier cannot tell an unbacked reservation from a real short. The ledger's three producers **commit at different moments**, and reading one producer's rule onto another is itself a way to get this wrong: a `PackageDelever` generation's reserved spot leg is **zero at `Planned`** and amended as the perp leg confirms (§7 here, its `Planned` row and its "exactly backed at every instant" invariant), because until the perp buys, nothing is committed; an in-flight `IntervalFloorReduction` carries **its full dispatched size** from dispatch, because that order *is* working — zeroing it would restore the very re-read as fresh naked exposure the reservation exists to prevent; an `Armed` protective order carries its reserved leg allocation (§5 here). The safety argument here is asymmetric and does not defend itself: over-reserving reads as a **phantom short** and makes the determined branch **buy**, while the invariants that would object are computed *from* this same ledger.
- **Safety across reachable states:** assert "**no naked-short created and no doubled/over-reduced short across *every* reachable venue state**" (core §9).
- **Order type of the reduction — the state-dependent function (core §5.3):** "The reduction's order type is the **single state-dependent function of §5.3** — `reduceOnly` set **only** when the order reduces an existing position on that instrument …, all exempt from `stop-opening`" (core §6.7). The core §5.3 cases, in full: "The action is **state-dependent, and `reduceOnly` is set only when the order reduces an *existing position on that instrument*** — never merely because it reduces package delta `[→ R2-#4, Codex]`:
  - **Naked long spot** (e.g. the perp short was ADL'd to zero): either an **inventory-capped spot sell** to flatten (a plain sell — `reduceOnly` doesn't exist for spot), or an **ordinary *non*-reduce-only perp short** to re-hedge — a reduce-only order here would be **rejected**, because the perp position is zero and reduce-only cannot *open*.
  - **Naked short perp** (spot leg undersized/sold): a **reduce-only perp buy** to flatten the existing short, or an **ordinary spot buy** to re-hedge.

  "The choice (flatten vs re-hedge) follows policy + the net-delta invariant; the `reduceOnly` flag follows the *instrument's current position*, not the package. A §9 acceptance case proves ADL-from-a-zeroed-perp re-hedges successfully."
- **`EmergencyClosePackage` as a classifier client (core §5.3):** it "**quiesces existing orders through the §6.7 finality contract**, then **closes *both* legs** (paired-IOC), routing any resulting one-leg residual back through the §6.7 classifier" `[→ R2b-B1]` (its supersession of an active `PackageDelever` generation: §7 here).
- **During the ambiguous window:** "directional risk is bounded by any **pre-placed venue-native protection** (core §7.4) and by the **naked-leg-gap sizing budget over the resolution window** (core §7.1), **never** by a blind compensating trade. Stop new *strategy* orders; if the resolving query is unavailable/rate-limited, hold new trading and reserve rate-limit budget for recovery. Escalate via the pre-authorized ladder (core §7.4), operator alerted in parallel" `[→ S4, X6, Y3]`.
- **Determined-only shortcut:** "'Reconciliation is never a prerequisite for flattening' holds for a *determined* residual, **not** an ambiguous one."

### Chaos & acceptance cases (§9 of the core)

- **Ambiguous one-leg failure** (core §9, mapped in full): "a counter-leg exposure-changing order with remaining executable quantity — `SubmissionUnknown`, **`PartiallyFilled`**, `Acknowledged`, or `CancelPending` → **quiesce-to-finality *before* compensating the *uncertain part***; sub-cases: partial fill before/after cancel-ack, **stable-not-found *followed by* a discovered execution**, and a **deadline-exceeded interval-floor generation** (a reserved `IntervalFloorReduction` that itself times out / partially fills → assert **never issued twice, never overshoots into the opposite sign** — the gap budget covers `max(|a|,|b|)` `[→ R1d-2]`); assert **no naked-short created and no doubled/over-reduced short across *every* reachable venue state**."

- **Duplicate position events during an outstanding reduction** — the fenced reduction generation: coalesce / amend / cancel-replace, never a fresh command per event.
- **ADL from a zeroed perp** — "re-hedge via a *non*-reduce-only short, never a rejected reduce-only" (the state-dependent order-type function).
- **RTOs (core §9 gate):** **determined** naked-leg detected→reduced **< 5 s** (alert at 2 s); **ambiguous-order quiesce-to-finality < 30 s**; "**max observed *determined*-unhedged-exposure duration < 5 s** — the **ambiguous** window … is bounded separately by the ≤30 s quiesce RTO, and its directional risk is covered by the **sized naked-leg-gap budget (§6.4) + pre-armed protection (§7.4)**, not scored as a `<5 s` violation (§6.7 forbids a blind compensating trade inside it)" `[→ R2b-B1]`.

## §3. FenceReadyLost arbitration `[→ R2c-2, Cx4-5, Codex]`

**Source (v0.7.1):** build-spec §7.4 (the `Fence` bullet: the `FenceReady` health gate, the `FenceReadyLost` branches, the fence-unavailable failure branch) + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §7.4 (tier bindings: core §1.1); this section is the mechanism. Ownership split with §4: this section owns the **arbitration** (dimension tracking, first-safe-action, the three branches, the RTO structure, the tiered fence-unavailable floor); §4 owns takeover/epoch mechanics and is referenced, never restated.

**Scope.** "`FenceReady` — a continuously-monitored health gate, not a one-time preflight" `[→ R2c-2]`: "a successful provisioning-time propagation test is **not** an availability guarantee during a later incident", so the primary `Fence`'s health is "**polled continuously**" (`FenceGateway.FenceStatus`, core §4 ports: "CONTINUOUSLY polled health — blocks openings + winds down open exposure on loss"). The arbitration branches instead of taking one wind-down path "because the naïve "bot winds down" path is **impossible exactly when the signer itself failed** (the bot is alive but cannot sign `EmergencyClosePackage`/`ExposureReduction`, since signing readiness feeds `FenceReady`)".

### States

"**`FenceReady` is a differentiated *state*, not one Boolean `[→ Cx4-5, Codex]`**" — it tracks four **monitored health dimensions** (core §7.4):

- **signing readiness** — "can the bot sign at all?"
- **primary-revoke readiness** — "can the actuator **durably latch** a revoke/starve the signer honors across restart?"
- **backup-fence readiness** — exchange-side (mechanism: §4 here)
- **actuator execution readiness (`ActuatorReady`) `[→ R1d-4]`** — can the actuator *itself trade*: its **own independent trade credential** (validity propagation-tested), venue reachability from its IP, plan-store integrity — the takeover's premise, monitored continuously rather than discovered at incident time

(**Durably-fenced** — the latched, monotonic revoke *epoch* `VerifyFence` validates, not a point-in-time snapshot — is an **incident/takeover state, not a normal-operation health dimension** `[→ R1d-4]`: nothing is latched while the bot is the healthy writer; epoch semantics owned by §4 here. v0.8 listed it as a fourth dimension — reclassified by the round-4 ruling.)

Machine states (the branch labels name the source prose's numbered branches 1–3):

| State | Meaning |
|---|---|
| `FenceReady` | the differentiated health state above, continuously monitored; normal trading posture |
| `FenceDegraded` `[→ R1d-F5]` | **backup-fence-readiness-only loss** (signing, primary revoke, `ActuatorReady` all intact): alert + bounded repair posture; **openings continue** — the `$1K` premise (≥1 working, propagation-tested fence per venue) still holds via the primary; **not** a wind-down |
| `FenceReadyLost` | the explicit arbitration entered on loss of any *non-backup-only* dimension: the first-safe-action is applied, then a branch is selected on *which* dimension failed |
| `WindDown` (branch 1) | "Revoke-control lost, signing still works" — bot-driven wind-down through the defined verbs; **also entered on `ActuatorReady` loss while signing works** (host-death coverage is gone, the bot can still act) `[→ R1d-4]` |
| `TakeoverTransfer` (branch 2) | "Signing unavailable, a durable revoke is latchable, *and* `ActuatorReady` confirmed" — execution transfers to the actuator takeover (§4 here) |
| `ManualOnly` (branch 3) | "Fence state uncertain" — or signing unavailable with `ActuatorReady` unconfirmable — bounded pre-armed protection + operator manual kill only |

### Transitions

| From | Event / condition | To | Action / guard |
|---|---|---|---|
| `FenceReady` | **backup-fence-readiness-only** loss (signing + primary revoke + `ActuatorReady` intact) | `FenceDegraded` | alert + bounded repair posture; **openings continue** on the intact primary; a bounded repair window escalates to operator decision `[→ R1d-F5]` |
| `FenceDegraded` | any *further* dimension loss | `FenceReadyLost` | the full arbitration below; the backup loss alone never was the arbitration trigger |
| `FenceDegraded` | the backup is restored / repaired | `FenceReady` | redundancy restored — permissible *from `FenceDegraded` only* (no branch was started; the one-way rule below governs `FenceReadyLost` onward). **This is the *sole* health-driven return `[→ FM-4]`:** there is deliberately no counterpart from `FenceReadyLost`, not even before a branch is selected — see the repair-before-selection row below |
| `FenceReady` | loss of any non-backup-only dimension | `FenceReadyLost` | "Loss triggers an explicit **`FenceReadyLost` arbitration** that first **blocks `OpenTrade`** and **supersedes any active `PackageDelever` generation** (quiescing its reserved leg to §6.7 finality first)" (§7 here) ", then **branches on *which* dimension failed**"; the automated **first-safe-action** (block openings + confirm pre-armed protection) carries its own always-holds RTO (Invariants). **"Which dimension failed" is *recorded* at detection `[→ FM-4]`** — the arbitration below branches on that record, not on a fresh read of live health |
| `FenceReadyLost` | **every failed dimension repairs *before* a branch is selected** `[→ FM-4]` | `FenceReadyLost` (arbitration proceeds) | **the repair does not abort the arbitration.** The branch is chosen from the recorded failure, so the incident still resolves through its branch's terminal outcome + clearance — the one-way rule (Invariants) governs a *pending* branch exactly as it governs a started one. Rationale: the alternative (a health-driven return from `FenceReadyLost`) would make the detect→select window a silent escape from an incident that already blocked openings, and the window is short enough that committing costs at most one controlled wind-down. **Without the recorded failure the branch guards re-read live health and *all three* go false at once** — branch 1 needs a live failed dimension, branches 2/3 need live signing loss — stranding the incident in un-arbitrated `FenceReadyLost` with exposure open and no automated exit (a fair lasso; model-checked: `docs/formal/`) |
| `FenceReadyLost` | "Revoke-control lost, signing still works" — **or `ActuatorReady` lost, signing still works** `[→ R1d-4]` | `WindDown` (branch 1) | "**bot-driven wind-down** through the defined verbs — `EmergencyClosePackage` for a *neutral* package (an `ExposureReduction` would no-op at delta≈0), `ExposureReduction` only for a *fixed* residual — each routed through the §6.7 classifier" (§2 here). "This **overrides a configured `hard-halt-and-alert`**" (kill-switch mode (c), core §7.4): "halting while the fence is degrading is worse than a controlled exit — an explicit priority choice, not an arbitration conflict" |
| `FenceReadyLost` | "Signing unavailable, a durable revoke is latchable, ***and* `ActuatorReady` is confirmed** `[→ R1d-4]`" | `TakeoverTransfer` (branch 2) | "the actuator **latches a durable, monotonic takeover epoch**" — "the same **fence-first** revoke/starve primitive as the takeover protocol" (§4 here, which owns the epoch semantics: honored across restart until explicit operator clearance; `VerifyFence` validates **that epoch**, never a point-in-time snapshot) — "only then does execution **transfer to the actuator takeover**" (§4 here). A hand-off to an actuator that **cannot itself trade** would transfer the writer to nobody — signing unavailable with `ActuatorReady` failed is **branch 3**. **The hand-off is durable state, not a delivered message `[→ FM-3]`:** the branch is one-way (Invariants below), so an actuator that crashes — or never receives the hand-off — **before** latching MUST re-attempt the latch from that durable record on its reconcile-only boot (§4 here owns the re-engagement row and its `T_fence`/`FenceUnavailable` bound). Without that obligation the transfer is to nobody in a second way: the branch bars the bot *by branch*, not by signer health, so a restored signer does not resume writing |
| `FenceReadyLost` | "Fence state uncertain" — "no durable revoke latch achievable, and signing cannot be confirmed" — or signing unavailable and `ActuatorReady` **cannot be confirmed** | `ManualOnly` (branch 3) | "**bounded pre-armed protection + operator manual kill only**, never a compensating trade *or an un-latched takeover* that could create **two writers**". Branch membership rule (core §7.4): "a signer merely unreachable *without* a durable latch is **branch 3**", not branch 2 — because a point-in-time `VerifyFence` alone is insufficient (§4 here) |
| `WindDown` (branch 1) | signing fails mid-wind-down | `TakeoverTransfer` / `ManualOnly` | **escalate-only re-arbitration** `[→ R1d-F6]`: branch 2 if a durable latch is achievable and `ActuatorReady` holds, else branch 3 |
| `ManualOnly` (branch 3) | a durable latch becomes achievable (+ `ActuatorReady` confirmed) | `TakeoverTransfer` (branch 2) | **escalate-only**: manual-only → fenced takeover is strictly safer `[→ R1d-F6]` |

**The tiered fence-unavailable floor** (core §7.4 "Failure branch — fence unavailable at incident time"; stated here, consumed by §4's failed-latch edge): "fence-first is otherwise absolute (never two writers), so a *down* fence while the bot host is *also* dead would **deadlock the actuator while naked** — the precise failure the actuator exists to prevent. The resolution differs by tier, because **interval-floor safety proves only that a reduction cannot *overshoot the sign*, not that the actuator is the *sole writer*** — an unfenced actuator trade can still collide with a recovering bot:"

- **At `$1K`+ (single-writer guaranteed):** "if **no durable fence latch** can be established (neither a latched revoke epoch nor a validated `VerifyFence`), the actuator stays **read-only** — **wait `T_fence` → on miss, alert + operator manual kill (venue UI/2FA) *only*; it does NOT automatically trade**, because a transient double-write is *not* acceptable where single-writer is promised. The prior `FenceReady` wind-down (run while the bot was alive) is what keeps a position from reaching this point un-fenced; read-only + manual covers the residual."
- **In the pre-`$1K` canary only (core §12):** *if a minimal actuator already exists during the canary* (its construction is a **canary-concurrent workstream**, core §12 `[→ R1d-8]`; before it exists, canary host-death coverage is the **signed manual-recovery bound**), "the actuator MAY act on an **interval-floor / de-minimis residual** after `T_fence` — but this is the **separately-signed accepted bounded loss of the canary**, which **explicitly does *not* claim single-writer safety** (the fence/takeover is not yet §9-proven — possibly not yet built); it is never presented as a `$1K`+ guarantee."

(The writer-identity contrast with `DeadlineExceededAmbiguous` — ambiguous *order* vs ambiguous *writer* — is stated in §2's state table.)

### Invariants

- **RTO structure (core §7.4, verbatim):** "Each branch carries its own §9 target — an **automated first-safe-action RTO** (block openings + confirm pre-armed protection) that always holds, a **composite wind-down / takeover RTO** for branches 1–2 (which may include a §6.7 finality step), and a **manual-kill escalation *target*** for branch 3 (not an automated RTO)." Numbers (core §9): first-safe-action **< 5 s**; branch-1/2 composite **< 30 s**; branch 3 is a manual target, never an automated RTO (Chaos below).
- **The honest guarantee (core §7.4, verbatim):** "The honest guarantee is a **bounded first-safe-action, then wind-down or takeover within the composite RTO** — *not* "never outlives its fence": an *ambiguous* residual still quiesces to finality first (which can delay closure), so what is guaranteed is "**exposure is reduced toward flat within the RTO, never knowingly grown while `FenceReady` is lost, and never left with two writers**.""
- **Why the wind-down exists (tier gap, core §7.4):** "This closes the gap where "`$1K` requires a working fence" (§1.1) otherwise met only an incident-time **read-only + manual** fallback: exposure is wound down (or handed to the actuator) *before* an incident, rather than discovered fence-dead at host-death time."
- **Openings stay blocked while lost:** `OpenTrade` is blocked by the first-safe-action and exposure is "never knowingly grown while `FenceReady` is lost" (the guarantee above) — the block is scoped to the loss, not to a one-shot check. (`FenceDegraded` is *not* a loss in this sense: openings continue on the intact primary `[→ R1d-F5]`.)
- **One-way per incident `[→ R1d-F6]`:** a restored dimension **never aborts a started branch** — a started wind-down runs to completion — **nor a *pending* one `[→ FM-4]`: the rule binds from the moment the loss is *detected*, not from the moment a branch is selected.** The arbitration branches on the **recorded** failure (which dimension failed is snapshotted at detection, Transitions above), so a repair inside the detect→select window does not cancel it; the 2-vs-3 choice still reads **live** capability, because "latchable *and* `ActuatorReady` confirmed" is a claim about acting **now**. Scoping the rule to a *started* branch instead left the window as a silent escape: with live-health guards, a self-healed loss disables all three branch guards at once and the incident strands in un-arbitrated `FenceReadyLost` (model-checked; negative control **NC5**). Branch changes may only **escalate** — **and its corollary `[→ FM-3]`: because the bar on the bot is scoped to the *branch*, not to the health dimension that caused it, a branch that transfers the writer MUST guarantee the transferee actually engages** (§4's durable re-engagement obligation; a branch-2 hand-off whose actuator crashed pre-latch would otherwise leave exposure with *no* writer — neither the barred-but-healthy bot nor the un-engaged actuator) — **1→2 iff a durable latch is achievable *and* `ActuatorReady` holds, else 1→3** when signing fails mid-wind-down `[→ Cx5-2]`; 3→2 once a durable latch becomes achievable (with `ActuatorReady` confirmed); return to normal operation requires the branch's terminal outcome (**flat / reconciled**), **explicit operator clearance, and a fresh `VerifyFence` propagation test** — never health-flap re-entry. **Clearance is health-gated `[→ Cx6-3]`:** a fresh propagation test **cannot pass while signing readiness, primary-revoke readiness, or `ActuatorReady` is still failed** — those dimensions are exactly what the test exercises — so clearance with any of them down is unreachable, never merely inadvisable; and clearing while only the **backup** is still failed returns to **`FenceDegraded`** (that state's defining posture: alert + bounded repair, openings continue on the intact primary `[→ R1d-F5]`), never straight to `FenceReady`. (`FenceDegraded → FenceReady` on repair is the sole health-driven return, because no branch was started there.) Clearance deliberately does **not** wait on the §6 plan tombstone — that would couple operator clearance to plan-store availability (the R1d-5 coupling argument); it is safe *because* completion evidence terminalizes the trade `[→ FM-1]` (§4/§6 here), so a cleared bot can never re-admit exposure under a plan whose tombstone is still owed.
- **Tier bindings stay core-owned:** the `$1K` working-fence requirement and the actuator tiering ("a *minimal single-node* actuator with the fence-first protocol above + a plan **integrity check**" at `$1K`; `$10K+` hardens it; "The watchdog escalates (i)→(iii) on host silence") are core §1.1 / core §7.4 requirements — referenced here, owned there.

### Chaos & acceptance cases (§9 of the core)

- **`FenceReady` loss** (core §9, mapped in full): "differentiated state: revoke-lost-but-signing-works → bot wind-down; **signing-unavailable + `VerifyFence`-proves-fenced + `ActuatorReady`-confirmed → actuator takeover**; uncertain **or `ActuatorReady` unconfirmable with signing down** → bounded-protection + manual, **never two writers**; **backup-fence-only loss → `FenceDegraded`** — alert/repair, openings continue on the intact primary; **`ActuatorReady` loss with signing intact → wind-down while the bot can still act** `[→ R1d-4, R1d-F5]`; **a restored dimension never aborts a started branch — escalate-only (1→2 iff latch + `ActuatorReady`, else 1→3; 3→2), exit via flat/reconciled + operator clearance + fresh propagation test** `[→ R1d-F6, Cx5-2]`) → new openings blocked (first-safe-action) + **branch-appropriate RTOs met** (branch-1/2 wind-down/takeover composite; branch-3 → manual escalation)" `[→ R2c-2, Cx4-5]`.
- **Repair before branch selection `[→ FM-4]`** (core §9, inside the `FenceReady`-loss clause): raise a loss, then restore **every** failed dimension *before* the arbitration selects a branch — assert a branch is still selected, from the **recorded** failure, and that the incident never strands in un-arbitrated `FenceReadyLost` (openings blocked, exposure open, no branch, no automated exit). Also assert the converse is untouched: a *new* dimension failure after selection still escalates per the one-way rule. Model-checked both ways (`docs/formal/`): green under the recorded-failure guards, and a fair lasso under the pre-FM-4 live-health guards — **NC5**, which exists so the property is known to bite rather than assumed to.
- **RTO gate (core §9):** "**`FenceReadyLost` first-safe-action (block openings + confirm pre-armed protection) < 5 s** with a **branch-1/2 wind-down or durable-fence takeover composite < 30 s** (may include a §6.7 finality step) and **branch-3 = a manual-kill escalation *target*, not an automated RTO**".
- **Fence-unavailable** — the tiered floor above, exercised inside §9's actuator-takeover-fence clause (§4 here): "**fence unavailable** (no durable latch → **actuator read-only + operator manual kill at `$1K`+**, never an unfenced trade; de-minimis unfenced action only in the signed canary regime, §12, which claims no single-writer safety)".
- **Fence-race** — the core promises it: "Fence-unavailable and fence-race are §9 cases" (core §7.4). No §9 sub-case is *named* fence-race; the closest named exercise of the race (a second writer racing the fence) is the takeover clause's **bot-recovery-during-takeover** sub-case (§4 here).

### Flagged ambiguities

## §4. Actuator takeover protocol `[→ Codex, R1b-2, R2b-3, R1c-2, R1c-3, R2c-2, R2c-3, R1-meta]`

**Source (v0.7.1):** build-spec §7.4 (takeover bullet + `Fence` capability bullet + tiering/subproject bullets) + the §4 ports (`FenceGateway`, `ProtectionGateway`) + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §7.4; this section is the mechanism. Ownership split: this section owns **takeover/epoch mechanics**; the `FenceReadyLost` arbitration that can hand over to it, and the tiered fence-unavailable floor, are owned by §3 here; the `EmergencyPlan` lifecycle it consumes is §6 here.

**Scope.** "**Takeover is a fence-first protocol, not a fire-and-forget sell `[→ Codex]`.** The actuator is a *second writer*, so before it trades it MUST **fence the bot's trading credential/signer** (via the venue-specific **`Fence` capability** defined below — exchange-side credential disable *or* signer isolation) — single-writer is preserved by *transferring* the writer, never by running two." The protocol is "a bounded distributed-systems subproject" (core §7.4): "Three convergence rounds each surfaced a deeper takeover requirement (fence-first → reduce the *reconciled residual* → quiesce *all* resting orders to finality → replicate *full* recovery handles)"; the spec fixes the invariants below, and the protocol itself "MUST be **designed, prototyped, and chaos-tested as its own workstream** (host-death mid-`DisarmPending`, mid-reduction, partition, late-fill), not assumed correct from prose" — the recommended sub-`$1K` de-risking path stays core §12.

### States

Protocol phases, derived from the core §7.4 takeover bullet's mandatory sequence (fence → quiesce-to-finality → reconcile → reduce; the prose sequences the steps, it does not name states):

| State | Meaning |
|---|---|
| *(standby)* | the actuator holds replicated plans (§6 here) with watcher→actuator auth and independent key/IP (core §7.4); "The watchdog escalates (i)→(iii) on host silence" (core §7.4) |
| `FenceLatch` | latching the fence: a durable, monotonic revoke/takeover **epoch** via the `Fence` capability (mechanisms below) |
| `QuiesceSurfaces` | the finality barrier: every bot-owned exposure-changing order quiesced to finality across both product families |
| `Reconcile` | executions/positions reconciled via the §6.7 finality contract (§2 here) at the **same watermark** |
| `ReduceResidual` | the **reconciled end-state action** — a §2-classifier client whose verb is **state-dependent, exactly branch 1's selection `[→ R1d-1]`**: a **fixed residual** → the state-dependent `ExposureReduction`; a **neutral / near-neutral package** → the **two-leg `EmergencyClosePackage`-equivalent close within the plan's loss/slippage bounds** (post-quiesce, all resting protection is already cancelled — leaving a neutral package open would leave it unprotected and unmanaged, host dead). **The takeover's terminal state is *flat*** |
| `CloseInFlight` | the issued close/reduction orders awaiting **§2 finality + post-close reconcile** — completion is **evidence-gated** (all order surfaces final + both reconciled per-leg allocations zero: exactly the §6 tombstone evidence), **never issuance-gated** `[→ Cx5-1]` |
| `HeldIncident` | the close **cannot complete within the plan's bounds** (zero-fill IOC in a gapping market, the **close-attempt budget** — `max_close_attempts`/`T_close`, replicated plan fields (§6) — **exhausted**, or deadline-exceeded ambiguity): **fence stays latched, plan stays `Active` (no tombstone), operator escalated** — **never a false "complete", never an unbounded market dump** `[→ Cx5-1]` |
| `FenceUnavailable` | "**no durable fence latch** can be established" — the tiered fence-unavailable floor governs (§3 here) |

### Transitions

| From | Event / condition | To | Action / guard |
|---|---|---|---|
| *(standby)* | the bot host *and its local journal* die (watchdog: host silence) | `FenceLatch` | the emergency actuator "MUST act after the bot host *and its local journal* die" (core §7.4); if the actuator itself restarted, its own reconcile-only boot first enumerates active plans via `EmergencyPlanStore.ListActive()` and applies the latest generation per trade (§6 here) |
| *(standby)* | §3 branch-2 hand-off ("Signing unavailable *and* a durable revoke is latchable") | `FenceLatch` | the hand-off *is* this machine's fence-first step: the epoch is latched first; execution transfers only once latched (§3 here) |
| *(standby)* | **a durable branch-2 hand-off is outstanding** `[→ FM-3]`: the §3 branch is `TakeoverTransfer`, the plan is `Active`, and **no epoch is latched** — observed on the actuator's reconcile-only boot, or on standing back down without having latched | `FenceLatch` | **the hand-off is durable state, not a delivered message.** The §3 branch is one-way per incident `[→ R1d-F6]`, so the obligation **survives the actuator's crash** — and because the actuator keys off that durable record rather than a received signal, a **lost hand-off and a crashed actuator are the same case**. The actuator MUST **re-attempt the latch**; the re-attempt is bounded exactly like the watchdog path — it times out to the `FenceUnavailable` row below (§3's tiered floor), and since `ActuatorReady` gates the latch itself `[→ Cx6-2]`, a failed-ready re-attempt also lands on that floor rather than never happening. This is the **un-latched sibling of the crash-mid-close re-entry** below: with an epoch latched the reconcile-only boot resumes at the quiesce barrier, with none it resumes at the latch. Without it the incident **stalls with both writers idle** — the bot-write gate bars the healthy bot for the whole branch (a restored signer never aborts a started branch) while the un-engaged actuator waits on a hand-off that already happened (model-checked: `docs/formal/`) |
| `FenceLatch` | durable epoch latched **with `ActuatorReady` confirmed** `[→ Cx6-2]`; `VerifyFence` validates **the epoch** | `QuiesceSurfaces` | fence-first is absolute — "before it trades it MUST **fence the bot's trading credential/signer**"; epoch semantics in Invariants. The branch-2 hand-off arrives with `ActuatorReady` already confirmed (§3 here); **the watchdog activation path applies the same gate** — engaging the protocol with no execution capability would fence the bot and **transfer the writer to nobody** (§3's branch-2 rationale) — so with `ActuatorReady` failed the latch is **not completed** and the attempt times out into the `FenceUnavailable` row below `[→ Cx6-2]` |
| `FenceLatch` | "**no durable fence latch** can be established" | `FenceUnavailable` | the tiered floor (§3 here): at `$1K`+ read-only — wait `T_fence` → on miss, alert + operator manual kill only; pre-`$1K` canary = the separately-signed bounded-loss regime |
| `FenceUnavailable` | a durable latch is established within `T_fence` | `QuiesceSurfaces` | the floor's condition ("**no durable fence latch** can be established") no longer holds, so fence-first proceeds; the floor's stated consequences are for the `T_fence` **miss** (§3 here) |
| `QuiesceSurfaces` | every bot-owned exposure-changing order reaches finality | `Reconcile` | "Fencing stops *new* submissions but does **not** cancel orders the venue already holds, so the takeover then **quiesces every bot-owned exposure-changing order to finality across both product families** — entries, reductions, and **all resting protection** (conditional / algo / TP-SL / OCO / trailing / attached), which are **separate cancel surfaces** (Binance cancel-all-*algo* is distinct from cancel-all-orders; Bybit stop/OCO need distinct filters and ack asynchronously) — a **finality barrier `[→ Codex]`**" (port: `ProtectionGateway.EnumerateResting`/`CancelToFinality`, core §4) |
| `Reconcile` | reconcile completes at the watermark | `ReduceResidual` | "Only after that barrier does it **reconcile executions/positions via the §6.7 finality contract (same watermark)**" (§2 here — "never a weaker cancel-ack-only variant", §2's one-canonical-boundary invariant) |
| `ReduceResidual` | the state-dependent action is issued (routed through the §2 single gate): fixed residual → `ExposureReduction`; neutral package → the **two-leg close** `[→ R1d-1]` | `CloseInFlight` | act on the **reconciled live** state, *not* the pre-allocated qty ("which may be stale: an entry leg can still have filled, or a partial reduction already run"); any resulting one-leg residue routes back through the §2 classifier |
| `CloseInFlight` | every close/reduction order reaches **§2 finality** and post-close reconcile proves **zero per-leg allocations + final surfaces** | *(complete — **flat**; the fence stays latched until explicit operator clearance; plan deactivation: §6's actuator-side path `[→ R1d-F7]`)* | **completion evidence = the §6 tombstone evidence — one gate, no gap** `[→ Cx5-1]` |
| `CloseInFlight` | zero/partial fill with the **plan's close-attempt budget** not yet exhausted (attempts remaining under `max_close_attempts` *and* inside the total close deadline `T_close` — both **replicated plan fields**, §6, so the actuator enforces them post-host-death) | `ReduceResidual` (next attempt — **consumes the budget**) | each attempt stays within the plan's loss/slippage bounds; the *aggregate* bound is the consumable budget, not a per-attempt property `[→ Cx5-1]` |
| `CloseInFlight` | **budget exhausted** (`max_close_attempts` consumed *or* `T_close` elapsed) / no liquidity within the slippage cap / deadline-exceeded ambiguity | `HeldIncident` | **unconditional** on exhaustion — repeated zero-fill IOCs can never remain admissible indefinitely; fence latched; plan `Active` (no tombstone — §6 gate unsatisfied); alert → operator manual kill (venue UI) is the escalation; any later fill re-classifies (§2) `[→ Cx5-1]` |
| `QuiesceSurfaces` / `Reconcile` / `ReduceResidual` / `CloseInFlight` | **mid-takeover `ActuatorReady` loss** `[→ Cx6-2]` — the actuator's own execution capability (independent-credential validity / venue reachability / plan-store integrity — §3's monitored dimension) fails while the protocol is running | `HeldIncident` | **every actuator venue write requires execution readiness — the quiesce *cancels* included** (cancels are venue writes on the actuator's own credential, exactly like its closes), so with `ActuatorReady` lost the protocol cannot progress and parks **honestly**: fence stays latched, plan stays `Active`, operator escalated — never a silently stalled "takeover" presumed to be executing. Recovery is the held-incident path: operator manual kill, or the actuator's reconcile-only re-entry from durable state once ready again. **The park is not exited by *recording completion* `[→ Cx7-1]`** (clarification, not new behavior): the durable `ActuatedFlat` record and the §6 tombstone are themselves writes `ActuatorReady` covers — its dimension list includes **plan-store integrity** (§3 here) — so "held → complete → tombstone" would assert exactly the write the health state says is impossible; the two exits above are the only ones. **The self re-entry is scoped to *this* park `[→ Cx8-2]`** (clarification, not new behavior): `HeldIncident` is reached two ways with two different exits, and the reconcile-only re-entry belongs to the readiness cause only. A park entered by **budget exhaustion** (row above) has **two** exits and neither is a readiness re-entry: **operator escalation**, and **re-classification once the position is proved flat** (that row's own "any later fill re-classifies") — after which the actuator walks the barrier to evidence-gated completion, because nothing is left to close. What it must NOT do is re-enter to *retry*: that walks `quiesce → reconcile → reduce` straight back to exhaustion with **no attempt left to issue**, an unbounded no-progress cycle that never stays parked and never escalates. Both halves are load-bearing — scoping the re-entry to the readiness cause *alone* leaves the exhaustion park unclearable, since operator clearance requires the actuator to be standby/done/fence-unavailable and a manual kill would leave it parked in `HeldIncident` forever. An implementation MUST therefore record *why* it parked, not just *that* it did (model-checked: with the cause-blind guard the cycle is a fair lasso, and the branch-convergence property could not see it — one transient visit to `HeldIncident` already satisfied its "eventually" `[→ Cx8-3]`) |
| *(standby, after a spurious fire)* | the watchdog fire proves a **false positive**: the bot is verified alive and healthy, **no epoch was latched and no §3 branch started** (e.g. the actuator crashed or stood down before `FenceLatch` completed) | *(standby — alert dismissed)* | **the operator dismisses the alert `[→ FM-2]`** — nothing was fenced and normal operation was never left, so the §3 branch-exit preconditions (terminal outcome flat/reconciled + clearance + fresh propagation test `[→ R1d-F6]`) are **scoped to a started branch and do not apply**; requiring them here would demand flattening a healthy trade to acknowledge an alarm. (Found by model-checking the incident-resolution liveness claim: with branch clearance as the only exit, a spurious-fire incident had no reachable resolution — `docs/formal/`) |
| `CloseInFlight` / `HeldIncident` | actuator crash mid-close | *(resume from durable state on its reconcile-only boot)* | no double-close: the fence + §2 finality contract, not command IDs, prevent re-execution (Invariants); re-attempts stay bounded `[→ Cx5-1]` |
| *(any takeover state)* | the bot recovers mid-takeover | *(bot fenced, reconcile-only)* | "A bot that recovers mid-takeover finds itself fenced and stays in reconcile-only until an operator clears it" |

**The `Fence` capability — "per-venue, verify-and-pin, with a failure branch" `[→ R1b-2, R2b-3, R1c-2, R1c-3, R2c-2]`** (core §7.4; the dated per-venue endpoint facts live in Profiles §4):

- **Definition + availability:** "Fencing = guaranteeing single-writer by making the bot unable to trade; it has **two mechanisms**, and **at least one MUST be available and propagation-tested per venue before that venue reaches `$1K`**. **Signer isolation is the *primary* mechanism on both venues** (the *fence action* is a local revoke/starve needing **no venue credential or venue call** — the signer of course holds the *trade* credential, but no additional key-management/transfer-class credential `[→ R1d-4]`; no money-moving blast radius, account-tier-independent, §7.3); exchange-side disable is the **backup**".
- **Signer isolation (primary, core §7.3):** "the order-signer runs in **its own trust boundary the actuator can fence independently of the bot host** — a minimal signer daemon (a **fourth failure domain**, or a credential the actuator solely owns and can rotate), reached by the bot over an **authenticated signing protocol**, with a **health test** (feeding `FenceReady`" — §3 here — ") and a defined **revoke/starve** mechanism. A signer that merely lived on — and died with — the bot host would **not** be re-fenceable when the bot *restarts* mid-takeover, so **co-location with the bot is not signer isolation**. It holds the **trade** credential (within the §7.3 subaccount blast radius) but **no additional key-management/transfer-class credential** and has **no account-tier dependency** — that, plus the actuator's independent control, is why it is preferred over the money-moving exchange-side path. The trade-off it *does* add (a bot-facing signing RPC + the trade credential in that domain) is part of the §7.3 blast-radius analysis."
- **Exchange-side credential disable (backup):** on **Bybit** the caller "**must hold a transfer/withdrawal-class authority** (`Account Transfer` / `Sub Member Transfer` / `Withdrawal`): a money-moving credential, so grant the **narrowest — `Sub Member Transfer`, never `Withdrawal`** (§7.3)" — the blast-radius policy for that hotter-than-the-trade-key credential stays core §7.4. "**Binance** has **no REST way to disable a *regular* account's own key** (UI + 2FA only); it is API-automatable **only if the bot runs on a *sub-account*** and the actuator holds a **master key** with sub-account management … — **which presupposes the account actually *has* sub-accounts, a tier-gated Binance feature that MUST be confirmed for the real account (§7.2 verify-item); if sub-accounts are unavailable the Binance exchange-side path does not exist and signer isolation is the sole fence** `[→ R1c-3]`". (The elided endpoint list + dated sources: Profiles §4.)
- **Tiering consequence:** "because the primary mechanism (signer isolation) needs no venue credential *for the fence action* `[→ R1d-4, Cx5-5]`, a working fence **binds at `$1K` on every venue**; the exchange-side path is a per-venue *backup* used only where it is available *and* verified (a Binance regular/sub-less account has none). The `Fence` MUST define **ack semantics + a propagation test** (prove the bot can no longer write) before it is trusted." (`FenceGateway.VerifyFence`, core §4: "propagation test: prove the bot can no longer write".)

### Invariants

- **Single-writer by transfer `[→ Codex]`:** "single-writer is preserved by *transferring* the writer, never by running two" — the actuator is a second writer and MUST fence before it trades.
- **Epoch semantics (owned here; consumed by §3's branch 2 and its durably-fenced dimension):** the latch is "a **latched, monotonic revoke *epoch***" / "a durable, monotonic takeover epoch" — the same fence-first revoke/starve primitive in both uses — "that the signer **MUST honor across restart until explicit operator clearance**, and `VerifyFence` validates **that epoch** (not a point-in-time snapshot)"; "A **point-in-time `VerifyFence` alone is insufficient** — a transiently-crashed signer could restart mid-takeover and restore **two writers**".
- **Fencing is not cancellation:** "Fencing stops *new* submissions but does **not** cancel orders the venue already holds" — hence the quiesce barrier is mandatory: "Skipping it re-creates the exact hazard: an armed stop fires *after* the reduction and leaves a naked leg."
- **Reduce only the reconciled residual:** never the pre-allocated qty ("which may be stale: an entry leg can still have filled, or a partial reduction already run"); the takeover is a §2-classifier client ("actuator takeover", §2's single-gate enumeration) and reconciles through the §2 contract at its watermark.
- **Completion is evidence-gated; terminal state is flat *or* held-with-fence `[→ R1d-1, Cx5-1]`:** the takeover never *reports* complete on issuance — completion requires **§2 finality of every close/reduction order + zero reconciled per-leg allocations + final surfaces** (exactly the evidence that gates §6's tombstone, so the two can never disagree). A reconciled neutral/near-neutral package is closed **two-leg** within the plan's loss/slippage bounds (branch 1's verb selection; an `ExposureReduction` would no-op at delta≈0, and the quiesce barrier has already cancelled all resting protection, so an open package would be **unprotected and unmanaged** with the host dead); a fixed residual is reduced; any resulting one-leg residue re-enters the §2 classifier. A close the bounds **cannot** execute (zero-fill IOC in a gapping market) enters `HeldIncident` — fence latched, plan active, operator escalated — **never a false flat**; re-attempts consume the plan's replicated **close-attempt budget** (`max_close_attempts` + `T_close`, §6), whose exhaustion enters `HeldIncident` **unconditionally**. The honest §1.1 claim is therefore: *flat when the close can execute within plan bounds; held with single-writer preserved otherwise*. **Completion evidence terminalizes the trade `[→ FM-1]`** (core §7.4): once `ActuatedFlat` exists, the trade re-admits no exposure-opening order — the plan may only proceed to the §6 tombstone, and fresh exposure is successor-only through the §6 lease. The v0.9 gap this closes was found by model-checking (`docs/formal/`, NC4): clearance (§3) requires flat/reconciled but not the tombstone, so a clearance inside the `ActuatedFlat`→`Deactivate` crash window let the bot re-enter under the still-`Active` plan, and the stale re-driven tombstone then revoked host-independent coverage under live exposure.
- **Execution authority is the actuator's own independent trade credential `[→ R1d-4]`** (core §7.3/§7.4) — never the bot's signer (which the fence has revoked/starved): single-writer is preserved as *fence the bot's principal, then trade with the actuator's distinct principal*; that credential's validity is a continuously monitored `ActuatorReady` dimension (§3 here), and branch 2 hands over only with it confirmed. **The same gate runs the whole protocol `[→ Cx6-2]`:** the watchdog activation path latches only with `ActuatorReady` confirmed (else the latch attempt times out to `FenceUnavailable` — fencing the bot with no execution capability would transfer the writer to nobody), **every actuator venue write — closes, reductions, and the quiesce cancels — requires execution readiness**, and a **mid-takeover `ActuatorReady` loss enters `HeldIncident`** (fence latched, plan `Active`, operator escalated — the transitions row above).
- **Engagement obligations are durable, and the actuator re-drives them `[→ FM-3]`:** every way this machine is engaged leaves **durable state** the actuator re-reads on its reconcile-only boot — the §3 branch (one-way per incident `[→ R1d-F6]`), the `Active` plan (`ListActive`), the latched epoch — so **engagement is never contingent on a signal being delivered or remembered**. Concretely: latched + `Active` plan → resume at the quiesce barrier; **`TakeoverTransfer` + `Active` plan + no latched epoch → re-attempt the latch** (the transition table's second standby row); `ActuatedFlat` + `Active` plan → re-drive the tombstone `[→ R1d-F7]`. The gap this closes was model-checked: with the branch-2 hand-off treated as a one-shot signal, an actuator that crashed before latching never re-engaged, and — because the branch is one-way and the bot-write gate is scoped to the branch, not to the signer's health — the **healthy bot was permanently barred while the actuator sat idle, leaving unprotected exposure with no writer at all** (`docs/formal/`). A re-attempt that cannot latch is not a stall: it times out to `FenceUnavailable` and the §3 tiered floor governs (alert + operator manual kill at `$1K`+).
- **The fence, not command IDs, prevents double-reduce:** "`Place` isn't a venue idempotency key (§5.3), so the fence — not "idempotent command IDs" — is what prevents a double-reduce."
- **Plan handles, never coarse balances:** the takeover associates orders/fills via the replicated plan's handle set (§6 here); coarse-balance fallback is forbidden (core §7.4: "never on selling from **coarse venue balances** (forbidden — it can hit unrelated inventory)").

### Chaos & acceptance cases (§9 of the core)

- **Actuator takeover fence** (core §9, mapped in full; bracketed pointers mark the sub-cases owned by sibling machines): "network partition / late-fill-after-takeover / bot-recovery-during-takeover / **fence unavailable** (no durable latch → **actuator read-only + operator manual kill at `$1K`+**, never an unfenced trade; de-minimis unfenced action only in the signed canary regime, §12, which claims no single-writer safety)" [floor: §3 here] " / **host-death with an armed stop or `DisarmPending`**" [§5 here] " / **host-death with an outstanding reduction** → single writer, **all resting orders quiesced to finality *before* the reduction**, no double-reduce, reduces only the reconciled residual / **host-death with a fully-filled *neutral* package → the takeover's two-leg close within plan bounds — terminal state flat, never an open unprotected/unmanaged package** `[→ R1d-1]` / **takeover holding only a stale entry-generation plan after later hot-path generations → complete discovery via the order namespace/prefix + venue enumeration + cursor sweep, correct residual** `[→ R1d-5]`; **actuator reconcile-only boot enumerates plans via `ListActive` (no `TradeID` list post-host-death) and never re-actions a `Deactivate` tombstone; `Replicate`↔`Deactivate` reorder/retry, crash between close and deactivation, actuator restart → no stale plan re-actioned; an actuator flatten tombstones only after zero reconciled per-leg allocations + final order surfaces (durable `ActuatedFlat` re-drives an interrupted `Deactivate`; never a premature tombstone)** `[→ R1d-F7]`" [plan lifecycle: §6 here] ") — assert journal recovery + net-delta invariant + no duplicate/over-reduction + host-independent coverage every time."
- **From the takeover bullet (core §7.4):** "Network-partition, late-fill-after-takeover, partial-fill, and bot-recovery-during-takeover are §9 cases."
- **Pre-latch actuator crash during a branch-2 hand-off `[→ FM-3]`** (core §9, the takeover-fence clause): kill the actuator between the §3 hand-off and the epoch latch, with the bot alive and barred by the branch — assert the reconcile-only boot **re-attempts the latch** from durable state (and that a re-attempt which cannot latch reaches the `FenceUnavailable` floor and alerts), never that the incident idles with **no** writer. The same test with the hand-off *signal* dropped (never delivered) MUST behave identically — the obligation is the durable branch record, not the message.

## §5. Protective-order disarm `[→ R1-F2, Z3, R2-#4, R2b-B2, Codex]`

**Source (v0.7.1):** build-spec §7.4 (host-independent-coverage bullet [the arm side] + protective-order-disarm bullet) + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §7.4 (per-venue attach facts: Profiles §1/§3); this section is the mechanism.

**Scope.** Per live leg-level protective order. "Entry-time leg-level protection exists only to bound the first-fill→hedge-complete window." The window exists because "Exposure begins the instant an entry leg fills — a *separate* venue op from any follow-on protective order, so it cannot share the fill's journal transaction" (core §7.4). Protection is armed venue-natively where a leg *verifiably* supports atomic attach (core §7.4/§1.1; per-venue attach facts + the spot-IOC caveat — "Assume the spot IOC leg is unprotected until an integration test proves otherwise" — Profiles §1/§3); the host-death backstop for every leg lacking verified attach is the pre-armed `EmergencyPlan` actuator (§6 here) — "armed **before** entry submission and covering **whichever leg fills first**" — not this machine. "Disarm is a **fenced state machine `Armed → DisarmPending → Disarmed`**, not a fire-and-forget cancel". A protective execution while still `Armed` pre-neutral is the protection doing its job — a fill event classified by §2 like any other; this machine models the disarm half of the lifecycle.

### States

| State | Meaning |
|---|---|
| `Armed` | a live leg-level protective order covers the first-fill→hedge-complete window; it **reserves** the leg allocation (core §7.4) — the §2 sizing counts it ("a protective order's leg reservation", §2's reservation-aware sizing) |
| `DisarmPending` | the disarm is in flight: the cancel is issued but "a stop can trigger *during* cancellation, and §5.3's post-cancel-late-fill rule applies" (§1 here) |
| `Disarmed` | entered only through the §6.7 finality contract (§2 here) — never on a cancel-ack alone; remaining-executable quantity has collapsed; "Ongoing protection is then package-level (the §6 monitor + this ladder), not leg-level" |

### Transitions

| From | Event / condition | To | Action / guard |
|---|---|---|---|
| *(first-fill→ack window)* | the armed protection is confirmed | `Armed` | arm side (core §7.4): the attach is "submitted atomically with the entry, but **acceptance is async — the fill *and* the armed protection are confirmed on the private WS, not the HTTP response**" `[→ R2b-B2]`; "The residual first-fill→ack window is minimized, bounded, and a §9 acceptance case" |
| `Armed` | hot-path `ExposureReduction` on the protected leg | `Armed` (same order, amended) | "A live (non-host-death) protective order **reserves** the leg allocation, so a hot-path `ExposureReduction` **amends / cancel-replaces that same fenced protective order** rather than duplicating it" (core §7.4) |
| `Armed` | neutral-hedge confirmation (both legs filled, package net-delta-neutral) | `DisarmPending` | the package is now neutral, so the armed stop has become "a naked-leg generator" (the full rationale sentence: Invariants); "on neutral-hedge confirmation the OMS issues the cancel" |
| `DisarmPending` | the protective order **partially** executes (incl. a wick-triggered late fill) | `DisarmPending` (stays) | "a protective order that **partially** executes stays in **`DisarmPending`** and is **reclassified after every fill**" (§2 here); "a partial fill with quantity still live is *ambiguous*, never compensated mid-flight" |
| `DisarmPending` | the §6.7 finality contract completes (§2 here) | `Disarmed` | "runs the **§6.7 finality contract** (not a cancel-ack alone) before `Disarmed`": the contract collapses the order's remaining-executable quantity to a fixed residual; "a protective execution is package-compensated via the fenced reduction generation **only once the finality contract collapses its remaining-executable quantity to a fixed residual**", "and the protection's inventory reservation is held until then" |

### Invariants

- **The naked-leg-generator rationale (core §7.4, verbatim):** "**Once both legs are filled and the package is net-delta-neutral, an armed leg-level stop is no longer protection — it is a naked-leg generator** (a benign wick through the spot stop-sell leaves you naked short)."
- **Never a cancel-ack alone:** disarm completes only through the §6.7 finality contract (§2 here) — "protection-disarm's sweep" reconciles "through *this* contract **and its watermark**, never a weaker cancel-ack-only variant" (§2's one-canonical-boundary invariant).
- **Ambiguous mid-flight is never compensated:** a protective execution is package-compensated via the fenced reduction generation only once finality collapses the remaining-executable quantity to a fixed residual — "a partial fill with quantity still live is *ambiguous*, never compensated mid-flight" — and the inventory reservation is held until then.
- **Reservation/amend rule (arm side, core §7.4):** a live protective order reserves the leg allocation; the hot path amends / cancel-replaces that same fenced protective order, never duplicates it (so the §2 classifier does not misread the reservation as naked exposure).
- **Package-level thereafter:** "Ongoing protection is then package-level (the §6 monitor + this ladder), not leg-level."
- **The honest acceptance claim (core §7.4, verbatim):** "Absent an atomic package-level conversion, the acceptance claim is a **measurable bound on detect→re-neutralize**, not "a wick can never create a naked leg".

### Chaos & acceptance cases (§9 of the core)

- **Protective-order disarm race** (core §9): "wick-triggered late fill during `DisarmPending` → re-neutralized within bound"; the source's own case line: "a §9 case (armed → neutral → DisarmPending → wick-triggered late fill → re-neutralized within bound)."
- **Host death between first fill and protective-order ack** (core §9) — the arm-side window: covered by the pre-armed `EmergencyPlan` backstop (§6 here) + the minimized, bounded first-fill→ack window (core §7.4).
- **Protective-order ↔ OMS inventory handoff** (core §9) — exercises the reservation lifecycle above: reserve at arm → amend on the hot path → release only at finality.
- **Host-death with an armed stop or `DisarmPending`** (core §9, inside the actuator-takeover-fence clause — §4 here): the takeover quiesces the armed/disarming protective order to finality **before** any reduction — "an armed stop fires *after* the reduction and leaves a naked leg" is the exact hazard (§4's quiesce invariant).

## §6. EmergencyPlan lifecycle `[→ Y3, Z3, R1-F2, R2c-3, Codex]`

**Source (v0.7.1):** build-spec §7.4 (actuator-authority bullet: the replicated `EmergencyPlan`) + the §4 `EmergencyPlanStore` port + §6 step 9 (Close) + §7.5 (reconcile-only boot) + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §7.4 / §6 step 9 / §7.5 (the three-failure-domain and watcher→actuator auth requirements stay core §7.4); this section is the mechanism.

**Scope.** Per-`TradeID` plan, across replicate → act → deactivate. The port (core §4): "INTERNAL driven port (NOT a venue call) — replicate the EmergencyPlan off-host BEFORE exposure opens" `[→ R2c-3, Codex]`; "EmergencyPlanStore is internal-only (off-host replication, not a venue call)". Its methods (port comments, verbatim): `Replicate` — "monotonic per-(TradeID,generation) upsert/CAS — a later generation supersedes; ack REQUIRED before the entry submits"; `ListActive` — "actuator reconcile-only boot enumerates ALL active plans — it has NO TradeID list after host death"; `Load` — "latest generation for one trade"; `Deactivate` — "TERMINAL, IDEMPOTENT TOMBSTONE — ack succeeds even if already tombstoned; after ack any Replicate for this TradeID (same OR later gen) is REJECTED (no reactivation); ListActive never returns a tombstoned trade". Why the plan exists (core §7.4): the emergency actuator "MUST act after the bot host *and its local journal* die. Because the allocation cap lives in that journal, the actuator relies on **host-independent coverage** …, never on selling from **coarse venue balances** (forbidden — it can hit unrelated inventory)."

**Plan content (core §7.4, verbatim):** "carrying, for **both legs**, everything the takeover needs *without* the host-local journal: subaccount + `TradeID`, all intended **client/algo order IDs** + the bot-owned order namespace/prefix, sides, allocated qtys, the creation window, **recovery cursors**, and attached-protection parent/child IDs, plus loss/slippage bounds + fencing generation". "Without these handles the actuator can't associate fills once the journal dies" (consumed by §4's reconcile/reduce). **v0.9 addition `[→ Cx5-1]`:** plus the **close-attempt budget** — **`max_close_attempts` + a total close deadline `T_close`** — consumed by §4's `CloseInFlight` re-attempts; exhaustion of either transitions **unconditionally** to `HeldIncident` (replicated as plan fields precisely so the actuator can enforce the aggregate bound after host death, with no config dependency).

### States

| State | Meaning |
|---|---|
| *(none)* | no plan replicated — exposure MUST NOT open: the plan "is pushed to the actuator **before exposure opens** (actuator **ack required before the entry submits**)" |
| `Active` | replicated and acknowledged; carries the latest **generation** ("monotonic per-(TradeID,generation) upsert/CAS — a later generation supersedes", port); enumerable by `ListActive()` |
| `DeactivationPending` | close-side: a durable journal record that the close reached finality but the `Deactivate` ack is not yet persisted; the hedge-group lease is retained |
| `Deactivated` (tombstone) | terminal: the idempotent `Deactivate` tombstone — rejects any same-or-later-generation replication; "ListActive never returns a tombstoned trade" (port) |

### Transitions

| From | Event / condition | To | Action / guard |
|---|---|---|---|
| *(none)* | entry planned; `Replicate(plan)` acknowledged (`ReplicaAck`) | `Active` | "ack REQUIRED before the entry submits" (port); "pushed to the actuator **before exposure opens**", "with watcher→actuator auth and independent key/IP" (core §7.4) |
| `Active` | a later protection/reduction generation is created | `Active` (generation++) | "later protection/reduction generations are replicated **as they are created** (monotonic generation upsert/CAS)"; a later generation supersedes (port). **Async — never load-bearing for coverage** (the prefix-completeness invariant below `[→ R1d-5]`); a **policy-changing** generation (bounds/fencing edits) takes effect **only after its replica ack** |
| `Active` | the close reaches finality (core §6 step 9) | `DeactivationPending` | the OMS "**journals a durable `DeactivationPending` before/atomically-with close finality, retains the hedge-group lease while pending, and invokes the idempotent `EmergencyPlanStore.Deactivate` (a terminal tombstone)**" |
| `Active` | **the actuator's own flatten completes** `[→ R1d-F7]`: the §4 takeover's two-leg close / reduction done, **per-leg reconciled allocations zero**, **all order surfaces final** (§2's contract + watermark) | `DeactivationPending` (actuator-side) | the actuator persists a **durable `ActuatedFlat`** record, then drives the same idempotent `Deactivate`; **tombstoning earlier is forbidden** — a tombstone rejects all future replication, so it must never precede proved-flat evidence |
| `DeactivationPending` | the `Deactivate`'s **persisted acknowledgement** | `Deactivated` (tombstone) | "only its *persisted acknowledgement* releases the lease or admits a successor trade"; idempotent: "ack succeeds even if already tombstoned" (port) |
| `DeactivationPending` | crash between close and ack, or the store is unreachable | `DeactivationPending` (held; re-driven) | "A crash between close and ack is recovered by **reconcile-only boot re-driving the pending `Deactivate` (idempotent, bounded backoff, alert)**" (core §6 step 9, §7.5); "Holding the lease while the store is unreachable is the correct fail-safe (a symbol waits rather than risk a stale-plan takeover against a successor)". **Actuator-side symmetrically:** an actuator crash between its flatten and the tombstone re-drives from the durable `ActuatedFlat` record on its reconcile-only boot `[→ R1d-F7]` |
| `Deactivated` (tombstone) | a same-or-later-generation `Replicate` arrives (reorder / retry) | `Deactivated` (replication rejected) | "after ack any Replicate for this TradeID (same OR later gen) is REJECTED (no reactivation)" (port); "a flattened trade leaves **no stale, still-actionable plan** even under `Replicate`↔`Deactivate` reordering" (core §7.4) |

### Invariants

- **Replicate-before-exposure, ack-before-entry `[→ R2c-3, Codex]`:** the plan is replicated off-host **before** exposure opens and the actuator ack is **required before the entry submits** — the *(none)* → `Active` guard above; entry-time arming order is a core §6/§7.4 requirement.
- **Actuator boot reads `ListActive`, never a `TradeID` list (core §7.4, verbatim):** "The actuator's **own reconcile-only boot enumerates active plans via `EmergencyPlanStore.ListActive()`** — it has no `TradeID` list once the host is gone — applies the **latest generation** per trade, and treats a **`Deactivate` tombstone** as terminal (rejecting any same-or-later-generation replication)". **That boot also re-drives §4's engagement obligations `[→ FM-3]`** — an `Active` plan whose incident is in branch 2 with **no latched epoch** means a takeover is owed and the actuator re-attempts the latch (§4's transition table); the boot is where every durable obligation is re-derived, not only the plan set.
- **Close awaits the tombstone (core §7.4):** "the normal **Close awaits that tombstone before releasing the lease** (§6 step 9), so a flattened trade leaves **no stale, still-actionable plan** even under `Replicate`↔`Deactivate` reordering."
- **The lease is never released with a plan still active (core §6 step 9, verbatim):** "the lease is **never** released with a plan still active — so a closed trade leaves no plan an actuator restart could re-action, even under `Replicate`↔`Deactivate` reordering or a mid-close crash". The §7.5 restatement: "A journaled **`DeactivationPending`** (a close that had not confirmed its `EmergencyPlanStore.Deactivate`) is **re-driven to acknowledgement (idempotent, bounded backoff, alert) before its hedge-group lease is released** — a closed trade never leaves an active plan behind".
- **Generations are monotonic:** per-(`TradeID`, generation) upsert/CAS; a later generation supersedes; the actuator always applies the **latest** generation (port + core §7.4).
- **Prefix-complete discovery — replication is freshness, never coverage `[→ R1d-5]`** (core §7.4): every order the bot ever submits for a trade carries a client/algo ID **deterministically derivable from the entry-generation plan's replicated order namespace/prefix**, so a takeover holding only an older generation still discovers **every** bot-owned order/execution by venue-side enumeration (`EnumerateResting` + the **`HistoricalOrders`** port — normal *and* algo history, server↔client ID mapping, end watermark `[→ Cx5-3]`) + the §2 executions sweep from the replicated cursors (an older cursor widens the sweep, never narrows coverage **within venue retention**). **Handle-bearing** generations (hot-path order IDs) replicate async under this guarantee — a per-generation ack-before-external-write was **rejected** (it would couple an emergency reduction to plan-store availability); **policy-changing** generations (bounds/fencing — approval-kernel, human-timescale) require the replica ack before taking effect, so the actuator never holds *looser* bounds than the bot trades under. **Retention bound `[→ Cx5-3]`:** venue history expires (Binance ≈90d orders / ≈6mo trades — Profiles §4), so a **periodic acknowledged checkpoint generation** (config cadence, e.g. daily: accumulated server-order-ID↔client-ID map + fresh cursors) keeps the un-checkpointed window days-wide — discovery never depends on expired venue history.
- **A terminal trade re-admits no exposure `[→ FM-1]`** (core §7.4): once a trade's flatten reaches completion evidence — the actuator's durable `ActuatedFlat` record (§4 here), or the bot-side close reaching §2 finality with flat evidence — the only remaining lifecycle step is the tombstone (re-driven across restarts, both sides); no exposure-opening order may reference the trade again, and new exposure is a **successor trade** admitted by the lease, which only the tombstone releases. This closes the model-checked hazard of a stale re-driven tombstone landing under freshly re-admitted exposure (`docs/formal/`, NC4).

### Chaos & acceptance cases (§9 of the core)

- **Plan sub-cases of the actuator-takeover-fence clause** (core §9, mapped in full; the clause itself is quoted in §4): "**actuator reconcile-only boot enumerates plans via `ListActive` (no `TradeID` list post-host-death) and never re-actions a `Deactivate` tombstone; `Replicate`↔`Deactivate` reorder/retry, crash between close and deactivation, actuator restart → no stale plan re-actioned**".
- Mapping: reorder/retry → the tombstone-rejection row; crash between close and deactivation → the re-drive row (core §7.5); actuator restart → the boot invariant (latest generation; tombstone terminal, never returned by `ListActive`).

### Flagged ambiguities

- **[FLAG-7 — resolved v0.9 `[→ R1d-F7]`]** *Was:* the deactivation path for a trade flattened **by the actuator** (host dead) was never stated. **Ruling (round 4):** reading (ii), evidence-gated — the actuator tombstones **only after** a proper two-leg emergency close (§4's terminal-flat action `[→ R1d-1]`), **zero per-leg reconciled allocations**, and **final order surfaces** (§2's contract + watermark); it persists a durable **`ActuatedFlat`/`DeactivationPending`** record *until that tombstone is durable* (an interrupted `Deactivate` is re-driven from it on the actuator's reconcile-only boot). A premature tombstone is forbidden — it would reject all future replication while flat was unproven. The transitions table above carries the actuator-side path.

## §7. PackageDelever generations & reserved reductions `[→ R1b-1, C4, C5, P3, X2, R2c-1]`

**Source (v0.7.1):** build-spec §5.3 (`PackageDelever` command) + §7.1 (trigger / top-up / escalation) + §9 — re-expressed, no new behavior. **Normative owner:** the requirement + tag live in core §5.3 + §7.1; this section is the mechanism.

**Definition & entry context (core §5.3, §7.1).** `PackageDelever` is "foundation-originated, **exempt from `stop-opening`**, used to **reduce leverage on a *still-neutral* package** when isolated-margin liq distance breaches and the top-up path fails". The escalation chain that reaches it: the §5.2 `liq_distance` **rebalance** threshold (<20% BTC; tighter for alts) breaches — "recomputed via the OMS-owned mark-risk read port … on every mark update *and* every margin/position/tier-change event" (never account-event-only; "a **stale mark feed blocks openings and escalates** … never silently freezing the trigger" `[→ R2c-1]` — the escalation is **defined** in core §7.1: REST-mark failover on the reserved rate-limit budget, then the `T_blind` pre-authorized de-risk (`PackageDelever`/close per `mark_blind_action`) `[→ R1d-9]`) — → the **active top-up** (Binance `POST /fapi/v1/positionMargin {type:1}`; Bybit `POST /v5/position/add-margin {margin:+}`) with its **bounded latency budget** (alert-on-miss) and **reserved rate-limit allocation** → "if the top-up fails or misses its budget (rate-limit, venue lag, insufficient staged margin), the ladder **escalates to a `PackageDelever`** … rather than waiting". It is "deliberately **not** an `ExposureReduction`: the package has **no naked residual**, so an `ExposureReduction` would either no-op (delta≈0) or, by reducing a single leg, *create* a naked leg during the rally."

### States

Generation phases, derived from the core §5.3 `PackageDelever` sequencing prose (phase-boundary caveats: FLAG-3, FLAG-4):

| State | Meaning |
|---|---|
| `Planned` | a **generation** is created: "each **generation is a bounded attempt**" carrying "**explicit per-leg target positions**"; its intended net-long transient is "an **atomically reserved part of the fenced generation**" from creation. **The entry exists from creation and carries the generation's *outstanding net intent*, never its target `[→ FM-5]`:** at `Planned` the perp leg has bought nothing, so the reserved **amount is zero**, and it is **amended** as the perp reduction confirms (§2's own "coalesce / amend / cancel-replace it, never a fresh command per event", applied to the reservation rather than to the order). Booking the *target* at creation makes a still-**neutral** package read to the §2 classifier — which subtracts the ledger unconditionally — as **short by the target**, and its determined branch then buys back exactly the exposure this generation's own perp leg is about to buy (model-checked; the literal reading is control `NC7`, `docs/formal/`) |
| `PerpReduceInFlight` | the perp-short reduction (buy-to-reduce) is submitted **first** — "which itself relieves the liq risk" |
| `PerpReduceFinal` | the perp reduction is confirmed **to finality** (§2; core §6.7) |
| `SpotReduceAuthorized` | a **durable journal record**, entered on perp-reduce finality, authorizing the reserved spot reduction's dispatch `[→ R1d-F3]` — the §5.3 crash-boundary discipline at generation scope: recovery reads it and knows the perp-finality precondition was met (the spot order itself then follows §1's own `DispatchAuthorized`); the reservation itself is generation-scoped from creation, not first made here — **what is first *fully amounted* here is its amount `[→ FM-5]`**, since by this state the perp reduction is confirmed and the outstanding net intent equals it |
| `SpotReduceInFlight` | the reserved spot reduction is submitted — "**sells no more spot than the confirmed perp reduction**" |
| `Complete` | the generation has reached §6.7 finality; only now is a next generation admissible |
| `Held/Alert` | "a leg that is deadline-exceeded/ambiguous **holds and alerts, never blind-retries or blind-flattens**" |
| `TerminalFlatten` | "if it cannot complete, its **terminal full-flatten routes through the same §6.7 finality contract** (the liquidation-imminent branch), not a blind market dump" |

### Invariants

- **Perp-short-first sequencing — never net-short `[→ R1b-1]`:** the reduction is "**sequenced so the transient never worsens the at-risk direction**": perp short reduced *first*, confirmed to finality, then "**sells no more spot than the confirmed perp reduction** — the momentary exposure is thus net-*long* (safe in the triggering rally), **never net-short**."
- **The reserved second leg vs the §2 classifier:** "That intended net-long transient is an **atomically reserved part of the fenced generation**, so the §6.7 classifier **subtracts the reservation** and does **not** misread it as a naked residual to re-hedge — only the **reserved spot reduction** (never a policy-selected re-hedge) completes the generation."
- **A generation's ledger movements are §2 re-classification triggers `[→ FM-6]`:** every transition here that creates, amends or retires the generation's entry — `Planned` (created at zero), the perp leg's confirmations (amended upward), `Complete`, `TerminalFlatten`, and either supersession row — changes `outstanding_reserved_reductions` and therefore changes the residual §2 gates on, **while emitting no fill and no order event**. §2's classifier MUST re-run on each. Without it a generation can end with the classifier's verdict frozen at whatever the last *order* event left it: found by model-checking as a **dead end** — every interval collapsed, the verdict still `DeadlineExceeded`, its one permitted action (the interval floor) already spent, and a determined naked residual with dispatch budget in hand and nothing enabled. The path that reaches it is the perp-side `Held/Alert` park, because it is the **only** exit from a generation that does not pass `PerpReduceFinal` (`docs/formal/`, control `NC19`).
- **The reservation is exactly backed at every instant `[→ FM-5]`:** the entry's *existence* is generation-scoped from creation (FLAG-3), but its **amount is the generation's outstanding net intent** — the confirmed perp reduction not yet matched by the reserved spot sale — so it is **zero at `Planned`**, grows with the perp leg's confirmed fills, and returns toward zero as the spot leg sells. It is **amended**, never re-created per event. The rule this replaces was not wrong about existence but silent about amount, and the silence was exploitable: **§2's sizing subtracts the ledger unconditionally, so a reservation booked ahead of its counterpart is indistinguishable from a real short.** The check that would catch it cannot: §2's overshoot reasoning is phrased over quantities *computed from* the ledger, so a corrupt ledger corrupts the check too and the phantom buy computes as non-overshooting — **an invariant built on the ledger cannot audit the ledger** (model-checked: `docs/formal/`; the literal reading is `NC7`, and the dispatch it produces is exhibited at three steps).
- **Bounded generations, gated on finality:** explicit per-leg target positions; "each **generation is a bounded attempt made *only after* the prior generation reaches §6.7 finality**"; the escalation ladder is "bounded and terminal-escalating, dropping notional/margin requirement" (core §7.1).
- **Never blind:** a deadline-exceeded/ambiguous leg "**holds and alerts, never blind-retries or blind-flattens**"; the terminal full-flatten routes through the §6.7 finality contract, never a blind market dump.
- **Completes the target on a determined leg failure** — "never buying the spot back to restore neutrality *and* the original notional (that would re-arm the same liq breach and loop)."
- **Not an `ExposureReduction`:** "the package has **no naked residual**, so an `ExposureReduction` would either no-op (delta≈0) or, by reducing a single leg, *create* a naked leg during the rally" (also core §7.1: "the package is still neutral, so reducing a single leg would *create* a naked leg").
- **"No naked residual" is a STANDING condition, not only an entry test `[→ FM-8]`.** The clause above is the generation's **entry** precondition, and it is evaluated on §2's **reservation-netted** residual — so it admits a package that is neutral *pending an in-flight reduction* rather than physically flat. That reading is retained (a reserved reduction genuinely offsets the exposure it is reducing), **but it is no longer sufficient on its own**, because the reservation it nets against can be **released without executing**. §2 row 4 is the route: when a reduction's *own* result comes back ambiguous it "never blind-retries — its own ambiguous result routes through this same §6.7 finality contract", so its ledger entry is released and the exposure re-enters as an **unresolved order contributing an interval**. **This is true of every reduction that owns a ledger entry, not only the interval floor** — the model's witness (`PC28`) uses an ordinary `ExposureReduction`, and an `IntervalFloorReduction`'s own ambiguous result behaves identically; only §7's own `PackageDelever` spot leg is excluded, because that entry *is* the generation's. Naming a single producer here would repeat `FM-5`'s own fix mistake, where a rule derived from one of the ledger's three producers read as universal. The generation is then running on a premise nobody re-checked — the package physically exposed and no longer even `Determined`. **Therefore: while a generation is active, the premise leaving the state the generation opened under supersedes it** (the transition row above), quiescing the reserved second leg to §6.7 finality first. A precondition checked once can be falsified the instant afterwards, and **the stronger *physical*-neutrality reading would not have closed this** — a floor issued after the generation opens moves the package underneath it just the same, which is why the fix is the standing obligation and not a tighter entry guard. Found by model-checking (`docs/formal/`, model (a) probes `PC27`/`PC28`, reached at 3 and 4 steps); it is **`FM-5`'s mirror** — that was a reservation counted *before its backing existed*, this is a reservation's *premise outliving the entry*, and both are §2 and §7 disagreeing about what the shared ledger means.

- **The standing obligation is a rule about EVENTS, not a state predicate `[→ FM-8]`.** The dissolved state is **reachable and legal** for exactly as long as this section's quiesce obligation takes, because the reserved second leg must reach §6.7 finality **first**. So the rule is not *"a generation never coexists with a dissolved premise"* — that would forbid the window this very section mandates, and could be satisfied only by violating the quiesce rule. It is: **while the premise is dissolved the machine MUST NOT take the generation further** — no leg submitted, no spot authorized — and MUST discharge the supersession. Venue events (fills, finality) and the `Held/Alert` parks are unaffected: they are what the quiesce window is made of. Model (a) checks it as `INV9`, read from a flag written at the decision, which is the shape `INV6` above already uses for the same reason. **Two boundaries of "take it further", both established by model runs rather than by argument, and both binding on an implementation `[→ FM-8]`:** *(a)* it does **not** cover **sending a leg that was already authorized** — the amount was fixed at authorization and the entry is already in the shared ledger, so refusing to send it does not prevent a commitment, it **strands** one, which is the harm the quiesce rule above exists to forbid. Blocking it in the model produced a generation frozen at `SpotReduceAuthorized` on a package that was **physically flat and `Determined`**, unable to finish. *(b)* the obligation must be **DISCHARGED, not merely permitted**: an implementation that makes the supersession *possible* on the next event and never guarantees it has a real stuck state — the model's counterexample is a generation halted at `PerpReduceFinal` with a genuinely dissolved premise, the dispatch budget spent so §2 cannot compensate either, and the one action that would end it available and never taken. **A standing obligation nothing is obliged to discharge is not a standing obligation**, and it is a liveness requirement (`P5`) rather than a safety one, so no invariant will find it for you — model (a) keeps both boundaries as committed controls (`NC23` for the discharge obligation) rather than as prose, because the first encoding got the second one wrong with a written reason beside it.
- **`FM-9` — the trigger names a quantity the generation itself moves `[→ FM-9]`.** v0.9.25 stated the trigger as *"the §2 classifier leaves `Determined` for this hedge group"*. **The generation's own perp reduction is an exposure-changing order on that group**, so submitting it drives the classifier out of `Determined` by itself — and §7 *requires* that (it is how §2 refuses every compensating trade while the leg is live). Under the literal reading the row therefore fires on the generation's own first step: model (a)'s control `NC22` reaches it **4 states from `Init`, with `realized = 0`, nothing outstanding and no external event whatsoever** — a generation opened on a genuinely, physically flat package and aborted one step later by its own machinery. **A spurious abort is not free**: §7's generations exist because the perp short is nearing liquidation, so cancelling one cancels the mechanism that was reducing the risk, and does it with a reserved leg out. **The trigger is therefore the entry test re-evaluated NET OF THE GENERATION'S OWN LEGS** — this generation's unsold transient removed from the realized delta and its own ledger entry removed from `outstanding_reserved_reductions`, both sides of the same subtraction. That quantity is **invariant under every step of the generation's own ladder** (perp fills raise the transient and amend the entry by the same amount — `FM-5`'s fix, stated as a quantity), so it moves only when something *external* moves it, which is what "the premise dissolved" means. Checked as `INV10`, whose control is the literal sentence itself. **This is the third finding in the same family** — `FM-5` (an entry read before its backing exists), `FM-8` (an entry's premise outliving it), `FM-9` (a rule evaluated on a quantity that includes its own subject); all three are §2 and §7 disagreeing about what the shared ledger means, and none was visible to any invariant phrased over the ledger.
- **Model status, stated exactly:** the ruling's encoding and its controls **LANDED** in slice F (`AmbiguousOrder.tla`, constants `PREMISE_IS_STANDING` / `PREMISE_NETS_OWN_LEGS`; `INV9`/`INV10`; controls `NC21`/`NC22`; probes `PC29`/`W5`). `NC21` — the pre-ruling world, the precondition as an entry guard alone — **violates `INV9`**, and `W5` shows its harm reaches a **nonzero spot sale** on the dissolved premise rather than only a flag. `PC29` shows the new row **fires** in the nominal model, so `INV9`'s greenness is a guard doing work rather than a rule nothing exercises.
- **Ambiguous top-up result ⇒ re-query first:** "(timeout, success unknown) it **re-queries margin + position first** (the add-margin may have applied)" — a lost timeout may mean the top-up actually applied. **The op itself is a durable journaled `MarginOp`** (local op ID, intended delta, before-state + watermark, fsynced before dispatch) **resolved by per-venue evidence, never point lookup, never a blind delta retry** — Binance `positionMargin/history` match; Bybit `positionIM` delta vs before-state (its transaction-log documents no margin type); the escalation reads *live* state, so a lost ack cannot fake a restored liq distance (core §7.1, Profiles §4) `[→ R1d-6]`. **Same-position ops are serialized and `MarginOpStatus` includes a first-class `Ambiguous`** (coincident adjustment / duplicate same-amount row → no delta retry, openings blocked, live-state safety continues, explicit float reconciliation) `[→ Cx5-4]`.
- **Supersession quiesces the reserved leg first:** **all three** superseding paths (`EmergencyClosePackage`, core §5.3; `FenceReadyLost`, core §7.4/§3 here; **the premise-lost row `[→ FM-8]`**) cancel/quiesce the generation's reserved second leg **to §6.7 finality first**. The third was added with `FM-8` and is deliberately given no separate discipline: it is the same obligation, so it is policed by this same invariant rather than by a new one.
- **Escalate, don't wait:** "A slow top-up under stress is the same failure class §7.1 warns about for spot→futures transfers, recreated one level down, so it gets a pre-authorized fallback" (core §7.1).

### Chaos & acceptance cases (§9 of the core)

- **Margin top-up under stress** (core §9, mapped in full): "liq-distance breach → `positionMargin`/`add-margin` top-up within budget; on failure/slow → **re-query margin/position, then `PackageDelever`** (**perp-short-first-sequenced**, transient **never net-short**, bounded + terminal-flatten escalation), never wait and never a single-leg `ExposureReduction`."
- **Mark-price-driven liq breach** (trigger side, core §9): "a pure rally moves mark toward the short's liq price with **no** account event → liq distance recomputed on the **mark stream** → rebalance/top-up fires; a **stale mark feed** blocks openings + escalates, never a frozen trigger" `[→ R2c-1]`.
