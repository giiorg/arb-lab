## 1. Product scope & non-goals

**Goal.** A multi-exchange funding-rate arbitrage platform. The platform is a **strategy-agnostic foundation** that runs pluggable, parametrized **strategies**. The MVP proves the foundation end-to-end with **cash-and-carry** on **Binance + Bybit**, built **N-venue-ready** from day one.

**MVP scope.**
- Venues: Binance (spot + USDⓈ-M linear perp) and Bybit (spot + linear perp). Adding a venue = implement one adapter (§4).
- Strategy #1 (proven first): **cash-and-carry** — long spot + short perp on the same venue, harvesting positive funding.
- Strategy #2 (next): **cross-exchange spread** — long perp on the low-funding venue, short perp on the high-funding venue. Scoped to alt pairs / dislocation windows, **not** majors `[→ P1]`.
- Real capital, live (eventually). Correctness, **durable order/account truth**, custody/key security, reconciliation, and money-losing edges are ship-blockers `[→ risk bar, X1]`.

**Explicit assumptions / scope boundaries** (previously scattered in the tutorial — now normative) `[→ pedagogy]`:
- **Deployment shape:** a **single-process engine** for MVP — all bounded contexts run in one `arblab-bot` binary over an in-process dispatcher (§3) `[→ D1]`. N-service split is a documented later path (§3.7), not built.
- **Authoritative state:** one context — `oms` — is the **single writer** of order/fill/trade/position truth, backed by a durable **write-ahead journal**. No other context mutates that state `[→ X1, X3]`.
- **Contracts:** linear USDⓈ-M / USDT-margined perps only in MVP. Inverse (COIN-M) perps are out of MVP scope; the adapter still carries a `ContractType` so neutrality math can branch later `[→ C6]`.
- **Position mode:** One-way mode on both venues (single net position per symbol). The venue nets all strategies' exposure per symbol, so the OMS enforces an exclusive lease per `(account, venue, symbol)` unless explicit allocation accounting is built `[→ X3]`.
- **Margin collateral:** plain **USDT or USDC only** (the Oct-2025 USDe local-mark failure is the reason) `[→ S1]`.
- **Money math:** the `platform/fixedpoint` scaled-integer decimal type **everywhere** — no `float64` in any price/size/notional/margin/rate/fee path, lint-enforced. Intermediates use 128-bit/`big.Int`; values are wrapped in **dimensional types** (`Money`, `Quantity`, `Price`, `Rate`). The four **categories are compile-time-distinct Go types** — a `Price` will not add to a `Money`, a `Rate` will not stand in for a `Quantity` — so category errors fail the build. The **asset/currency tag *within* a category is a runtime field** (`Money.Currency`, `Quantity.Asset`): because venue assets are discovered dynamically they cannot be phantom-typed, so same-category mismatches (USD vs USDT, BTC vs ETH) are caught by a **runtime `Validate()` on every cross-value operation**, not by the compiler `[→ D3, X7, R2-#10]`.
- **Time:** exchange **server time is authoritative**; the injected `Clock` models per-venue server-clock offset + uncertainty. Domain/application code reads time only from the `Clock` (§3.5), never `time.Now()` `[→ D4, X8]`.

**Non-goals (MVP).** True HFT / co-location / kernel-bypass; options/vol overlays; DEX/perp-DEX legs; portfolio-margin optimization; automated tax filing (emit records only); multi-process **split of the trading-engine's bounded contexts** / NATS on the trading loop (seam documented §3.7, not built — **the operator/control and actuator processes are *separate required* deployment domains, §11/R2c-4, not part of this non-goal**); cross-strategy netting on a shared `(venue,symbol)` (excluded by the exclusive lease, §3.2) `[→ X3]`.

## 2. Strategy model

### 2.1 The edge, stated honestly `[→ P1, P2, P3]`

Two different trades with different edge magnitudes; the foundation supports both, MVP leads with the first:

- **Funding *level* (cash-and-carry).** Long spot + short perp on one venue collects that venue's funding when it is positive. This is the ~5–10% APY the research documents (what Ethena industrializes). The **level** is the edge.
- **Funding *spread* (cross-exchange).** Long/short perps across two venues collects `F_high − F_low`. On majors this spread is sub-bp to low-single-digit-bp/8h and mean-reverts within hours, while round-trip cost is ~0.29% — so it rarely clears break-even for a realistic hold. Therefore cross-exchange is scoped to **alt pairs and dislocation windows** with a much higher edge bar.

**Hurdle rate.** Net APY MUST be evaluated against the on-chain **near-risk-free** floor (tokenized T-bills ~4.6% — "near" because it still carries smart-contract / counterparty / depeg risk, so the benchmark is **haircut-adjusted**, never called "risk-free"), not zero `[→ P2, R2c-10]`. The **hurdle benchmark is itself a dated, sourced, revision-controlled input** — its **source + as-of timestamp + access cost + liquidity haircut + smart-contract/counterparty haircut** are recorded and **replayed like any calibration revision** (§8/§3.5), **never a hardcoded `4.6%` constant** (the number above is illustrative); a change to the benchmark forces a new revision the same way a threshold change does `[→ R2c-10]`. Report strategy return on the **full allocated bankroll `C_allocated`** (§2.2 — spot principal + perp margin + rescue margin + fee/slippage reserve + committed float), never on posted margin or on the leg-capital floor `[→ 4.2 of review, Codex]`. **A gate MAY report on a denominator other than `C_allocated` on one condition: the denominator is explicitly declared in the artifact and is demonstrably *at least* `C_allocated` at the run's declared sizes and leverage** — the prohibition above names the two failure modes (posted margin, the leg-capital floor) and both are *smaller* denominators, because the risk this rule exists to bound is a flattered return. A larger declared denominator can only understate the figure, so it makes the hurdle comparison strictly harder; what it must never be is *implicit*, since a reader who assumes `C_allocated` would then read a number that means something else. *(Landed v0.9.23 with strategy #2's cross-venue gate, which reports on the per-leg notional: at 4× the two perp legs post `notional/2` in margin and `C_allocated` adds only the rescue margin and fee/slippage reserve on top, so the notional is the larger number and no leverage uplift enters the verdict arithmetic at all — crossvenue-gate design record §45p.)*

**Tail reality — stated precisely `[→ P3, X2]`.** ADL is a *realized* hedge-failure mode. The subtle part: in the Oct-2025 crash the exchange force-closed **profitable short** legs (ADL), leaving desks **naked long into a still-falling market** — the hedge vanished exactly when it was needed. So cash-and-carry's advantage is narrower than "spot offsets the loss":
- The **spot leg is not ADL'd or seized to cover the perp loss** — *under the pinned segregated/isolated account posture (§4.1), verified at boot* — so you never lose the whole position involuntarily. (A posture property, not a law of spot: a unified-collateral account would let the margin engine reach the spot.)
- But a **force-closed perp short still leaves directional exposure** that MUST be detected from a private account/ADL event and **auto-rehedged or flattened immediately** (§7.4). Waiting for the next monitor tick is too slow.
- Sizing MUST budget the **naked-leg price gap + reacquisition slippage** during the unhedged window, not merely "budget for ADL" `[→ X2]`.

### 2.2 Strategy #1 — Cash-and-carry (MVP flagship)

- **Setup:** long `q` spot + short `q` perp, same venue, same asset. Net delta ≈ 0.
- **PnL:** `Σ funding_received − fees − slippage − borrow(if any) ± basis_drift`. The spot and perp price terms cancel modulo spot-vs-perp basis.
- **Capital.** **Minimum leg capital** `C_legs = N + N/L_perp = N(1 + 1/L_perp)` (at 3× perp, ~1.33·N). But the **denominator for hurdle, APY, utilization, and concentration is `C_allocated`** = spot principal + perp initial margin + **rescue margin** (§7.1) + fee/slippage reserve + committed venue float — *all* capital at risk, per "report on the full bankroll" (§2.1). `C_legs` is a floor, not the reporting base `[→ Codex]`. Lower capital efficiency than perp-perp, but no inter-venue basis risk and no second counterparty for the hedge.
- **Enters when:** venue funding is positive and expected forward funding over the hold clears (round-trip cost + hurdle) with margin `[→ C2, C3]`.
- **Primary risk:** **negative-funding regimes** (e.g., the 46-day negative streak in 2026) turn the carry negative → the strategy MUST detect and **stand down through a hysteresis band** (§2.4), not a naive sign flip that whipsaws, and never hold a now-negative carry `[→ 04 negative-regime, R1-F3]`. Secondary: perp-short liquidation on a sharp rally → rebalance margin from pre-funded rescue collateral (§7.1); **recompute liq distance on every fresh perp mark-price update *and* every margin/position/tier change** — liq distance is a function of **mark price** (a market-data event that moves continuously with no account mutation), so a rally can breach the rebalance threshold with **no** account event; a **stale mark feed itself blocks new openings and escalates open positions** (the escalation is defined — REST-mark failover, then a bounded pre-authorized de-risk, §7.1 `[→ R1d-9]`) `[→ R2c-1]`.

### 2.3 Strategy #2 — Cross-exchange spread (post-MVP)

- **Setup:** long perp on lower-`F` venue, short perp on higher-`F` venue, equal base quantity `[→ delta residual math]`.
- **Scope:** alt pairs and dislocation windows only; edge bar set from measured spread persistence, not the headline spread `[→ P1]`.
- Inherits the full two-venue execution/one-leg-failure machinery (§6) — which is exactly why it is valuable to build the foundation for it even though MVP leads with cash-and-carry.

### 2.4 Break-even & sizing math — single-sourced `[→ C1, C2, C3]`

- **One source of truth for cost.** Round-trip cost MUST be computed from programmatically-fetched, per-leg, per-venue maker/taker fees plus a measured slippage model. No hardcoded fee constants; no second copy of the number in another module `[→ C1]`. **Spot taker fees are materially higher than perp** (~0.075–0.10% vs ~0.05%) and MUST be fetched separately — do **not** reuse the perp round-trip figure for cash-and-carry. **How "programmatically-fetched" composes with §3.5's replay discipline: a fee fetch lands as a dated, provenance-carrying reference revision, and the decision path — live and replay alike — reads the fee (and lot-rule, and hurdle) revision *as-of the decision instant*, never by a scoring-time venue call; a revision without provenance (writer class, observed-at, document revision) is refused.** The `fetched` class carries two writer shapes, split by what the endpoint answers for (§69): fee rows require the AUTHENTICATED fetch (the venue answers for the account's tier — the account-real precondition below), while **lot-filter rows are written by the unsigned public fetch** (`arblab reference fetch`, milestone 3): the filter endpoints are venue-published definitions, a fetched lots revision is a NEW dated document (never an in-place overwrite — an existing output target refuses), and every fetched row is bound to its whole cell before the stamp: HTTP 200 required before decode, redirects not followed, and the venue's own base/quote/status/contract-type words must agree with the row's, so a suspended instrument or a wrong-cell body refuses rather than earning `fetched` provenance. Without this clause the sentence reads as demanding a venue call at scoring time, which §3.5 forbids and which no replayed sample could satisfy. **Milestone-2 authorization: the pre-capital gate MAY be scored on a sourced, dated, published-tier fee revision explicitly labeled modeled-tier (VIP0/non-VIP); account-real authenticated fee revisions are a precondition of any live order.** Without it, the milestone-2 gate — scored before any authenticated account exists — is non-conforming the day it is scored, and the record absorbs the violation silently *(both clauses landed v0.9.17, taken at the `ReferenceData` port — strategy design record §40d)*.
- **Discrete settlement.** Expected funding capture MUST enumerate the actual settlement timestamps inside the planned hold on each leg (from live `nextFundingTime` + `fundingIntervalHour`) and sum expected per-settlement rates. It MUST NOT multiply a per-hour rate by hours as if funding accrued continuously `[→ C2]`.
- **Interval is live, not static.** Funding interval is read per-symbol on every market-data update, because Bybit can flip an alt's interval 8h↔1h mid-position without notice `[→ C8]`.
- **Min-edge from measured drift.** The entry threshold multiplier MUST be derived from the empirically-measured distribution of `(realized_settlement_rate − entry_estimate)` per symbol/venue (e.g., cover the p75–p90 adverse drift), not a flat 2× `[→ C3]`.
- **Forward-funding forecast is an explicit, testable model `[→ R1-F3, R2-#3, Codex]`.** Venue feeds expose an *evolving estimate for the next settlement*, not a forward curve, so a multi-settlement hold needs a stated estimator. Contract: `FundingForecast.Estimate(inst, horizon) → []SettlementForecast{ts, expRate, dispersion}` over the **horizon = the settlements enumerated in the planned hold** (the discrete-settlement rule above). **Default:** the imminent settlement uses the live per-settlement estimate; later settlements use a **trailing realized-settlement EWMA** (half-life a strategy param, default ~3 days), clamped to the live cap/floor; `dispersion` is the per-symbol adverse-drift distribution (C3). The **decision quantile** is a param (default p25 of expected carry — size the edge to a conservative outcome, not the mean). Hot-reloadable, and MUST clear **out-of-sample calibration thresholds** against the §8 persistence model (predicted-vs-realized coverage) — it is *the edge*, specified and measured, never assumed. `MarketView` carries the raw materials (live estimate, recent realized settlements, live cap/floor, interval). The planned hold is a **durable `HoldPlan`** (explicit settlement timestamps + terminal time, recorded at entry) so exit evaluates its *remaining* settlements unambiguously. Because the quantile of a *sum* is **not** the sum of marginal quantiles, aggregation uses a **stated joint rule** — default **conservative**: one adverse scenario with each settlement at its per-settlement adverse quantile and funding/basis co-moving against you, not independent draws (a strategy param, §5.2).
- **Decide on expected *total* carry at the decision quantile, not mean funding alone `[→ R2-#3, Codex]`.** All terms are in **one unit — USD over the `HoldPlan`, then a return on `C_allocated`** — so entry requires `Q_p[ Σ funding + basis_convergence − round-trip cost − slippage ] − reserve/opportunity-cost ≥ hurdle · C_allocated · holdFraction` (the ~4.6% floor, §2.1/§2.2; **`holdFraction` = the planned hold's duration as a fraction of a year**, scaling the annualized hurdle to the actual hold length `[→ R1b-6a]`), the quantile taken under the joint aggregation rule above. **Basis** enters via a `BasisForecast` port; absent a configured estimator the **default is conservative — assume zero favorable convergence and charge the measured adverse basis move**, never an optimistic basis credit.
- **Exit is an incremental continue-vs-close score, not a re-run of the entry test `[→ R1-F3, R2-#3, Codex]`.** Entry costs are **sunk** once paid, so exit does **not** re-subtract the round trip (that would double-count and exit prematurely). Symmetrically, **closing cost is paid on *either* branch** — now if you close, later if you continue — so it **nearly cancels and MUST NOT be charged to the continue branch alone**, which would bias toward premature exit (the sunk-cost error in mirror image) `[→ R1b-4]`. Exit therefore scores **remaining carry against opportunity + risk, charging cost terms only where the branches *differ*:** `Q_p[ remaining funding + basis-from-here ] − opportunity-cost − Δ(closing cost: now vs later) − Δrisk` — the **same decision quantile + joint-aggregation discipline as entry, over the *remaining* `HoldPlan`**, and *not* the already-incurred entry-cost basket (realized entry costs live in lifetime PnL). In the common case where closing cost is branch-symmetric, the decision reduces to *remaining carry vs. opportunity + risk*. Stand down when that forward score stays below an **exit band materially more adverse than entry** for a **dwell of `exit_persist` settlements** (§5.2), the band's width from **measured regime-persistence** (the C3 discipline) so majors' brief negative dips don't whipsaw — two conforming implementations decide alike.
- **Leg quantization.** Target quantity MUST be quantized to the **intersection of both legs' venue lot sizes**, with an explicit residual-delta tolerance; leftover delta beyond tolerance is a sizing failure, not silently accepted `[→ X7]`.
- **Trading-filter conformance is a VERIFIED property of the order path, not only a derived one at sizing `[→ X7, M3 record §62]`.** The lot grid the previous bullet quantizes to is one member of the venue's published filter set — lot step, min quantity, **price tick**, **min notional** — and every planned leg MUST be verified against all four of its own venue's values at **three** points: at plan, before any intent is journaled; at execute preflight, before any authorization fsync; and at **every other path that dispatches a planned order**, of which [mechanism: State-Machines §7]'s `PackageDelever` ladder is the first — its two legs are sequenced across a finality wait and cannot go through the package preflight at all `[v0.9.58, task #184, record §77]`. The passes after the first are what catch a record **replayed** from a journal whose plan ran under an older filters revision or a pre-filters build. A failing leg refuses the **whole package** where there is one, naming the filter; the order path MUST NOT round or repair, because a repair would silently absorb a sizing↔venue grid disagreement and dispatch a quantity the caller's own records do not describe. The harm this duty exists to prevent is **asymmetric leg rejection**: each leg is judged by its own venue against its own grid (BTCUSDT lot steps differ by 100× between Binance's spot and perp, ticks by 10× — Profiles §5), so an off-grid package sent anyway is one leg filled and one refused — naked exposure, not an error message. The tick binds every order this system sends because §6 fixes marketable-IOC LIMIT as the only expressible pattern; min notional is judged at the leg's **own limit price** (the quantity the venue's filter reads for a limit order) with rounding **toward zero**, so the only disagreement rounding can open is refuse-what-the-venue-accepts, never the reverse. Filters resolve from the dated reference revision (§40d) under a declared **max row age**, judged TWICE: at boot, where a violation refuses the run naming the file, and again at **every admission** — filters move server-side without notice, and a long-running process's boot-fresh map stays green while the venue judges the current grid. **The grid and its date are ONE policy and MUST be enforced together**, because conforming to a row the venue may have moved past is a claim about the row and nothing else; a path that enforced half of it would be the same gap in a quieter form `[v0.9.58, task #184]`. **The admission INSTANT belongs to the enforcing path's own unit of legs — the set that must be refused together — and MUST NOT be pushed down to the single-order dispatch, which cannot know the unit `[v0.9.58, task #184, record §77]`:** the Executor's unit is the whole package, judged at ONE instant so a two-leg package cannot straddle the bound and refuse asymmetrically (§69), while §7's ladder's unit is the SINGLE leg, because the spot cap is the confirmed perp reduction and its two legs therefore have no shared instant to be stamped at. A per-leg clock read inside the package fan-out would re-open the asymmetry the one-instant rule closed. A row observed AFTER the admission instant refuses separately (a negative age would read as fresh; the fix is investigating the clock, not a wider bound). and an absent instrument, a tick-less row, a stale row, or no filters at all (the nil map) fail **closed**: a deployment that resolves no filters is one that plans nothing.

**Break-even worked example — the flagship's own kill-math `[→ R1-F4]`.** The tutorial kills strategy #2 with a cost table; cash-and-carry MUST face the same honesty. Round trip at VIP0 taker: spot `2×~0.10%` + perp `2×~0.05%` + `~4×0.02%` slippage ≈ **0.34–0.38%**. Against baseline funding `+0.01%/8h` (= 0.03%/day on notional): **~12–13 days just to break even**, ~4 weeks to clear the 4.6% T-bill hurdle scaled to the `1.33·N` leg-capital floor (the true denominator `C_allocated` is larger — rescue margin + reserves — so the real hurdle is *higher*, §2.2); at a rich `0.02%/8h` regime, still ~6 / ~9 days. Three consequences the spec draws explicitly rather than leaving implicit:
1. **Minimum holds are weeks — the same length-scale as the negative regimes** (the 46-day streak). Regime persistence is the *dominant* PnL driver, not a tail risk — which is why entry and exit ride the forecast + hysteresis band above, not a spot funding read.
2. **Utilization is part of the edge.** During stand-down the bankroll idles at ~0% on-exchange while the hurdle compounds elsewhere, so the viability headline (§2.1) MUST be quoted at expected **time-in-position** (e.g. a gross 8% carry at 60% utilization nets ~4.8% before ops risk), never at the in-position rate.
3. **Maker execution on the non-time-critical leg is a first-order lever** — routing the spot entry maker roughly halves round-trip cost and shortens break-even by ~40%, a bigger effect than most modeled refinements. It trades against the taker-IOC leg-risk mandate (§6.6), so it is a **documented, opt-in tactic** (maker spot entry + taker perp hedge + a fill-timeout fallback that reverts to taker), never the silent default.

**Authoritative-state principle (the highest-leverage rule).** There are **two authorities, and the spec names both `[→ R2-#5]`:** the **venue** is authoritative for *external reality* — what actually filled, live balances/positions, forced closes (ADL/liquidation), venue corrections — and the **`oms` write-ahead journal** is authoritative for *local intent, strategy allocation, and the reconciled view* that joins the two. Within the process, order/fill/trade/position state is owned by **exactly one** context, `oms`, as a durable single-writer state machine; it is continuously reconciled to venue truth (§7.5), and on conflict **venue reality wins for *what happened*** while the journal owns ***what we intended and how it is allocated***. Execution is its *mechanism*; monitoring and reconciliation are its *projections/process-managers*; audit is a *projection*. Nothing else writes that state `[→ X1, X3]`.

**Bounded contexts sit at `internal/<ctx>/`** — `internal/oms/`, `internal/risk/`, `internal/marketdata/` — as peers of the machinery groups `internal/{platform,engine,app}/`, with no grouping segment above them. First-class business capabilities are top-level; supporting machinery is grouped. The earlier `boundary/` segment is dropped: in DDD the term is *bounded context*, while "boundary" reads as the adapter **edge** — the opposite of what those directories hold (domain cores, with adapters nested inside). `contexts/` was rejected in turn for colliding cognitively with `context.Context`. The segment carried **zero enforcement value**: none of §3.6's gates key on it (rule 1 keys on `domain/`/`application/`, rule 3 on `infrastructure/`, rule 6 names `oms` directly).

**Context anatomy (every `internal/<ctx>/`):** `domain/` (aggregates, value objects, domain events — no infra/engine imports), `application/` (`ports/` = driven-port interfaces + use-case `Core` structs + a `<Ctx>Service` interface), `infrastructure/` (`driven/` outbound adapters + `driving/` inbound transport). Enforced rules in §3.6.

**Outbox delivery is ordered per `Key` — and deliberately not across two.** The export is at-least-once **and** per-key FIFO: records sharing a `Key` MUST be delivered in the order they were appended, and records under different `Key`s carry no ordering relationship whatever. Order is load-bearing rather than incidental — audit is a **projection of the OMS journal** (table above, §7.5/Z4), and a projection that applies a fill before the order that produced it does not reproduce its source — so a delivery-**count** guarantee on its own was relying, unstated, on a delivery-**order** one. The scope is the point: global FIFO is strictly stronger, unnecessary, and would let one poison record halt every consumer — the same structural rule §3.5 already states for dispatch ("an unready `SourceID` never stalls dispatch of ready inputs from other `SourceID`s"), and the agreement is deliberate. The cost is stated rather than hidden: **a record that fails forever blocks its own key forever**, which is the loud direction, where skipping past it would silently reorder a hash-chained projection.

**The dedup key is the sequence, and the exported payload is the committed bytes.** At-least-once means the relay publishes and *then* acks, so a crash in that window redelivers; closing the window would need a distributed transaction with every consumer, which is precisely the exactly-once mechanism D2 assigns to the **journal** instead. The consumer therefore needs a dedup key, and D2 says *idempotent* without ever saying idempotent **on what**. It is the record's **durable, store-assigned sequence**, unique by the store's construction — and a consumer MUST NOT dedup on payload content: two legitimately identical events (the same funding accrual on two successive intervals) are **distinct facts**, and content-hash dedup silently drops the second, which is a *missing funding receipt* in the tax records of §10 that nothing reports. The **`Payload` is the bytes that committed** alongside the journal write, retained and republished verbatim — never a Go object held and re-marshalled at delivery time. A map iteration order or a struct-tag change is enough to make the exported bytes differ from the committed ones, and because the audit projection is hash-chained (§7.5, Z4), that difference does not read as a serialization bug: it reads as **tampering**.

**The bootstrap phase order is a set of constraints, and two of them are normative.** §11's three binaries have genuinely different phase sets, so the roster above is not a closed five-item sequence — a sequence MAY carry additional service phases, and the constraints bind on the kinds named rather than on a fixed length. But two positions are load-bearing, and both fail *silently* when got wrong:
- **Signal disposition MUST be installed first.** A Go process's default disposition for SIGINT/SIGTERM is to **terminate**, so a phase installed after a slow join means an operator's interrupt *during* that join kills the process outright — no graceful shutdown, no flush, and no record that a shutdown was ever requested. The window where a boot is slowest is exactly the window where somebody interrupts it.
- **Observability MUST start before any phase that can fail.** Every later phase reports its failure through the machinery this one installs, so a sequence that starts it late does not merely lose telemetry: a boot that dies in the journal join dies with an **exit code as its only diagnosis**.

Configuration necessarily sits between them, and the direction is forced rather than chosen — the exporter endpoint, the log level and the sampling policy are configuration.

**The total graceful-shutdown budget is a safety number, bounded by §7.4's watchdog** — see §7.4, which owns the threshold.

### 3.3 Strategy interface (context inbound port)

```go
type Strategy interface {
    Name() string
    Universe() []VenueInstrument                    // canonical (venue,product,symbol,contract); spot & perp DISTINCT [→ Z1]; static for MVP — dynamic/dislocation-driven selection (strategy #2) is a later seam [→ R1]
    Evaluate(v MarketView) []Intent                 // MarketView is strategy-owned & immutable — NOT engine/state's type
    OnPosition(p PositionView, v MarketView) []Intent
    Params() StrategyParams                         // typed, validated, hot-reloadable
}

type Intent struct {
    IntentID   IntentID         // strategy-minted dedupe key — re-emitting the same signal is idempotent [→ R2-#8]
    Revision   uint64           // supersedes a prior IntentID's spec (e.g. re-sized on a fresh snapshot)
    ValidUntil time.Time        // engine Clock; a stale Intent is dropped, never executed late
    Kind       IntentKind       // OpenTrade | CloseTrade
    Legs       []LegSpec        // each leg names a VenueInstrument (spot vs perp on one symbol are distinct) [→ Z1]
    TargetQty  Quantity         // dimensional; identical across legs for exact neutrality, lot-quantized (§2.4)
    Reason     string           // for the audit log
}
```

`MarketView`/`PositionView` are immutable value types owned by `strategy` (or a domain-safe shared kernel); `engine/state` implements a read port and **translates** its cache into them, so `domain/application` never imports `engine/*` `[→ X5]`. The foundation owns `TradeID`/`ClientOrderID` generation, sizing caps, execution, and monitoring. A strategy that emits a two-leg Intent gets the same one-leg-failure handling as any other. **Duplicate suppression is layered:** the single deterministic command sequencer (§3.4) plus the exclusive per-hedge-group lease (§5.1) serialize commands so a second `OpenTrade` on a leased key is rejected — that, not the `IntentID`, is the primary race guard; `IntentID`/`Revision`/`ValidUntil` additionally make **strategy re-emission** (the same signal on successive snapshots) explicitly idempotent and let a stale Intent be dropped rather than executed late `[→ R2-#8]`.

### 3.4 Concurrency, dispatch & delivery lanes `[→ X4]`

A single trading process needs explicit delivery semantics or a slow consumer silently corrupts either latency or the audit log. Lanes are typed, not one undifferentiated bus:

- **Control lane (lossless, ordered, write-ahead).** Private order/execution/account/liquidation/ADL events and OMS commands. Never dropped; feeds the single-writer OMS in a documented total order (§3.5).
- **Market-data lane (bounded, latest-value).** Book/mark/funding updates in per-**`VenueInstrument`** mailboxes (spot and perp on the same symbol are distinct sources, §5.1) `[→ Z1]`; superseded updates MAY be **coalesced (latest wins) only after reconstruction** — **except the perp mark feeding liq-distance, which uses *adverse-preserving* coalescing: the worst adverse mark since the OMS last consumed it is never dropped, so a brief adverse excursion that breaches a threshold cannot be hidden by a later recovery** `[→ R2c-1]`. A raw snapshot+delta order book is **never** coalesced or drop-oldest'd on the wire — dropping a delta desyncs the book; raw deltas get **lossless application with sequence-gap detection and automatic resnapshot** in `marketdata`, and coalescing applies to the resulting *reconstructed immutable snapshot* (and to snapshot-style feeds like tickers). Bounded depth + defined overflow (drop-oldest + freshness gap counter) governs the post-reconstruction snapshot lane, never unbounded growth `[→ R2-#7]`. **The buffer holding deltas behind a gap is a DIFFERENT buffer with the opposite overflow policy, and it is bounded too.** §3.5 permits reconstruction to hold a delta pending resnapshot; that buffer is what makes resync *terminate*, so it is a correctness mechanism and not a latency one — a depth of zero holds nothing, the REST snapshot always lands behind the live stream, the very next delta gaps, and the loop re-requests forever while every metric reports a connected feed. It is therefore **bounded, keep-NEWEST, and the drop is counted**. Keep-newest rather than the snapshot lane's drop-oldest because the two buffers are asked opposite questions: the lane holds a latest-value view where the oldest entry is the stalest, while these deltas exist solely to bridge from a snapshot that has *not arrived yet* and will be **newer** than the buffer's head — so a retained prefix is destined to be stale on the drain, and drop-oldest evicts precisely the deltas that would have chained. The count is required for §3.5's reason: a reconstructor that quietly sheds held deltas presents a resync loop as a slow venue. **A reconstructed book MUST carry a venue sequence, and a zero one is refused rather than published.** `VenueSeq` is otherwise optional on an observation — a REST-polled funding read genuinely has none — but a book is the case that exemption does not reach, because the sequence *is* the position the next delta is placed against. A book admitted at position zero is not a wrong book: it validates, it is marked synced, and every subsequent delta is then unplaceable against it, so each is refused and each refusal requests a snapshot that re-establishes position zero. The failure presents as a connected feed, a valid book and a healthy transport, permanently.
- **Observability lane (isolated, lossy).** Metrics/logs/traces; back-pressure here never blocks trading.
- **Command sequencer.** Risk→OMS commands pass through one deterministic sequencer so live and replay apply them in the same order.

`engine/state` is single-writer (the marketdata reducer) handing immutable `MarketView`s to readers. Every published snapshot carries a **watermark**: source sequence, exchange timestamp, receive timestamp, and max cross-leg skew. **Cross-leg skew is measured over `RecvTime`, never over `SourceTime`.** §3.5 carries both timestamps "for freshness, cross-leg-skew metrics, and offline analysis" and names neither for this, but the choice is not free: a cash-and-carry package is spot on one venue and the perp on another, so a `SourceTime` skew across its legs **is** the unsynchronized-clock subtraction §3.5 forbids — and it fails quietly, because the number it yields is the two venues' clock *offset* rather than any property of the market, which against a sub-second limit is indistinguishable from a genuinely skewed package; the limit is then either permanently unreachable for a healthy pair or widened until it admits a real one. A `ServerNow`-corrected `SourceTime` skew is arithmetically available and is refused too: `ServerTime` carries an **uncertainty band**, and a measurement whose error bar is the size of the threshold it feeds is not a measurement. `RecvTime` is stamped by this process from the one clock both legs share (§3.6 rule 5), so the subtraction is exact, it needs no clock reading at all, and it is consistent with the ages beside it — **skew = |`Age(a)` − `Age(b)`| at any single instant**, since the instant cancels, so skew and freshness cannot contradict each other. The cost is stated rather than hidden: it measures when we *learned* rather than when the world *was*, absorbing the two venues' transport-latency asymmetry — which is the quantity a marketable IOC's two legs are actually exposed to. **Freshness is per-data-class**, not one 30 s threshold: order books used for execution need sub-second budgets + a cross-leg skew limit; **the perp mark used for liq-distance/rebalance has its own per-venue max-age budget, enforced by a `Clock` timer that fires on *silence* — a feed that simply stops emits no event, so staleness MUST be detected by a timer, not only by the next update** `[→ R2c-1]`; funding metadata tolerates longer. **One budget per (data class, venue), measured TWICE.** A feed dies two ways and one number governs both: *transport age* is measured from `RecvTime` against `Clock.Now()` — has anything arrived — and *data age* from `SourceTime` against `Clock.ServerNow(venue)` — is the venue's own view moving. A venue-side stall keeps updates arriving on schedule with a frozen `SourceTime`, so the transport measurement reads perfectly fresh for the entire outage. Both verdicts are **reported separately**, because the operator response differs, and **reduced by minimum** for any trade decision, which is §3.3's cross-leg rule applied within one leg. There is deliberately **no second budget** for the venue-side measurement: §3.4's stated reason for per-class budgets is the *data's* tolerance for staleness, which does not change with which clock measured it — a second number would buy a looser tolerance for a venue whose clock is known to lag, at the cost of a config field per venue and a second unreachable-rung validation. Measuring a venue's `SourceTime` against engine time is forbidden for §3.5's reason: it is the unsynchronized-clock comparison with one venue instead of two. **`engine/state`'s cached entries carry NO freshness verdict, and the re-judgement happens at the READ.** Both verdicts above are computed at *accept* time, and a latest-value cache is precisely where an observation sits and ages with nothing arriving to re-judge it — so an entry that stores what it was handed reports the feed fresh **for the entire outage, with every light green**. That is this section's own silence-timer failure one hop downstream, in the place the timer does not reach: the timer answers for a consumer who never asks again, read-time re-judgement answers for one who does, and both are required. The rule is **structural rather than procedural**, because the two are not equally safe when somebody forgets — a cached entry has no freshness field *to* read, so the stale verdict is unrepresentable rather than merely unused, and every age is derived from the stored watermark against an instant the **caller** supplies. Re-deriving the verdict inside the cache is refused for the same reason a second budget was: it makes a second freshness authority holding a second copy of §5.2's budgets. **A latest-value store REFUSES a write whose `RecvTime` precedes the held one, and ACCEPTS an equal one.** "Latest wins" is ambiguous in the direction that matters — read as *last to arrive wins*, an out-of-order write is exactly the last to arrive — and storing the older observation makes the cache report data **staler than it was a moment ago on a feed that just delivered**, while overwriting the newer reading that would have explained it. The per-`SourceID` mailboxes are FIFO so this should not arise, and "should not" is load-bearing: that invariant lives inside the dispatcher, and a consumer relying on an ordering guarantee it does not check fails silently the day that component ships with a different one. The equality half is not a detail — under a `TestClock` every observation dispatched between advances shares a `RecvTime` exactly, so a strict *not-after* check drops all but the first update at each instant **in the backtest only**, a §3.5 parity divergence no test of the live path can see. The comparison is on `RecvTime` and **not** on `VenueSeq`, which is authoritative only *within* a `SourceID`: a full snapshot replaces rather than follows, so a resnapshot recovering a desynced book legitimately carries a lower sequence, and a sequence check would reject the one write this cache most needs to accept. Shutdown drains the control lane before exit. Execution uses per-venue worker goroutines with rate-limit governors (§7.6).

### 3.5 Backtest-live parity (the from-scratch discipline) `[→ B1, D4, X8]`

Parity requires reproducing **input ordering**, not just timestamps. The engine depends only on these seams and one dispatcher:

```go
// platform/clock — live wall-clock vs. a deterministic TestClock the backtester advances.
// The live Wall clamps Now to be monotonic: a backwards system-clock step (NTP) is ABSORBED, never
// reported — right for the engine, where a timer firing late beats a settlement evaluated twice, and
// wrong for anything writing an ARCHIVE, where a clamped run of identical instants silently squashes
// the replay time axis with nothing failing. Wall therefore exposes the clamp as an OBSERVATION SEAM
// — Backsteps() reports (count, total absorbed) — and an archival consumer MUST record an engaged
// clamp as data (the capture lane below writes a clock-step record). It MUST NOT be given a second,
// unclamped time authority instead: a tool whose job is to detect a clock defect must not hold two
// clocks and privately arbitrate them.
type Clock interface {
    Now() time.Time                       // engine time; per-venue server offset/uncertainty modeled separately
    ServerNow(Venue) ServerTime           // authoritative for funding-boundary decisions, with uncertainty band
    SetTimer(id TimerID, at time.Time, prio uint8)  // cancel/replace by id; ordered by (at, prio, id) — LOWER prio is MORE urgent
    CancelTimer(id TimerID)
}

// Timer CONSUMPTION is pull-based, on an interface separate from Clock: only the dispatcher pumps it,
// while every domain component holds a Clock. A Clock pushing due timers on its own goroutine would
// force the dispatcher to re-queue what it was handed, putting the arbitration that decides the replay
// key in two places. Fired.At is the SCHEDULED instant, not the delivery instant — identical in replay.
type TimerSource interface { NextDue() (Fired, bool); Pending() int }

// The dispatcher assigns every DISPATCHED envelope a monotonic IngressSeq (a.k.a. DispatchSeq) — that
// consumed order, not the timestamps, is the replay key. VenueSeq is local to a SourceID and can collide across symbols.
type SourceID struct { Instrument VenueInstrument; Stream StreamKind } // a VenueInstrument stream — COMPOSED, not restated (below); NOT globally ordered [→ Z1]
type Envelope struct {
    AcceptOrdinal uint64     // a.k.a. RawIngressSeq — stamped in raw arrival order at ingestion on EVERY raw input; the causal/audit order (capture lane), NOT necessarily the dispatch order. Present from ingestion onward, so a PRE-dispatch envelope on a §3.4 mailbox already carries it — a producer INHERITS it, never mints one. Zero means timer-triggered (below) [→ Codex, R2b-11, R2c-6]
    IngressSeq uint64        // a.k.a. DispatchSeq, the REPLAY KEY — dense monotonic order the DISPATCHED envelope is released to the state machine; derived from arrival, NOT a SourceTime reorder, NOT forced to equal global AcceptOrdinal order (held/coalesced inputs). Assigned ONLY at dispatch: zero on every pre-dispatch envelope, and a producer that minted one would be a second authority over the replay key [→ Y4, R2b-11, R2c-6]
    Source     SourceID
    SourceTime, RecvTime time.Time  // venue/local timestamps — freshness (BOTH, §3.4), cross-leg skew (RecvTime ONLY, §3.4 — a SourceTime skew across two venues is the unsynchronized subtraction below), analysis; NOT a live reorder key [→ R2b-11]
    VenueSeq   uint64        // per-SourceID only; authoritative ordering WITHIN a SourceID
    Prio       uint8
    Payload    any
}

// engine/venue — the data & execution seams (live adapter vs. replay / fill-model adapter).
type MarketDataSource interface { StreamBook(VenueInstrument) <-chan Envelope; StreamFunding(VenueInstrument) <-chan Envelope; StreamMark(VenueInstrument) <-chan Envelope } // see §4 — the per-stream shape is AUTHORITATIVE and the per-stream product constraints are §4's (funding/mark perp-only). ONE channel per (instrument, stream) = one SourceID = one §3.4 mailbox; this replaced a flat Subscribe(VenueInstrument) that merged three streams onto one channel (below) [→ Z1]
type ExecutionVenue interface { OrderGateway; AccountSource; MarginGateway; ProtectionGateway } // see §4 — the safety-path capabilities (margin top-up, protection quiesce) are IN the parity seam so the SAME OMS/monitor/safety code runs live + backtest/chaos; fence/plan behaviour gets test adapters [→ R2c-3, Codex]
```

**`SourceID` composes `VenueInstrument`; it does not restate its fields.** The identity is `(instrument, stream)`, where the instrument is §5.1's canonical `(venue, product, symbol, contract type)`. The earlier flat form had no way to express the **`ContractType`** §5.1 gives an instrument, so a source could not name an inverse contract at all; and duplicating the fields duplicates their validation, which is how two definitions of "a valid instrument" come to disagree. Since `SourceID` keys the §3.4 mailboxes, one spelling of an instrument is one mailbox — which is the other half of §5.1's "exactly one spelling" requirement, enforced here structurally rather than by convention.

**Not every `(instrument, stream)` pair names a source a venue can produce, and a `SourceID` MUST refuse the ones that do not.** §4 states the constraint per stream and this is where it binds, because this is the type that holds both fields: **`StreamFunding` and `StreamMark` are perpetual-only** (spot has neither — price the spot leg from its own book, §4.2), **`StreamBook` exists for both product families**, and **the private streams (`StreamOrders`, `StreamExecutions`, `StreamAccount`) and `StreamControl` are NOT product-constrained** — §4.2 makes spot a full API family with its own user-data stream, so constraining them would silently unsubscribe half of a cash-and-carry trade. That last row is stated rather than left to inference precisely because the constraint reads like a market-data property and is not one. A stream whose product family this spec has **not** classified is treated as perpetual-only: the direction denies an unclassified source rather than admitting it, matching §5.2's hot-reload and §10's label-cardinality defaults. The check belongs at the identity rather than at each consumer because §3.4 makes `SourceID` the **mailbox key**: an impossible source is a mailbox that exists, can be subscribed to, and never delivers — a spot funding subscription and a venue that has gone silent look identical to every consumer downstream, and §3.4's silence timer will faithfully report the second.

**The market-data seam is `MarketDataSource`, and §4's per-stream shape is authoritative.** It was declared twice — here as a flat `DataSource{ Subscribe(VenueInstrument) <-chan Envelope }` and in §4 as three per-stream methods — for the same position in the pipeline: both are what the dispatcher reads and what §8's backtest substitutes a replay adapter for, and a type satisfying one does not satisfy the other. §4 wins on three grounds, and the resolution is a **rename plus a deletion, not a new requirement**. One: a `SourceID` is `(instrument, stream)` and §3.4 gives each its own mailbox, so one channel per instrument merges three of them and forces the subscriber to demultiplex on `Envelope.Source` — re-deriving a key the seam could have kept. Two: the per-stream product constraints above are **inexpressible** in `Subscribe(VenueInstrument)`, so a spot subscription silently yields a third of the streams with nothing naming which third. Three: §7.6 makes venue capacity a budgeted resource with a priority ladder, and a consumer that needs only funding would have to open the high-rate book feed to get it, spending that budget on nothing. The rest of this seam block is already written as a reference to §4 — `ExecutionVenue` is a composition of §4's four interfaces and says so inline — and `DataSource` was the one line written as an independent definition, which is why its signature is the one that fell behind.

**Timer ordering is `(At, Prio, ID)`, and the priority direction is normative: lower `Prio` is MORE urgent, so the zero value is the most urgent.** Chosen rather than inherited — under the opposite convention an unset priority sends a safety timer to the back of the queue, and noisy-but-early beats quiet-but-late. The `ID` tie-break makes the order **total**, which is what lets a replay reproduce a drain sequence exactly. **Waking a live consumer is deliberately not part of `Clock` or `TimerSource`:** it belongs to the dispatcher's select loop, alongside the persisted `DispatchSeq` (below), and is not yet built.

**An envelope's `Prio` is a per-`SourceID` constant and MUST NOT depend on the content of what is published.** The direction is the same as a timer's — lower is more urgent, zero most urgent of all — but the constancy is a separate requirement and a safety one that reads backwards. §3.4's mailboxes are per-`SourceID` and `VenueSeq` is authoritative *within* one, so two envelopes from one source published at different priorities are two envelopes that can be drained out of sequence. The tempting implementation escalates on a *worse* reading — a `FreshnessBlind` snapshot looks like safety traffic because it is what fires §5.2's `mark_blind_action` — and the consequence is that the blind reading overtakes the stale one it followed inside the mailbox they share, so **a consumer watching a degrading feed sees it recover**. Which constant a source takes is a policy choice; that it takes one is not. A source MUST also not default to the zero value, for the same reason the priority direction is normative: an unclassified envelope treated as most urgent puts market data ahead of the safety kernel in a drain because nobody chose.

Live wiring injects real WS/REST clients and a wall-clock `Clock`; backtest injects a replay `MarketDataSource` (Tardis + self-captured streams), a `TestClock`, a fill-model `ExecutionVenue`, and **replayed config/reference-data revisions + deterministic seeds**. Strategy, risk, sizing, OMS, and monitor code are identical across both. **The state machine's total order — the one it consumes *and* replays — is the *dispatch* order (`DispatchSeq`/`IngressSeq`), not raw arrival `[→ R2c-6]`.** Every accepted input is stamped an `AcceptOrdinal` in **raw arrival order at ingestion** (the causal/audit order — a.k.a. `RawIngressSeq`), and `IngressSeq` — the dense, tie-free **replay key** (a.k.a. `DispatchSeq`) — is assigned to the **dispatched** envelope **in the order the state machine actually consumes it**, which is *derived from* arrival but **NOT forced to equal global `AcceptOrdinal` order** `[→ Y4, R2b-11, R2c-6]`. The two genuinely differ: reconstruction may **hold** a book delta behind a sequence gap (pending resnapshot) while a later-arriving input from an *independent* source is dispatchable, and coalescing means some raw inputs produce **no** dispatched envelope at all — so forcing the dispatched stream to strict global raw order would either **head-of-line-block independent sources** or require skipping ordinals. Instead: **an unready `SourceID` never stalls dispatch of ready inputs from other `SourceID`s** (they carry no cross-stream ordering), a held source's reconstructed snapshot takes its `IngressSeq` **when reconstruction completes**, and the `RawIngressSeq → DispatchSeq` mapping is **explicit and persisted**. Replay re-applies the persisted `IngressSeq` (the consumed order), **not** `AcceptOrdinal` — determinism keys on **what the state machine actually consumed**, still with **no `SourceTime` reorder**. Raw arrival order (`AcceptOrdinal`) is causally honest — you reacted to what you received, in the order you received it — and is the **capture/audit** authority; it is **not** the replay authority (the persisted `DispatchSeq` log is, below). **Cross-venue `SourceTime` is *not* a sound live reorder key:** the two venues stamp with unsynchronized clocks, so sorting a merged stream by `SourceTime` can *manufacture* an incorrect order, and no clock-uncertainty proof justifies it; `SourceTime`/`RecvTime` are carried for **freshness, cross-leg-skew metrics, and offline analysis only**, never to override the persisted acceptance order. **Within a `SourceID`, `VenueSeq` stays authoritative** (deltas apply in `VenueSeq` order with gap-detection + resnapshot, §3.4); across `SourceID`s a latest-value cache needs no cross-stream temporal merge, so the MVP builds none. A **bounded, explicitly clock-uncertainty-justified cross-venue reorder is a documented later seam** — it matters only for cross-venue strategy #2 (comparing two venues' books) and is **out of MVP scope**. Replay re-applies the **persisted `DispatchSeq`/`IngressSeq` log** exactly — **parity is defined as replaying that persisted dispatch log, not regenerating dispatch order from raw capture**: live dispatch resolves any concurrent reconstruction-ready timing (multiple sources becoming dispatchable at once) and **freezes that arbitration in the log**, so replay is deterministic without re-deriving order from `AcceptOrdinal`; parity therefore does **not** depend on cross-venue clock synchronization `[→ R2b-11, R2-#6, R2c-6]`. **The persisted order lives in a durable capture lane** — the self-captured market-data streams (§8) plus the dispatched-sequence log, **separate from the OMS control-lane journal** (which persists order/account truth). That lane is **append-only with per-`(Source, Topic)` sequence numbers — per capture *stream*, not per `SourceID`**: the lane stores wire bytes, one `SourceID` has more than one wire representation (the same book as a partial-depth stream and as a diff evidence stream; one topic's cadence edited in config six weeks in), and a per-`Source` counter spanning two wire feeds has **no hole when one of them stops**. The finer key preserves every hole the coarser spelling would have shown, so the drop discipline below is unchanged; under load it is **bounded, and any drop is a recorded capture gap — never a silent reorder** — marking the affected `IngressSeq` window non-replayable and alerting, so losslessness is *checked* by the same sequence-gap discipline used on the wire, never assumed `[→ R1b-6c]`. **Market-data coalescing is a deterministic rule** keyed on `(Source, field)` — never a function of goroutine scheduling — applied **only to reconstructed snapshots** (§3.4), and both the pre- and post-coalescing dispatched sequences are persisted for replay. `AcceptOrdinal` originates at **raw ingestion** on every input (including each raw delta); the **dispatched** envelope — a reconstructed snapshot for book streams — carries the `AcceptOrdinal` of the delta that triggered it (causal traceability), while `IngressSeq` is assigned to that dispatched envelope in **consumption order** — so each dispatched envelope is traceable to its triggering raw `AcceptOrdinal`, yet the **replay authority is the consumed `IngressSeq`**, not global arrival order. **The inheritance rule is scoped to envelopes derived from a raw input, and it binds every producer, not only book reconstruction** — the reconstructed snapshot is an *example* of the rule, not its extent; a producer publishing zero where an ordinal exists breaks the trace silently, since nothing downstream can tell a lost ordinal from an absent one. **The one envelope derived from the ABSENCE of an input carries no ordinal, and `AcceptOrdinal == 0` is how it says so:** §3.4's silence timer publishes a re-judged verdict on an observation nothing has superseded, so there is no raw input to inherit from. Reusing the last input's ordinal is **forbidden** — it makes the capture log claim one raw input produced two dispatched envelopes, so a replay reconciling dispatched envelopes against raw inputs reports a phantom duplicate and finds nothing wrong with the feed, which inverts the meaning of the one event that fired to say a feed had gone quiet. Because zero is meaningful, a producer MUST refuse a zero ordinal on an input-derived envelope rather than pass it through: the value has exactly one reading, and an omission wearing the same clothes would destroy it. **`Envelope.Validate()` is therefore the DISPATCHER's post-stamp check, not a producer-side one** — it requires `IngressSeq`, which a pre-dispatch envelope cannot satisfy, and a producer that called it before publishing would have to mint one to pass. It does **not** judge `AcceptOrdinal`: zero is the absence-derived envelope's one legal reading and the check cannot see derivation, so a clause refusing zero here would refuse the exact envelope §3.4's silence timer is required to publish — the refusal of zero on an *input-derived* envelope is the producer obligation above, enforced where derivation is visible, and a check stated over "both sequence fields" was a true rule stated without its scope *(narrowed v0.9.16, when the sim wiring first drove an absence-derived envelope through the dispatcher)*. **REST calls run outside the state-transition dispatcher** and re-enter as fresh envelopes with their own `IngressSeq`. The guarantee is **shared code + invariant parity under this single ingress order** — not "byte-identical," which is false the moment two inputs share a timestamp `[→ Y4]`.

### 3.6 Structural rules (enforced, not aspirational)

Each is checked by a boundary/lint test in CI.

**A rule identified BY POSITION reads a Go external test package as the package it tests**. Rules 1, 6, 9 and 10 scope themselves by import path, and an external test package is the one Go construct where a package's import path and its directory **disagree**: `package oms_test` in a file under `internal/oms/` compiles as `internal/oms_test` — outside `internal/oms/` by path, inside it by directory — so a rule phrased as "packages outside `X`" does not decide the case on its own. It is decided here, once, because the consequences differ per rule and deriving them separately is what produced two gates answering it independently: `hexboundary` classifies `marketdata/domain_test` as `domain/` and **polices** it, while `singlewriter` reads `internal/oms_test` as `internal/oms` and **exempts** it. Both follow from the one sentence; neither is a special case. The cost of leaving it unstated is measured rather than hypothetical — `singlewriter` shipped without the normalisation and reported `oms`'s own `module_test.go` as a second writer to order state, because a test double for a port has to name that port's types in its method signatures. Note the shape that hides it: an external test package of a **subpackage** (`oms/application_test`) still sits below the exempt path and is covered by a prefix comparison for free, so only the **owner** package's own external test exercises the rule — which is why a fixture set can look complete and miss it.

The rules:
1. **Hexagonal boundary.** `domain/` and `application/` MUST NOT import `infrastructure/` or `engine/`. Strategy inputs are domain-safe value types, not `engine/state` types (rule enforces §3.3) `[→ X5]`.
2. **Ports in `application/ports/`.** Every driven dependency is an interface there; adapters live in `infrastructure/driven/` with a compile-time `var _ ports.X = (*Impl)(nil)`.
3. **Infrastructure shape.** `infrastructure/` contains **only** `driven/` and `driving/` — a **permitted-children** rule, not a required-children one. The rule's purpose is to stop `infrastructure/` growing a third category (a `persistence/`, a `shared/`) where the adapter *direction* stops being visible in the path; it is not a requirement that a context with adapters in one direction create an empty package in the other. `oms` is the case that decides it: its inbound adapters are §6's private order and execution streams, which are a later slice, and an empty `driving/` to satisfy a literal "exactly" would be the same mistake as a lint over an empty tree — a shape that looks compliant while asserting nothing. **One documented exception since `[v0.9.49, task #179, record §70i]`: `oms/infrastructure/baseline`**, the spot-baseline document package, sits BESIDE `driven/` as a third child, and the position is load-bearing rather than drift: rule 6 polices `oms/application/ports` and `oms/infrastructure/driven` **by position, `app/` roots included**, and the composition roots must construct §5.2's `spot_baseline` pin and name its dialect — housed under `driven/`, every root building that value would acquire the whole write-adapter surface with the import, which is precisely the shape rule 6 exists to make undeclarable. What this rule protects — the adapter direction staying visible in the path — the package keeps by holding no port implementation rule 6 polices; what the rule forbids — a category where direction blurs — is bounded by the exception naming ONE package, never a kind.
4. **Money is dimensional `fixedpoint`.** No `float64` in any money path (`nofloat` AST lint — **type-based, not textual**: the rule is "no value here is a float", which needs type information, so it also catches an untyped constant becoming `float64` on assignment and a float handed over by the standard library). The check is **default-deny anywhere under `internal/`**, with a per-line `//nofloat:allow <reason>` escape for genuine wire seams (Prometheus takes `float64`); the reason is mandatory and an escape with nothing to suppress is itself reported. The **categories `Money`/`Quantity`/`Price`/`Rate` are distinct compile-time types** (cross-category ops do not compile); the **asset/currency tag is a runtime-checked field** — dynamic venue assets can't be phantom-typed, so same-category unit mismatches are caught by `Validate()`, not the compiler `[→ R2-#10]`. Arithmetic uses 128-bit/`big.Int` intermediates, canonical scale, and an explicit rounding mode per operation; a SQL codec (not raw floats) persists them `[→ X7]`. **Error precedence is a stated contract:** invalid mode → divide-by-zero → **overflow** → precision loss. When a result is both out of range and inexact, **overflow wins** — a value that cannot be held at all is more fundamental than one that cannot be held exactly, and reporting precision loss would send a caller to their rounding policy when the number is orders of magnitude too big.
5. **Time is injected.** No ambient clock reads in `domain/`, `application/` **or `engine/`**; funding-boundary logic uses `Clock.ServerNow(venue)` with its uncertainty band `[→ X8]`. The ban is the **whole ambient-time family**, not literally `time.Now()`: `Now`/`Since`/`Until` and the scheduling calls `Sleep`/`After`/`Tick`/`NewTimer`/`NewTicker`/`AfterFunc`, which §3.5 assigns to `Clock.SetTimer` so the backtester can drive them. Methods on an instant the caller already holds (`t1.After(t2)`) are not ambient and stay legal. **`engine/` is in scope because `platform/clock`'s monotonic clamp is only a guarantee if everyone reads the same clock:** `Wall` absorbs backwards time and `time.Now` does not, so an adapter stamping `RecvTime` from the raw clock while freshness is computed from the injected one puts two disagreeing clocks either side of a subtraction — yielding a negative or inflated age exactly across the NTP step backwards the clamp exists for, in code where freshness gates execution (§3.4) and stale marks drive liq-distance `[→ R2c-1]`. `engine/` alone MAY annotate a per-line exception with `//notimenow:allow <reason>` for **live-only transport** (a socket read deadline carries no venue-server-time meaning, never runs under replay, and must fire when the dispatcher is wedged); `domain/`/`application/` admit none, and the directive written there suppresses nothing and is reported.
6. **Single-writer authority.** Only `oms` mutates order/fill/trade/position state, through the journal-then-apply path (§6). A lint (`singlewriter`) forbids **every package outside `internal/oms/`** from importing the OMS write path, identified **by position rather than by naming a type**: `oms/application/ports` **and** `oms/infrastructure/driven`. Three scope decisions, each with a failure direction: **the port is policed as well as the adapter**, because depending on the abstraction is the *recommended* way to depend on anything — a gate covering only the concrete repository would forbid the shape nobody writes and permit the shape everybody does, leaving a context holding `OrderWriteRepository` with full write authority and a clean run. **The composition roots under `app/` are policed too**, although rule 7 has the binary wire modules by hand: each context constructs its own adapters in its `module.go`, so a root never needs to *name* one, and a root that may hold a repository may pass it to another context — which needs no import at all to accept it, since Go's interfaces are structural. **`oms/domain` is deliberately NOT policed**, because §5.1 makes `audit` and `reconcile` "projections over the journal, never co-owners", and denying a read model the order-state enum would force it to declare a second copy of SM §1's state set — worse than the import. Position rather than a marker for the standing reason about defaults: an opt-in `//arblab:writerepository` tag leaves the repository somebody adds next year silently unpoliced, while a package tree covers it the day it is declared. The gate reads **declared import edges**, so it makes a second writer impossible to declare *by accident* and not impossible to construct *by determination* `[→ X1]`.
7. **Explicit wiring.** Each context has a `module.go`; the binary wires modules by hand. **No DI container.**
8. **Typed value objects.** Enum-likes are `type X string` + constants + `Validate()`. **Documented exception — `fixedpoint.RoundingMode` is `uint8` + `iota`.** The `type X string` shape exists for enums crossing a **persistence or wire** boundary, where a self-describing stored token is worth the width. A rounding mode is an *argument* — never persisted, never transmitted — so the property that matters is the opposite one: that the **zero value be an unusable sentinel** (`RoundInvalid = 0`), which only an integer enum gives for free. An enum-like that does cross either boundary follows the rule. **Second documented exception — `capture.RecordKind` is `uint8`**, and it crosses a persistence boundary (it is a byte in every archive frame), so it is an exception *to* the letter above, not outside it. Two grounds, argued in the capture design (§32e's format): the archive frame is a **fixed-width header** in the one part of the format that must stay decodable from a corrupt file, so a variable-length token would put a second length in front of every payload's; and the self-description this rule buys is already delivered one level down by the format's own tooling — "the archive is the fact; readability is a tool over it", and `arblab capture cat` is where a kind becomes a name, so spending eight bytes per record to duplicate what a tool prints is width bought for nothing. What the integer keeps is this rule's *other* half: `RecordKindUnspecified = 0` is refused, so a zero-filled region — a sparse hole, a page allocated before a crash — cannot decode as a valid record.
9. **Kernel purity.** A package under `platform/` may import only the standard library and other `platform/` packages (`kernelpurity` lint). Two failure modes, one rule: a kernel importing a bounded context turns a technical shared library into a shared **domain** kernel — DDD's most tightly coupled integration pattern — and `platform → engine` inverts the spine `engine/` already sits on, inviting a cycle. **Scope is in-module imports only:** third-party is deliberately out, because `platform/observability` legitimately needs `prometheus/client_golang` (§11).
10. **Exhaustive switches over enum-likes** *(enforced — `exhaustiveswitch`)*. A `switch` over a rule-8 enum-like MUST cover every declared constant or fail the build, so adding a state to a safety machine breaks compilation at every decision site instead of falling through to `default`. This is the compensating measure for the one place Go is genuinely weaker than a language with sum types, and it matters here because the safety kernel is seven state machines (SM §1–§7) whose formal model has already yielded four counterexample-backed defects `[→ FM-1…FM-4]`. **A `default:` does not excuse a missing member** — that is exactly where a new member lands silently — and there is **no escape directive**: the way to say "the rest are handled alike" is a grouped `case`, which names them and which the compiler then rechecks when one is added. `golangci-lint`'s `exhaustive` was evaluated first, as this rule required, and did not suffice; the evaluation is recorded and **closed**. **This rule's deferral named the wrong trigger, and that is worth keeping:** it waited on a *state machine*, while what actually made it buildable was the kernel's eleven enum-likes, which had existed for several slices — it found **13 silent fallthroughs** on its first real run, all of them reachable the whole time. A deferral should name the construct the lint reads, not the feature that motivated it.

**Gate status. All six are enforced** — rules 1 (`hexboundary`), 4 (`nofloat`), 5 (`notimenow`), 6 (`singlewriter`), 9 (`kernelpurity`), 10 (`exhaustiveswitch`) — each a `golang.org/x/tools/go/analysis` analyzer with `analysistest` fixtures that MUST produce diagnostics, so every gate is *shown* to bite rather than assumed to. **Rule 6 was the last deferral and it expired on schedule** (2026-07-27, mid-sixth-slice; the doc-set version bumps at that slice's close): it waited on "`oms`'s write repository exists", because a lint over an empty tree passes trivially and that is indistinguishable from a broken lint — the repository landed, and the gate landed in the **same session**, as rules 1 and 10 did rather than after the code they police. **Its trigger named the construct the analyzer reads**, which is the property rule 10's deferral lacked (that one waited on a *state machine* while what it actually read was the kernel's eleven enum-likes, and it found 13 silent fallthroughs that had been reachable for several slices); §12's milestone roster named the same trigger, so nothing had to be re-derived to know when the gate was due.

**A clean gate run is not evidence, and rule 1's positive control is the case that proves it.** The obvious probe — `application/` importing `infrastructure/` — is an **import cycle**, so the type-checker refuses before the analyzer runs, and the gate scores a pass without executing. Every `infrastructure/` package in a context imports its own `application` or `domain`, so *within* one context Go's no-cycles rule already covers most of rule 1; where the rule earns its place is the edge Go cannot see — `engine/`, and another context's `infrastructure/`. The probe that works is a package under `infrastructure/` importing **only** `domain`, imported from `application/`. Any future gate's bite-check must find a fixture the compiler will actually admit.

**Rule 6's control adds the other half of that lesson: a gate must be shown to bite where NO OTHER gate would.** The obvious probe — `marketdata/application` importing `oms/infrastructure/driven` — fires `singlewriter` and `hexboundary` together, so it demonstrates that *something* objected, not that this rule did. The probe that isolates it is a **context root** (`internal/marketdata`, package `marketdata`) importing `oms/application/ports`: rule 1 is silent there because the importer is not an inward layer, and rule 6 reports it alone. That is also the realistic accident — a context reaching for order state to *read* it — so the isolating fixture and the motivating case are the same one.

**Custom analyzers rather than linter configuration** is deliberate: `depguard` cannot be unit-tested, so it cannot be shown to bite; `forbidigo` would need inverted path-exclusion logic that silently stops covering any context added after it was written; and rule 4 cannot be expressed as configuration at all, since it needs type information.

### 3.7 Service-split seam (documented, not built) `[→ D1, A2]`

If a context ever needs its own process: introduce an `internal/platform/<ctx>sdk` courier (interface + wire DTOs + NATS request-reply), swap the in-process port for the sdk client at the composition root, and route that context's domain events through `platform/outbox` → NATS JetStream. Nothing in `domain/`/`application/` changes. The MVP builds none of this; today's ports stay split-ready (narrow, one concern, DTOs free of `engine/*` types).

## 4. Venue contract (the N-venue seam) `[→ A1, X1, X2]`

`engine/venue` owns raw Binance/Bybit clients and normalized DTOs; contexts consume **segregated capability interfaces** declared in their own `application/ports/` and satisfied by thin ACL adapters. Every per-instrument method keys on the canonical **`VenueInstrument{Venue, ProductCategory, Symbol, ContractType}`** — spot `BTCUSDT` and perp `BTCUSDT` are *different* instruments with independent order/execution-ID namespaces and separate REST endpoints; **the signatures below key on `VenueInstrument`** (not the display-only `VenueSymbol`), and recovery (`Fills`) is always product+symbol-scoped `[→ Z1, R1]`.

**`Place` takes the §7.6 shed class as an ARGUMENT, because nothing it could read carries it `[→ M3 slice C2a]`.** The venue call needs a priority to acquire rate-limit budget under, and the class of an order is a property of the §5.3 **command** that produced it — `OpenTrade` creates exposure, `ExposureReduction`/`PackageDelever`/`EmergencyClosePackage` remove it (the mapping is in §5.3). **Neither the `Order` aggregate nor its projection holds which command that was**, so the adapter — the one layer that must state the class — is the one layer with no way to derive it, and the argument is what closes that gap. **Defaulting is not available, and the two defaults are not symmetric:** `Opening` puts the order under the ~70% back-off ceiling, so a **flatten** silently defaulted to `Opening` is shed during exactly the incident the reserve exists for; `Safety` puts it at capacity, so ordinary trading spends the reserve and needs a second coincidence before it costs anything. A silent default would be the first kind, which is why there is none. The class an adapter accepts is narrowed to the two an *order* can carry — §7.6's `Routine` is read traffic, under no §5.3 command, and it maps to **neither** ceiling, so admitting it would force the adapter to round a value no caller could correctly have chosen. **The better long-term shape is recorded and deliberately not taken here:** a field on the `Order` aggregate naming its originating command would also decide §5.3's `stop-opening` exemption, which likewise has no carrier — one missing carrier serving two rules — and it is a §5.1 aggregate change reaching the journal codec, the planner and recovery. A later slice reopens it deliberately.

**`Cursor` is a venue SERVER INSTANT, not a venue resume handle, and the obvious reading satisfies this signature completely while making §6.7 inexpressible `[→ M3 slice C2b, Profiles §8]`.** The three execution surfaces hand back three resume handles — an ascending trade id on both Binance families, an opaque **descending** page cursor on Bybit — and **none of them can be compared to a time**. §6.7 step 3 requires sweeping *"through a venue/server watermark strictly later than the order's cancellation-effectiveness / max landing horizon"*, which is a comparison against a horizon, so a `Cursor` defined as "whatever the venue returns" implements this interface correctly on all three surfaces and leaves the one clause that consumes it unable to be written. The venues corroborate the same conclusion from the other side: on **both** Binance families `fromId` and the time window are **mutually exclusive** (futures states it, spot's supported-combination whitelist contains no such pair), so a sweep bounded by a watermark cannot also resume by id. **The venue's own handle is therefore demoted to within-sweep paging and MUST NOT be persisted as the resume point** — it is a different quantity travelling in the same shape, and on a descending venue it points the other way: a `nextPageCursor` stored as the next `since` resumes at the **oldest** row of the previous sweep and re-reads that window forever **while every request succeeds and dedup absorbs the duplicates**. Two further requirements follow, both §6.7's rather than conveniences. **The sweep takes the HORIZON as well as the resume point**: every surface returns data with the time parameters omitted and thereby proves coverage *through* nothing, so a defaulted window is not a substitute for asking, and a page MUST report the watermark it **proved** — the window's horizon when the window was exhausted (**including an empty page**, since "nothing happened through T" is a positive answer and the commonest one), and no further than its own last row when it was not. **A window wider than the surface will serve is REFUSED, never truncated**, because a truncated sweep reporting success is a false watermark and a false watermark is what §6.7 collapses a possible-delta interval on — and the caps are **not** uniform: 7 days on Binance USDⓈ-M and Bybit, **24 hours on Binance spot** (Profiles §8). Where a venue's execution timestamp is **not unique** (Bybit states this) the watermark **rewinds to the start of the tied instant** rather than advancing past it: §5.1's dedup key makes a re-read cost one row check and a gap cost an execution the net-delta invariant is computed without, so the tie resolves toward re-reading.

**`OrderByClientID` returns an ABSENCE as a value; only an unanswered query is an error `[→ M3 slice C2b, Profiles §8]`.** The two venues put "no such order" in opposite layers — Binance in an **error envelope** (`-2013 NO_SUCH_ORDER`), Bybit in a **success** body with an empty list — and Binance's is a true statement about the *query* (it was refused, nothing happened) and a category error about the *order*. Propagated as an error it is indistinguishable at the call site from a query that was rate-limited or timed out, which is the inference §5.3 forbids in terms. The status a venue returns MUST therefore carry a **presence** distinct from the error path, and — because retention differs per surface (§5.3, Profiles §8) — the **surface that answered and how far back it can see**, since an absence from a surface that cannot see far enough is not evidence of anything. A venue with more than one order surface (Bybit's realtime → history, §5.3) reports the surface that **answered**, which for an absence is the last one tried.

**`Ack.VenueOrderID` — the earlier claim that "nothing in this system requires the venue's id" is WITHDRAWN, and it was generalized from the one venue where it holds `[→ M3 slice C2b, Profiles §8]`.** Bybit's `GET /v5/execution/list` returns `orderLinkId` on every row, so a fill there is attributable by our own handle. **Binance's trade lists return neither a `clientOrderId` nor an `origClientOrderId`** — not on `/fapi/v1/userTrades` and not on `/api/v3/myTrades` — so on Binance the venue's `orderId` is the **only** join key between a swept execution and one of our orders. The composition still closes, and only by a second venue fact: Binance retains an order **with fills** for 90 days, so `OrderByClientID` can recover the `orderId` for any fill worth attributing. **That makes `Fills` and `OrderByClientID` a composition where the signatures above suggest independence**, and it makes the sweep useless alone in exactly the scenario it exists for — a lost ack, which is when §6.7 runs and when no `orderId` was ever read. The field's own status is unchanged (a venue that returns none leaves it empty); what is withdrawn is the reassurance. This is the mirror of the *hazard-named-for-one-input* shape in the **reassuring** direction, which is worse, because a hazard note at least announces that something needs checking.

**`OrderGateway` is the VENUE-facing capability set; the recovery path's consumer port MUST be narrowed to the two READ methods `[→ M3 slice D]`.** §5.3 says an order at `DispatchAuthorized` or beyond is resolved *"only by `OrderByClientID`/`Fills` — **never resubmitted**"*. Handing the resolution use case this whole interface leaves `Place` one line away from the code whose entire subject is not calling it, so the rule survives only as long as every future reader remembers it. Narrowed — the resolver holds a port carrying `OrderByClientID` and the executions sweep and **nothing else** — "never resubmit" stops being a rule to remember and becomes a method that **does not exist**, and the §5.3 clause is inexpressible rather than merely forbidden. This binds the **consumer's** port, not the adapter's: `VenueAdapter` above still composes the wide capability set, because which surfaces a venue offers is a fact about the venue. The two are different declarations for the same reason §3.6 puts a port with its consumer.

**Per-venue quirk matrix the adapter MUST encode (verified 2026-07-18):** the full matrix — every row normative for the adapter, each fact dated — is at (Profiles §1).

**Routing keys on `VenueInstrument`, and on Binance that selects a HOST, not a path `[→ M3 slice C2a, Profiles §7]`.** §4's rule that the order surface is product-routed already rests on spot and perp having independent order-ID namespaces; beneath it sits a blunter fact: Binance serves spot from `api.binance.com` and USDⓈ-M futures from `fapi.binance.com`, with separate documents, separate rate-limit budgets and a **different new-order cost** (Profiles §7). Bybit is the opposite shape — one host, one path, and `category` selects the market — so on Bybit a mis-route is a mis-set string **inside a signed body**, where nothing about the URL looks wrong. **An unconfigured or unrecognised product family MUST be refused, never routed to the other one's default:** `BTCUSDT` is a real, executable instrument on both, so a mis-route is not an error but an **accepted order on the wrong product** — a leveraged short where a cash purchase was intended. There is no status code for that, and no later reconciliation distinguishes it from an order we meant.

Contract-type (`linear`/`inverse`) is first-class so neutrality math can branch when inverse is added `[→ C6]`. All numeric fields cross the boundary as dimensional `fixedpoint` (parsed from venue decimal strings), never `float64` `[→ D3, X7]`.

**The same discipline binds the venue fields that are DURATIONS, and it needs a different mechanism.** `fixedpoint` makes a money field carry its dimension in its type; a duration has no such tag, and the unit of a venue's duration field is stated only in its **name** — Bybit's `fundingIntervalHour`. A field like that MUST cross this seam through a **conversion that states the unit**, and a value outside the range that unit can plausibly hold MUST be **refused rather than converted**. Without the rule, an adapter can multiply `fundingIntervalHour` by `time.Minute`, satisfy every sentence above, and hand §2.4 a 480-minute funding interval: the settlement enumeration divides by it, returns a plausible count, and §12's kill-gate carry figure is wrong by a factor of sixty **with nothing failing**. This is §10's argument for the recording seam — a duration recorded in the wrong unit renders as a plausible number and fails nothing — applied one layer earlier, at the boundary where the duration is *created*. The plausibility bound is a **unit check, not venue policy**: every perpetual on either MVP venue settles at 1/2/4/8h (Profiles §1), so a ceiling generous enough to admit any real schedule still rejects an argument in minutes, in seconds, or a `time.Duration` truncated to an integer — each of which is wrong by orders of magnitude and none of which is detectable downstream. **A zero or absent duration is refused, never defaulted to the venue's documented value.** Zero reaches the conversion from three situations a fallback answers identically — the venue genuinely reported nothing (Binance supplies no interval on the stream at all; it comes from the `fundingInfo` REST overlay, Profiles §1), the overlay was never fetched or a decode dropped the field, and a Bybit ticker **delta** whose unchanged field is simply absent (Profiles §1: "absent field = unchanged, never null-coerce") — and two of the three are a wiring failure wearing a correct reading's clothes. The third is worse: it absorbs §2.4's C8 flip, where a venue moves an alt 8h↔1h with no notice and the hold's settlement count silently changes by 8×. A venue's documented default is therefore the **adapter's**, applied from the positive fact that an overlay was fetched and came back empty — a state the caller must be holding in order to express `[→ C8]`.

**The `Envelope` is authoritative for provenance; a normalized payload carries none.** Source, `VenueSeq`, `SourceTime` and `RecvTime` are fields §3.5 defines for *every* stream, so a payload restating them is a second copy of one fact with nothing forbidding the two to disagree — and the unsafe direction is reachable without any implementer noticing they chose it, because gap detection reads `VenueSeq` while freshness reads the timestamps. Those two questions would then be answered from different sources, and a venue that restamps an unchanged reading becomes a fresh observation with no gap: precisely the silent stall §3.4's silence timer exists to catch. A payload likewise carries **no instrument** — `SourceID` is the mailbox key, so a payload naming a different one is a state no feed can produce and every adapter would otherwise have to check. **A payload MAY carry the one provenance field the `Envelope` structurally cannot, and a book delta is the case: it carries `FirstSeq` and MUST NOT carry `LastSeq`.** A delta spans a *range* of venue sequences — Binance's depth events cover several per message, Bybit's cover one — while an `Envelope` has a single `VenueSeq`. One end of the span therefore has to travel in the payload, and *which* end is the rule: `VenueSeq` is the last sequence the message covers, so a payload restating it is the forbidden second copy, whereas the span's beginning is not provenance at all but the message's own extent. The remaining disagreement — a `FirstSeq` past the envelope's `VenueSeq` — needs no rule of its own: it is an inverted span, and the existing refusal names it. The rejected alternative is instructive, because it looks safer: carrying both ends makes the payload internally consistent while contradicting its envelope, which is a third condition nobody writes a check for. The stream comments above list payload contents only.

### 4.1 Account & margin architecture — the safety premise (normative, boot-verified) `[→ R1-F1, R2-#2]`

The flagship's "the spot leg cannot be seized to cover the perp loss" property is **not universal — it is a consequence of a specific account posture**, and the two MVP venues reach it by *different, mutually-exclusive* mechanisms. The adapter MUST pin the posture below and the bot MUST **assert it at boot (reconcile-only boot, §7.5) and refuse to trade if any check fails** (a `$1K` non-negotiable, §1.1). Default posture = **segregated / isolated on both venues**; UTA unified-collateral is a documented capital-efficiency path, not MVP.

Per-venue posture facts + assert-or-refuse read paths: (Profiles §2).

The isolated **perp short can still be liquidated on a sharp rally** — a margin-management risk (the hedge breaks; spot gains but the perp margin is lost), *distinct* from spot seizure, which the posture above prevents. Because this property rests on per-position / segregation semantics rather than a single guarantee, an **empirical testnet liquidation test (isolated perp + non-collateral spot) MUST pass before real capital.** The `C_legs = N(1 + 1/L_perp)` *leg-capital floor* holds under this posture (the full reporting denominator is `C_allocated`, §2.2); **UTA unified-collateral would lower `C_legs`** (spot doubles as collateral) at the cost of this safety property — the documented efficiency upgrade, not MVP.

**The posture is ASSERTED and never REPAIRED, so Profiles §2's `POST` setters are OPERATOR acts and no automated path may call one `[v0.9.51, task #198, record §73c-3]`.** Two grounds, and the second is the one that survives an argument about convenience. An account-wide, effectively irreversible mutation inside an automated boot path is the wrong default — but more than that, **a posture the bot can repair is a posture whose violation stops being evidence.** This gate's value is not that the margin mode ends up right; it is that a wrong margin mode means *something happened here that we do not understand* — an out-of-band change, the wrong account, a compromised key. Silently correcting it discards exactly that signal and leaves the system trading on an account whose history it has just erased. An operator-run `arblab posture set` is not wrong in principle and is deliberately **not** in this milestone: it is a new credentialed **write** path, and with credentials deferred its only evidence would be a fixture.

**Per-symbol coverage is answered from the CONFIGURED ROSTER, never from the rows the venue happened to return `[v0.9.51, task #198, record §73b F4]`.** Profiles §2 already says it for Bybit — auto-add-margin off *"for every configured linear symbol (**not only open positions**)"* — and the parenthetical is load-bearing rather than decorative: an implementation that iterates the venue's returned positions checks **zero symbols on a flat account**, which is the state at every cold boot before the first trade, i.e. precisely when this gate is supposed to speak. A configured symbol the venue said nothing about is therefore a **refusal carrying a named reason**, not a pass. This is the same ruling §7.5 reached for spot baselines (*"coverage is answered from configuration, never from the journal"*), followed rather than re-derived, and it makes the failure direction right in the case that matters: a virgin deployment cannot pass by having nothing to check. Observations for symbols **not** on the configured roster are ignored rather than failed — an unexpected position elsewhere is §7.5's net-delta invariant's subject, not this gate's.

**The leverage pin is an OPERATOR-DECLARED config value, an absent pin REFUSES, and deriving the pin from the venue at first boot is forbidden `[v0.9.51, task #198, record §73b F3]`.** *"Configured leverage matches pin"* has one natural implementation — read the venue's leverage at first boot, store it, compare on later reads — and that check compares the venue against itself, so it **cannot fail on the first boot**, which is the boot that would have caught an account configured wrong before we ever touched it. One value feeding both the setter and the verifier stays self-consistent under every mutation. The pin is stated in configuration, independently of what the venue reports (§5.2), and its absence is §3.6 rule 4 in its most literal form: an unpinned leverage reads as *"any leverage is acceptable"*, which computes the safety gate in our favour with nothing failing.

**Portfolio Margin is a required check with NO verified read path, so it is ATTESTATION-BACKED with default REFUSE, and what that buys is stated rather than assumed `[v0.9.51, task #198, record §73b F1, §73c-1, §73k F10]`.** Every item in Profiles §2's Binance assert-or-refuse cell names a `GET` **except** Portfolio-Margin, and no section of either document supplies one — the requirement is stated (*"Portfolio Margin / Unified MUST be OFF"*) and a requirement is not a read path. It is the one check that cannot default to *passed*, because Portfolio Margin is precisely the setting that folds spot into futures collateral, i.e. the single account state that falsifies this section's whole premise. Until a read path is **verified** (Profiles §2 carries the marked unknown), the check is satisfied by an **operator attestation** shaped exactly like §7.5's spot baseline: an **inputs-not-conclusions** document recording what was observed, when, and by whom — never the verdict *"posture OK"*; pinned by a **two-act** `{path, sha256}` config edit, so writing the document and trusting it are separate deliberate acts; **invalidated by events, never by time**, so it cannot expire into either answer on a clock tick; and **absent → refuse**, by a named reason, never absent → pass. **Its limit is recorded so nobody re-derives it as a strength:** §7.5's baseline is bound to a *history* — a journal chain mark that a moved journal falsifies — and this document is bound to nothing, because the event that would invalidate it (somebody enabling Portfolio Margin) reaches **no endpoint this system reads**. So a loaded attestation is a point-in-time claim whose entire strength is the operator's word plus the deliberateness of the two acts. Every available mitigation is worse: a time bound is what this ruling excludes, and inferring the fact from a sibling classic-account setting establishes nothing, since Portfolio Margin is a different **account type** rather than a setting within the classic account. **The loosening trigger is a credential** — if any classic `/fapi` response distinguishes a PM account, the attestation gains a cross-check and stops being the only evidence.

**Every value this gate reads is admitted by WHITELIST, and a value the venue did not STATE is not a zero `[v0.9.51, task #198, record §73b F2, F5]`.** Bybit's `unifiedMarginStatus` is an external enum: Profiles §2 admits `{3,4,5,6}` and refuses classic `1`, which leaves the unlisted `2` — and every value the venue adds next year — decided by the direction of the default. Both refuse: the admitted set is a whitelist, not a blacklist of known-bad values, so the failure from forgetting is a refusal naming the value rather than a posture accepted because nobody enumerated it. The same direction governs **absence**, and there it is sharper than it looks, because one venue field already has a consumer that reads its silence the *other* way: §7.5's spot balance reader treats an empty `borrowAmount`/`spotBorrow` as *"the venue stated no borrow figure"* and lets the row pin, which is correct there — a total is being derived and a missing borrow does not corrupt it. Here the claim being asserted **is** *"borrow is off"*, and silence is not a zero. The two consumers of one field need **opposite** treatments of absence, so the posture check MUST NOT reuse the balance reader's predicate: reusing it imports the permissive arm into the one gate whose entire purpose is refusing borrow, and the resulting system passes its borrow check on a venue response that said nothing about borrow.

**A deployment with NO derivative instrument is VALID, and the empty roster crosses as a STATED FACT rather than as either default `[v0.9.51, task #198, record §73k F11]`.** §5.2's venue block is **singular** — *"a deployment trading two venues runs two of these, against two journals"* — so the spot half of a cross-venue carry is a legitimate configuration with no perpetual in it, and refusing an empty roster would outlaw a shape this project is building toward. Admitting it silently is the other error: a roster somebody forgot to fill in then passes vacuously, having evaluated no per-symbol rule at all. Neither default is safe, so the distinction is **carried**: the requirement states whether the deployment has derivatives or does not, the zero value names neither and is refused, and **both** disagreements are refused — derivatives with an empty roster, and no-derivatives while listing symbols — so the flag cannot say one thing while the roster beside it says another. What a no-derivatives deployment yields is not a vacuous verdict but a strictly smaller one: the account- and asset-scope rules still run and still refuse.

**The verdict names EVERY failed check, and "nothing was evaluated" is REFUSED rather than read as "nothing was wrong" `[v0.9.51, task #198, record §73d, §73j]`.** A first-failure-only checker never demonstrates the deeper claim and makes an operator fix a refused boot iteratively; the gate reports the full list so it can be acted on once. Failure reasons are a **product of two properties, not a severity ladder** — *was there an observation at all* and *did it satisfy* — so **unobserved** (a coverage gap) and **unstated** (an observation the venue did not fill in, i.e. a wire-shape change) are different files to open and are not collapsed into one. And the verdict carries **how many rules it evaluated**, because *passed* and *nothing happened* are otherwise the same zero value — and the second is the one a gate is most likely to be handed, since it **is** the zero value. A verdict that evaluated nothing is refused rather than agreed with, which is what stops a read that never answered from decaying into an account that was found clean.

**TWO answers on one key are a REFUSAL that names the check, never an unreadable answer, and the codec REPORTS both while the rules JUDGE them `[v0.9.52, task #198, record §73n F19]`.** A venue answering twice for one symbol has a documented cause and it is a posture violation: hedge mode returns one row per side (Profiles §9 records it verbatim for Binance V3; on Bybit it is one row per `positionIdx`, and there **no other probe names the position mode at all**). **Since `[v0.9.53]` the only surface this rule can fire on is Bybit's**, because §4.1 no longer reads any position enumeration on Binance — `symbolConfig` holds one row per symbol whatever the position mode is, so a duplicate there is a wrong-shaped answer with no venue behaviour behind it and stays a refusal, and Binance hedge mode is named directly and account-wide by `positionSide/dual`. The requirement is unchanged and is stated over the concern rather than over a venue; what changed is which venue can produce it. So the duplicate is **evidence**, and where it is handled decides what an operator is told. Handled in the codec as a wire fault, it refuses the whole read — and a posture that was **read and found wrong** then reports through the arm reserved for a posture that **could not be read**, which §7.5 classifies as incompleteness a retry may lift, for an account no retry will ever change. It also **discards every probe already decoded**, so the account-wide answer naming the same violation is lost with it, against this section's own rule that the verdict names every failed check. The division is therefore fixed: the codec makes both answers legible and attributes each to the probe that produced it; the rules see two answers on one (setting, scope, subject) key and refuse **by name**, latching. What remains forbidden is what the original argument was actually about — **folding** two rows into one answer, since either pick asserts a mode the account may not be in. The general shape is worth keeping: a layer that refuses what the layer above it has a rule for makes that rule unreachable, and both layers' tests stay green about a case the composition can no longer produce.

**§4.1's posture read rides product FAMILIES, and every family it rides MUST have a configured endpoint — checked at startup and refused by name `[v0.9.52, task #198, record §73n F20; NARROWED v0.9.54, task #199, record §73p]`.** A probe is routed by product family and a deployment holds one transport per **configured** endpoint, so a family with no endpoint makes that probe unissuable and this gate unanswerable on every boot of that document — §5.2's *"a value that makes the permitted region unreachable is refused at startup, by name"*, reached through an **omission** rather than through a value. The requirement is derived from the codec's own encoded steps rather than restated per venue, because a list and a table are two statements of one fact. **The set it binds over is the coverage-narrowed one and NOT the union of every probe** — see the subject requirement below: a family is required iff some probe answers a setting whose rule is **live** for this deployment. On Bybit that still binds in both directions, since `GET /v5/account/info` rides linear-perp and answers three settings whose subject is the **account**; on Binance it now binds only when a derivative is configured, at which point §5.2's instrument→endpoint rule already required the same family. The v0.9.52 half of this paragraph corrected a recorded reassurance — Bybit's account-level endpoints are answerable regardless *at the exchange*, and were not at this routing — and the lesson generalised further than it was written: **the reason a family is ridden is a property of the RULE, not of the venue**, which is what the next paragraph makes explicit.

**Every §4.1 rule MUST declare its SUBJECT — which part of the deployment it governs — and a rule whose subject this deployment does not have LAPSES, stated in the verdict rather than dropped `[v0.9.54, task #199, record §73p]`.** The scope of a rule (account-wide, per symbol, per coin) is the **granularity at which it is answered**; it is not what the rule is **about**, and the two come apart on this very table — `positionMode` is account-wide on Binance and per-symbol on Bybit, one subject at two granularities. Deriving the required families from the union of all probes silently read the first as the second, and demanded a **futures** endpoint from a deployment holding only the spot leg of a cross-venue carry — a shape §5.2's singular venue block actively builds toward — whose rules have nothing to say about a perpetual and whose boot would then depend on a futures API it never calls. Three subjects suffice: the **account** (its type, its collateral model, whether its legs are segregated), the **derivatives leg**, and the **spot leg**. Only the derivatives leg lapses today, because `RosterCoverage` is the only carrier that states a deployment lacks one; the spot leg has no such carrier and, under Bybit's UTA, a spot borrow is account-wide leverage regardless of which leg took it on — that argument MUST be re-derived before any future carrier reuses this mechanism. **The lapse is recorded, never silent.** A verdict carries every lapsed rule with its subject and the coverage that lapsed it, and `Evaluated` deliberately does not count them, so the vacuity guard still refuses a verdict that evaluated nothing: an exemption can narrow what is asked and can never produce a clean answer for an account nobody looked at. The classification is also **checked against the codec** — a rule with a venue read path that no probe answers is a startup refusal, since each half is internally consistent and only the composition can see the disagreement (the shape §7.6's fold-name check already uses).

**A per-symbol setting MUST be read from a surface that enumerates every CONFIGURED symbol, never from one that enumerates POSITIONS `[v0.9.53, task #199 item 1, record §73o; supersedes the F9/F18 ruling this paragraph previously owed]`.** A gate that cannot pass is not a conservative gate but a broken one — §5.2 already refuses, by name, a config value *"that makes the permitted region unreachable"* — and roster-scoped coverage (above) plus a setting published only on a **position** enumeration is exactly that shape, arriving through a rule rather than through a field: a flat account has no row for any configured symbol, so the gate that must pass before the first position opens cannot pass until a position exists. **This was recorded as an open operator question with four candidate rulings, and it turned out not to be a question.** `GET /fapi/v1/symbolConfig` publishes all three of Binance's per-symbol settings — margin type, leverage **and** auto-add-margin — for every configured symbol whether or not it holds a position, so the requirement above costs nothing: no operator bootstrap, no reliance on a recorded default, no second version of an endpoint to maintain, and one fewer probe. **The finding underneath it is larger than the gate it fixes, and it is the reason this is stated as a requirement rather than as a fix.** The setting was being read from `GET /fapi/v3/positionRisk`, which does not publish it **at all** (Profiles §2's ✅ SETTLED block, confirmed from two independent reads of the endpoint's field list) — so the gate refused on *every* Binance account, not only flat ones, and no fixture could see it because a fixture states what its author believes the venue sends. The version had been chosen for §7.5's net-delta invariant, where a missing row must mean *flat*, and §4.1 inherited it for the opposite question. *A narrowing carries an argument, and the next consumer inherits the choice without re-deriving its scope* — here the inherited choice was not merely out of scope, the field was never on the version inherited.

**RULED `[v0.9.54, task #199, record §73p]`: a Binance deployment configuring no derivative instrument does NOT route the futures family, and issues NO posture probe at all.** The question this paragraph carried — must a spot-only deployment declare a futures endpoint — was put as a choice between an operator burden and a coverage loss, and the subject requirement above dissolves it into neither. Every one of Binance's five **probed** rules governs the derivatives leg: the futures wallet's collateral mode, the futures position mode, and three per-symbol settings of a perpetual contract. The single Binance rule whose subject reaches the **spot** wallet is Portfolio-Margin — a different account **type**, which unifies the two — and it is the one rule with no venue read path anywhere, satisfied by the operator attestation (record §73b F1). So the exemption costs no check that could have applied, and the deployment's whole §4.1 answer is one evaluated rule and five stated lapses. **The two venues get opposite answers from one rule, which is what shows this is not a venue exemption**: a spot-only *Bybit* deployment still requires the linear-perp family, because `GET /v5/account/info` rides it and answers three settings whose subject is the account — under UTA the segregation property that decides whether its spot holding can be consumed as margin. **What this ruling exposes, and does not close `[OPEN]`:** Profiles §2's Bybit cell checks the spot leg directly — spot-margin mode off, every coin's borrow zero — and its Binance cell checks **nothing** about a spot leg. That asymmetry was invisible while every Binance deployment dragged in the futures checks regardless, and it is a question about the venue's own surface rather than about this engine, so it is filed rather than guessed (task #201). A second, narrower unknown remains a **loosening trigger** rather than a defect: whether Bybit's `GET /v5/position/list` returns a row for a configured-but-never-traded symbol is established nowhere, and all three of Bybit's per-symbol settings ride it — so if it omits such rows, Bybit has the shape Binance lost in v0.9.53. One credentialed read settles that (task #171), and until it does the strict refusal stays implemented, because it is the safe direction and silently loosening it is the failure this section exists to prevent.

## 5. Data model & configuration

### 5.1 Aggregates, ownership & value objects `[→ X1, X3, X7, X9]`

**The OMS aggregate (single owner).** `oms` owns one aggregate root `Trade` → `Orders[]` → `Fills[]` → `PositionAllocation`, plus a `Version int64` (OCC) — **starting at 1, and incremented only by a write that CHANGES the record** — and a durable, **append-only hash-chained** write-ahead journal (tamper-evidence lives on the journal — the reconciliation truth, §7.5, Z4 — not only on the lagged audit projection) `[→ R1]`. **Both halves of the OCC rule are stated because the natural implementation gets each wrong in a different direction.** *Starting at 1* is the zero-value-is-unusable rule (§3.6 rule 4's discipline, applied to a version): an `expected` of 0 is what a caller that never loaded a record passes, so it must match **nothing** — a version counter based at 0 makes that caller's blind write succeed against a real record and race whatever is there, while satisfying "a `Version int64` (OCC)" completely. Zero is not a version; it is the absence of one. *Incremented only on a real change* is the duplicate-fill case: §4 puts the same execution on two streams and §5.3 has REST recovery re-reading fills the private stream already delivered, so a duplicate is the **ordinary** case several times per fill — and a version bumped to record that nothing happened invalidates every other reader's expectation for nothing, turning the normal path into a conflict storm among §6's independent producers. A no-op write reports *unchanged*; it does not advance the version. It holds an **exclusive lease per hedge-group `(account, venue, symbol)`** — deliberately grouping a trade's spot + perp legs (**`Account` = the venue subaccount** — the lease MUST span both legs, which on Binance are distinct spot/futures API domains under one subaccount and on Bybit are one UTA, §4.1), and distinct from per-**instrument** identity (§5.3) — for the life of a trade; a second Intent on a leased key is rejected (no cross-strategy netting in MVP) `[→ X3, Z1]`. **The key's THREE components MUST all be carried, and the `Order` field list below carries two of them `[→ M3 slice E]`.** An order holds a `VenueInstrument` — venue, product, symbol, contract type — and nothing that says *whose* it is; `Fill` holds an `Account` because this section's dedupe key puts it first. So §6.7's classifier, which computes its residual **per hedge group**, cannot derive the group from its order set: the account must be supplied by whatever holds the venue credential and **asserted** against the store's, never inferred. The failure of leaving it out is the rare one in this kernel that **concludes rather than halts** — keyed on `(venue, symbol)` alone, a naked long in one subaccount nets against a naked short in another to a residual of **zero**, and since positions and margin are per subaccount none of that netting is real: the group reads flat, no `ExposureReduction` is sized, both legs stay naked, and every invariant computed over the group agrees. One store therefore holds one account's orders and refuses another's group; a deployment holding two subaccounts takes two stores, or an `Account` on the order record, which is an edit to this list. `audit` and `reconcile` are projections/process-managers over the journal, never co-owners.

**The journal carries records at TWO scopes, and the second one's subject is not an order `[→ M4 #177]`.** Every order-scope record is keyed by a `ClientOrderID`. A `PackageDelever` **generation** is "a bounded attempt" whose identity outlives any single order on either leg (§7.1, [mechanism: State-Machines §7]), so its records are keyed by a **`GenerationID`**, and the ladder's durable set — the opening with its reserved-reduction handle and per-leg target, each leg's submission with its client order id, the FLAG-3 authorization with its size, the supersession with its **path**, and the remaining phases — is stated there. Two rulings are normative here rather than left to an adapter. **(a) ONE chain, not two.** The invariant a replay most wants to check is that a generation's authorization record **precedes** its spot order's, and two chains have no order between them — so under two stores that invariant stops being a fact anything can check and becomes a discipline a package keeps. **(b) One chain is NOT one key.** The two id spaces share no namespace, so a primary key that is "sometimes an order and sometimes a generation" lets a lookup for one match the other; the record's subject column must say which space it is in. The write path stays single — §3.6 rule 6's `singlewriter` gate is unaffected, because both scopes are `oms`'s. **(c) The chain covers DOMAIN VALUES, not columns `[v0.9.56, task #203]`.** Widening an existing store's key column to carry a second scope's subject is a migration of an append-only table, and the question it raises — does an older record still verify — has a general answer worth stating: it does, provided every record's hashed preimage is built from the values a domain object holds rather than from the columns those values were stored in. Under that discipline a rename moves no byte of any preimage, so the chain's version label is unchanged and a journal written by the previous build verifies untouched; under the other, a schema edit silently forks the chain, which is the failure a version label exists to make loud. The append-only TRIGGERS are likewise untouched by the rename, because they police row writes and a column rename is neither.

Types (exported fields for repo hydration; all money is dimensional):
`Trade{ID, Strategy, Legs[], State, OpenedAt, ClosedAt, RealizedPnL Money}` · `Order{ClientOrderID, Instrument VenueInstrument, Side, Type, TIF, Qty Quantity, LimitPrice Price, ReduceOnly, PositionSide/Idx, State}` · `Fill{ExecutionID, Account, Instrument VenueInstrument, OrderID, Qty Quantity, Price Price, Fee Money, Ts}` (**no separate `FeeAsset`** — this field list predates the money kernel, and a `fixedpoint.Money` already carries its asset tag as a runtime-checked field per rule 4, so a second column would be a second copy of a fact the first states; the failure that invites is specific rather than cosmetic — fee attribution reads one field and the tax export reads the other, and a Binance fill paid in BNB against a USDT notional reconciles to two different numbers with nothing failing) (immutable venue `ExecutionID` = Binance `tradeId` / Bybit `execId`, unique only **within** an instrument; deduped by `UNIQUE(account, venue, product_category, symbol, execution_id)` — spot & perp ID namespaces are independent — so a fill seen on both `StreamExecutions` and REST `Fills` recovery applies once) `[→ Y1, Z1]` · `Position{Instrument VenueInstrument, Qty Quantity, EntryPrice Price, Margin Money, LiqPrice Price, MMR Rate}` · `FundingEvent{Account, Venue, Symbol, SettleAsset, SettleTs, Rate, MarkAtSettle Price, Amount Money, LedgerTxnID, Raw json.RawMessage}`.

Value objects (`Validate()`-guarded): **`VenueInstrument{Venue, ProductCategory, Symbol, ContractType}`** (the canonical identity for routing, market-data keys, orders, fills, reference calls, and recovery cursors `[→ Z1]`), `VenueSymbol` (underlying/display only), `ProductCategory{Spot|LinearPerp|…}`, `ContractType{Linear|Inverse}`, `Side`, `OrderState`, `KillSwitchMode`, `ForcedCloseReason{ADL|Liquidation|…}`, `SymbolSpec{ContractType, Tick, Lot, IntervalSource, CapSource}`, `FeeTier`, `StrategyParams`.

**Exactly-once funding ingestion `[→ A4, X9]`.** Prefer the venue's immutable **ledger transaction ID** as the identity. Absent that, key on `(account, venue, symbol, settleAsset, settleTs, ledgerEntryType)` — the specific contract **symbol**, not the `Spot|Perp` enum (else BTCUSDT and ETHUSDT perps settling USDT at the same instant collide and one receipt is silently dropped) — with a **DB `UNIQUE` constraint** and `INSERT … ON CONFLICT DO NOTHING` **in the same transaction** as ledger progress — a hash alone guarantees nothing `[→ Y5]`. Store the raw payload; model corrections/reversals as explicit events, never in-place edits.

### 5.2 Configuration schema
- **Global risk caps:** `per_trade_notional`, `per_venue_concentration_pct`, `per_symbol_concentration_pct`, `max_total_open`, `liq_distance` policy (open ≥30% / alert <25% / rebalance <20% / emergency <15% for BTC; tighter for alts) — one policy, reconciled `[→ C5]`; the **stale-mark escalation policy** — per-venue mark max-age (§3.4), the **`T_blind`** budget, and **`mark_blind_action` (`delever` | `close`)** (§7.1) `[→ R1d-9]`.
- **Market-data freshness:** §3.4's budgets, **one per (data class, venue)** — book, mark and funding — and the **cross-leg skew limit** the book budgets are gated beside. The mark's max-age already appears above inside the stale-mark escalation policy; the rest of the family did not, and one member of a per-venue set with a config field while the others have none is how the others become constants. Each is validated the way §7.4's ladder is: **a value that makes the permitted region unreachable is refused at startup, by name.** A skew limit of zero is the one somebody sets by accident — it admits only two legs delivered in the very same instant, so under a wall clock every package is refused and the engine simply **never trades, with nothing reporting an error**, because each individual refusal is the gate working. It is also reachable under a `TestClock`, so the backtest would pass a configuration that halts the live engine.
- **Per-venue:** endpoints, key refs (never inline secrets), **`spend_lock_dir`** — REQUIRED beside the key refs it protects, the directory of §7.6's one-spender `flock` (`<dir>/<domain>.lock`); all lock-aware processes on one host share it or they deliberately do not share the guard `[v0.9.47, record §68]` — IP-allowlist expectations, region, subaccount id. Example (the credentialed roots' schema): `"api_key_ref": "env:ARBLAB_API_KEY", "api_secret_ref": "env:ARBLAB_API_SECRET", "spend_lock_dir": "/var/lib/arblab/locks"`.
- **OMS deployment block `[→ M3 slice G2]`:** the write-ahead journal's **path** (§13's local-filesystem condition is met or missed by this value, and §7.5's `GateJournalDurable` is what checks it), the **subaccount id** orders and fills are attributed to, the **instrument table** with each instrument's base/quote decomposition (§5.1's `SymbolSpec` is what will own this — a venue symbol is deliberately unparsed, and a wrong split mints money whose asset tag is a lie), the **position enumerations** §7.5's net-delta invariant is asserted over, §5.3's **resolution policy** (propagation bound, sweep margin, per-surface assumed reach), and the venue **clock calibration** §5.3's anchor is stamped in. Four rules in it are about two fields AGREEING and no constructor beneath can make them: every instrument and every scope names the **configured** venue (one venue client cannot answer for two, and an instrument table spanning two makes the position adapter's own venue a function of map iteration order); every instrument's product family has an **endpoint** (on Binance the families are separate hosts, so an unrouted family is a query that cannot be issued) — and since `[v0.9.52, task #198, record §73n F20]` so does every family **§4.1's posture read rides**, which the instrument rule does not imply and cannot see: that read visits families this deployment may trade nothing on (all four Binance probes are on the futures family, two of Bybit's four on spot), so a one-sided document validated cleanly and then reported its posture unestablishable on every boot for ever; every **derivative** instrument is covered by a position scope (§7.5's scope-not-enumerated refusal is what this forecloses at the document — the spot half deliberately cannot use config-time enforcement, because `spot_baseline` is optional there, so its coverage check lives at assert time in the report); and the propagation bound sits **above** the request timeout and `recvWindow` beneath it, which §5.3 states and neither block's own validator can see. The `recvWindow` half also has a **construction check** since `[v0.9.47, record §68]`: a signed transport refuses to *build* when the calibrated venue-clock uncertainty already reaches the signing band (`min(recvWindow, ahead-tolerance)` — the same `checkServerTime` the send path applies, never a restatement of it), so a process that could only mint unsignable requests halts at boot instead of discovering it on its first post-fsync send. Two fields land with the spot baseline `[v0.9.49, task #179, record §70g]`: **`spot_settle`** — the settle bound (a positive duration) that §7.5's second look and the record protocol both wait, one rule with two callers — is **required whenever any spot instrument is configured and REFUSED on a spotless deployment**, because a bound nothing waits on is a claim nobody checks; and **`spot_baseline`** — `{path, sha256}` of the pinned baseline document — is **OPTIONAL, and the optionality is load-bearing**: a required field is circular on a virgin deployment (the record command runs off the same validated config the field would refuse to load), so absence is not a config error but the invariant's own named refusal (`UnassertedBaselineUnrecorded`, which holds the posture, §7.5); a pin on a SPOTLESS deployment is refused like the settle bound, a document nothing consumes being the same unchecked claim; and a field that IS present must name a document that loads, chain-verifies against the journal, and binds — venue, account label, credential fingerprint, rows-vs-prefix — or the boot ERRORS, a pinned document that will not load being a wiring defect rather than a gate refusal. **Two more land with §4.1's posture `[v0.9.51, task #198, record §73k]`, and both are REFUSED where nothing would read them:** every **derivative** instrument row carries the **`leverage` pin** — the operator-declared whole multiplier §4.1 compares the venue against — which is **required** there (an absent pin reads as "any leverage is acceptable", §4.1) and **refused on a spot row**, which no posture rule reads; and **`portfolio_margin_attestation`** — `{path, sha256}` of the pinned attestation document, §4.1's substitute for a read path that does not exist — is refused on a venue dialect whose account model has **no check that consumes it**, a pinned document nobody reads being the same unchecked claim as a settle bound nobody waits on. The dialect is also what selects the **account model** the posture rules are asserted against, and that mapping is not circular even though it looks it: choosing the classic table for an account that turns out to be Portfolio-Margin produces a **refusal** on the Portfolio-Margin row, not a wrong pass — the rules are asserted against the model we **require**, and the gate's job is to find out we are not on it.
- **The venue dialect is ONE field selecting FOUR collaborators `[→ M3 slice G2]`** — the order codec, the request signer, the rate-limit header reader and the response-envelope reader. Configuring them independently makes the mixture expressible, and the costly one is not hypothetical: on Bybit a refusal is stated in the **body of an HTTP 200**, so a client holding the other venue's envelope reader classifies every rejection as an **acceptance** — an order this system records as refused and the venue holds as live.
- **Per-strategy:** typed params (cash-and-carry: `min_funding_apr`, `min_hold_settlements`, `forecast_model`{`ewma_halflife`, `decision_quantile`, `aggregation`}, `basis_model`, `entry_drift_pct` (C3), `exit_band` + `exit_persist` (hysteresis band + dwell, §2.4), `perp_leverage`; cross-venue: `min_spread_bar`, symbol whitelist, `max_hold`).
- **Strategy registry:** `{enabled, weight}` per strategy `[→ user goal #1]`.
- **Emergency policy:** pre-authorized loss bounds + escalation ladder params (§7.4), editable only via the approval kernel (solo-honest: time-delayed self-approval + out-of-band confirm; four-eyes at scale) **before** exposure exists.
- Config is a typed struct with `Validate()`; every change is audit-logged and **revisions are recorded for deterministic replay** (§3.5).
- **Hot-reload is per field and default-DENY.** A field is restart-required unless it is explicitly marked reloadable (`config:"hot"`), and a reload that would change an unmarked field is **refused, naming the field** — not silently applied and not silently ignored. "Hot-reloadable where safe" is a per-field judgement somebody has to make, and the two defaults are not equally wrong when that somebody forgets: default-allow is noticed when a running process picks up a new journal path or a fencing-generation edit **mid-trade**; default-deny is noticed when a reload is refused with the field named. This is §3.6 rule 4's own argument — deny until a reason is written down — applied to a requirement this section left open rather than to one it decided differently. Composite fields **recurse** rather than being compared wholesale, so a reloadable rate-limit budget nested inside a non-reloadable venue map stays tunable while **adding** a venue requires the map itself to be marked: editing a budget and wiring a new venue client are different acts. One deliberate asymmetry: an **unrecognised** tag value is an **error**, not a silent deny — everywhere else the safe direction is the loud one, and here it would have been the silent one.

### 5.3 OMS order & fill identity, states, and commands `[→ X1, Y1, Y2, Y3]`

**Identities.**
- **`ClientOrderID`** — deterministic, OMS-minted, unique per submission; a **recovery correlation handle, not a venue idempotency key** (Binance permits reuse once an order is terminal). Never reused within the recoverable window.
- **`ExecutionID`** — the venue's immutable fill id (Binance `tradeId`, Bybit `execId`), unique only **within** an instrument. Fills dedupe on `UNIQUE(account, venue, product_category, symbol, execution_id)` — the single normative key (spot and perp ID namespaces are independent); `VenueSeq` is *not* an identity `[→ Y1, Z1]`.

**Order state machine + an orthogonal fill ledger `[→ Z2]`.** Fills are *not* gated by order lifecycle: a **cumulative-execution ledger** accepts any deduped fill for a *known* order regardless of its current state — so a post-cancel or post-`SubmissionUnknown` late fill still applies. Order state tracks submission/finality; the fill ledger tracks realized quantity; **net delta is recomputed from the ledger on every fill/position event, and the §6.7 classification is re-evaluated on every event that can change *either* of its inputs** — fill/position events (they move the *realized* delta) **and every order-lifecycle/finality transition on the hedge group** (ack, reject, cancel acknowledgement, terminal order status, an executions-sweep/watermark completion, a stable-not-found finality timer, a resolving-query result — they collapse an order's *possible-delta interval*) `[→ R1d-3]` (§6.7).

The order lifecycle is the fixed state set `Planned`, `DispatchAuthorized`, `Submitted`, `SubmissionUnknown`, `Acknowledged`, `PartiallyFilled`, `CancelPending`, `CancelUnknown`, and the terminals `Filled` / `Canceled` / `Rejected` / **`AbsentAfterFinality`** (**proved stable absence** — the stable-not-found rule completed across order *and* execution surfaces past the watermark; **distinct from `Rejected`, which requires an explicit venue rejection** — proved absence and venue rejection are different evidence classes, and a discovered late execution supersedes `AbsentAfterFinality` because venue reality wins, §3.0) `[→ R1d-F2]`. `DispatchAuthorized` is **the crash boundary** — a single `Place` for this client ID is **fsync-committed *before* the non-transactional network write** — and recovery resolves such an order **by query only** — never resubmit, never infer "not sent" `[→ R2b-4]`. Terminal states are terminal for *state* only: the **fill ledger never closes for a *known* order** — any deduped fill (`UNIQUE(account,venue,product,symbol,execution_id)`) is admissible **indefinitely**, since a legitimate fill can surface after prolonged downtime; the bounded "finality window" governs only **ambiguous-order *acceptance* resolution** (the stable-not-found rule), **not** fill admission `[→ R2b-12]`. Per-state meanings + the full transition table: [mechanism: State-Machines §1].

**Rules.** `Place` is called **once** per order; transport retries forbidden `[→ Y2]`. **Crash recovery is defined for every pre-ack state `[→ R2b-4]`:** a `Planned`-only order was never dispatched (no venue order can exist) → safe to replan or discard; an order at **`DispatchAuthorized` or beyond** is resolved **only** by `OrderByClientID`/`Fills` under the venue-specific stable-not-found rule — **never resubmitted, and "not sent" is never inferred** (the single `Place` may have executed with its response lost). `ClientOrderID` durability alone does not reveal whether the `Place` ran — the state machine does. `SubmissionUnknown`/cancel resolution runs **concurrently** with exposure management — the OMS never blocks flattening of a **determined** residual on it; an **ambiguous** residual (any counter-leg order with remaining executable quantity) is quiesced to finality **first** (§6.7). If the resolving query is unavailable/rate-limited, new trading stays disabled and rate-limit budget is **reserved for recovery**; "not submitted" is never inferred from a transient not-found — finality follows a **venue-specific stable-not-found rule**. On **Bybit**, `GET /v5/order/realtime` holds only the most-recent ~500 closed orders and is **cleared on a server restart**, so resolution MUST fall back to `GET /v5/order/history` by `orderLinkId` (a filled order is always recoverable there); never infer "not submitted" from realtime alone `[→ R2-#1]`. Applying a fill (dedup → ledger → `PositionAllocation`), advancing the **per-instrument** REST recovery cursor, and appending journal/outbox events happen in **one transaction** `[→ Y1, Z1]`.

**`AbsentAfterFinality` is BOUNDED BY THE VENUE'S PUBLISHED RETENTION, and beyond it the rule is not satisfiable `[→ M3 slice C2b, Profiles §8]`.** The order surfaces do not retain orders forever, and **each venue's cliff lands on this system's most common outcome**: Binance USDⓈ-M drops an order whose *"status is `CANCELED` or `EXPIRED` **and** … has no filled trade **and** created time + 3 days < current time"*, and Bybit's order history keeps `Cancelled`/`Rejected`/`Deactivated` for **24 hours**. §6 step 6 sends nothing but marketable IOC limits, so an IOC that did not fill — terminal immediately, with no execution — **is** that row. Past the cliff the resolving query cannot distinguish *"the order existed and expired unfilled"* from *"the order never existed"*, so a stable not-found there is **not** proved absence and MUST NOT be recorded as `AbsentAfterFinality`: the terminal state would be asserting an evidence class it does not have. **The rule is unchanged and what is new is that it has a domain** — §6.7's composition (a stable not-found **plus** an executions sweep past the watermark, *"never a synthetic stable-not-found alone"*) holds **inside** the retention envelope, where a filled order survives 90 days of orders and ~6 months of trades on Binance, and has no meaning outside it. **The venue-specific stable-not-found rule MUST therefore take the answering surface's published reach as an input and refuse to claim proof beyond it**, and where a venue publishes **no** retention (Binance spot's order endpoint) the unknown is carried as an unknown rather than encoded as an unbounded promise. **The exposure reading is identical either way** — an unfilled IOC and a never-existent order both contribute zero delta, so nothing is mis-hedged and no invariant fires — which is exactly why this is easy to dismiss: what breaks is the evidence class this section spends a paragraph keeping distinct from `Rejected`, and which §7.5's reconcile-only boot consumes as truth after downtime that can trivially exceed three days. The venue layer **reports** the reach; applying it is the recovery path's.

**The stable-not-found rule measures from ONE anchor — the instant this system committed to the single `Place` — and that anchor MUST be DURABLE `[→ M3 slice D]`.** The rule has two clocks in it and they count from the same moment. SM §2 step 1 will not accept an absence until a still-in-flight send can no longer land (*"a `DispatchAuthorized` send may land **after** the query"*), which is that instant plus a propagation bound; the retention paragraph above will not accept one from a surface that has purged the row, which is that instant plus the venue's published reach. The anchor is recorded in the **venue's own clock frame with its uncertainty band**, because the cliff comparison is against the venue's own arithmetic — Binance's is literally *"created time + 3 days < current time"*, evaluated by Binance on Binance's clock — and a local instant compared against a venue retention is wrong by a small stable offset while reading as correct. The two bounds then read **opposite edges** of that band, each taking the one that makes it refuse sooner: the landing horizon takes the **latest** edge (the order could have been created that late), the retention cliff the **earliest** (the row could have been purged that early). A bound that cannot be told apart from the band **refuses** rather than guessing; an *unset* anchor answers every boundary that way, which is safe and silent.

**Durability is where this rule silently stops working, and the failure is a halt rather than a wrong number `[→ M3 slice D]`.** This section already says a `DispatchAuthorized`-or-beyond order is resolved **only** by query. If the anchor lives only in a memory projection, a **crash-recovered** order at that state has none — so `AbsentAfterFinality` is **unreachable for exactly the order this section says recovery resolves that way**. The order stays in a state §6.7 reads as contributing a possible-delta interval, its hedge group is `Ambiguous` for ever, new trading is held, and nothing reports an error. **The journal is therefore the anchor's home** and §7.5's reconcile-only boot re-derives it on replay; any in-memory record of it is a cache and never the authority. **The anchor is a field of its own journal RECORD KIND, and the recorder MUST refuse to write `DispatchAuthorized` through any record that does not carry one `[→ M3 slice F1]`** — the same refusal the current-state store makes, in the store recovery actually reads. Stating it once, on the projection only, is what left the log able to hold an authorization the projection could not: the two are mirrors across *journal-and-projection*, and a rule enforced on one of them leaves the other holding exactly the shape the rule exists to eliminate. *(The rule's four composed gates — landing horizon, absent from every surface, a conclusive executions sweep past that horizon, and within the answering surface's reach — are SM §2's contract composed with the retention paragraph above; each is independently falsifiable and a failing gate yields a named refusal and **no** state change.)*

**An absence must be inexplicable under EVERY hypothesis, so the retention bound is the SHORTER of the surface's two `[→ M3 slice D]`.** At the moment the rule asks whether an absence is explicable by purging, it does not know whether the order filled — **that is what the absence means** — so the comparison MUST be against `min(unfilled retention, filled retention)`, never against the unfilled figure whose name makes it the tempting field. Both venues publish the shorter one for *unfilled* orders today, and that is precisely why taking the field by **name** rather than by **role** is unsafe: a venue that later publishes them the other way round widens the bound with nothing failing.

**Where a venue publishes NO retention, the assumption is an operator's and MUST be stated `[→ M3 slice D]`.** Neither default is available, and the unsafety is not symmetric. *"No cliff"* licenses treating an absence as proved for ever, writing an evidence class we do not have into a terminal state §7.5 consumes as truth after arbitrary downtime. *"Never provable"* means a lost-ack spot IOC that did not fill can **never** reach `AbsentAfterFinality` — and §6's cash-and-carry spot leg is a **BUY**, so that is not a corner but half of every trade, whose hedge group would stay `Ambiguous` for ever with new trading held. The second is the one that looks careful, which is why it is written down: it fails by halting quietly rather than by trading wrongly. So a surface that is unpublished **and** unconfigured yields a **refusal that names itself**, never a proof. The check that would be **in time** — refuse to trade an instrument whose absences could never be proved — belongs on **§7.5's boot list**, because the irreversible commitment is the `Place` and it has already happened by the time this rule runs.

**Commands (distinct verbs, so emergency ≠ strategy) `[→ Y3]`:**
- **`OpenTrade`** — strategy-originated, **exposure-increasing**; subject to `stop-opening`. **`CloseTrade`** — strategy-originated but **risk-reducing**, so **permitted while `stop-opening`** (mode (a) stops *opening*, not exiting — else a now-negative carry could not be stood down, §2.2/§2.5); subject to command arbitration (§3.4), and any ambiguous close order routes through the §6.7 classifier `[→ R2b-B1]`.
- **`ExposureReduction`** — foundation-originated, **exempt from `stop-opening`**, used to remove a naked leg after ADL / liquidation / one-leg-failure — issued **only on a residual whose sign *and size* are fixed** (§6.7); while **any** counter-leg exposure-changing order still has remaining executable quantity or an unresolved state (not only `SubmissionUnknown` — a `PartiallyFilled` or `CancelPending` order can still move the delta) the residual is *ambiguous*, and §6.7 requires **quiesce-to-finality first**, because no single compensating trade is correct in every reachable venue state `[→ R2b-B1]`. The action is **state-dependent, and `reduceOnly` is set only when the order reduces an *existing position on that instrument*** — never merely because it reduces package delta `[→ R2-#4, Codex]`; the per-case branches (naked long spot / naked short perp): [mechanism: State-Machines §2].
- **`PackageDelever`** — foundation-originated, **exempt from `stop-opening`**, used to **reduce leverage on a *still-neutral* package** when isolated-margin liq distance breaches and the top-up path fails (§7.1). It reduces **both legs**, but **sequenced so the transient never worsens the at-risk direction `[→ R1b-1]`**: the trigger is the **perp short nearing liquidation on a rally**, so it **reduces the perp short *first*** (buy-to-reduce — which itself relieves the liq risk), **confirms that reduction to finality** (§6.7), then **sells no more spot than the confirmed perp reduction** — the momentary exposure is thus net-*long* (safe in the triggering rally), **never net-short**. Generation mechanics (the reserved second leg, bounded finality-gated attempts, hold/alert, terminal flatten, supersession): [mechanism: State-Machines §7]. **Two clauses of that mechanism are normative HERE because they are about this command's own vocabulary `[→ M4 #177]`.** (i) **"Quiesce the reserved second leg to §6.7 finality first" is AWAITING finality, never issuing a cancel** — §6 step 6 sends nothing but marketable IOCs, so every order this system places is immediately terminal at the venue; there is no cancel verb on the §4 venue contract and none is owed, and the wait is bounded because the phases it binds on exit only by ending the generation. (ii) **A supersession ends the GENERATION, and whether §7.1's ladder may open a LATER one is a property of WHICH row fired**: the premise-lost row resumes it (the package becomes neutral again while the perp short may still be nearing liquidation, so refusing would disable leverage reduction for the life of the process), while `EmergencyClosePackage` and the `FenceReadyLost` arbitration do **not** (the foundation has taken the package away from this ladder, and re-opening would be the OMS re-authorising itself against a live arbitration). The answer is carried on the durable supersession record, because the two failure directions are not symmetric and neither is re-derivable from an order journal.
- **`EmergencyClosePackage`** — foundation-originated, **exempt from `stop-opening`**, the kill-switch **flatten** action for a package with **no naked residual** (a healthy *neutral* cash-and-carry). `ExposureReduction` would **no-op** there (delta≈0) and `CloseTrade` is **strategy-originated** — the foundation cannot rely on a strategy emitting it during an emergency, since **emergency authority belongs to the foundation, not the strategy** (and a strategy `CloseTrade` is subject to strategy logic + command arbitration, §3.4) — so **neither is the foundation's emergency close of a neutral package**; this command fills that gap. *(`CloseTrade` is **not** subject to `stop-opening` — that mode is `OpenTrade`-only, §5.3 above — so the old "subject to `stop-opening`" rationale is dropped; the justification is authority + the delta≈0 no-op, not a `stop-opening` block)* `[→ R2c-7]`. It **supersedes and quiesces any active `PackageDelever` generation**, **quiesces existing orders through the §6.7 finality contract**, then **closes *both* legs**, routing any resulting one-leg residual back through the §6.7 classifier `[→ R2b-B1]` [mechanism: State-Machines §2, §7].

**Every command maps to a §7.6 shed class, and the mapping is NORMATIVE here because nothing else carries it `[→ M3 slice C2a]`.** §4's `Place` takes the class as an argument precisely because the `Order` aggregate does not hold its originating command; this table is therefore the only statement of which class an order is entitled to, and the caller that knows the command is the one that must apply it:

| Command | §7.6 class | Why |
|---|---|---|
| **`OpenTrade`** | `Opening` | It creates new exposure — the act §7.6's `Opening` row names, and the act `stop-opening` stops. |
| **`CloseTrade`** | `Safety` | Risk-reducing, and **the classification follows §7.6's own "monitoring outranks new exposure" argument rather than the command's origin**: shedding an exit at the ~70% ceiling makes the governor the reason a now-negative carry cannot be stood down, and rate-limit pressure correlates with the volatility that turns a carry negative. It is strategy-*originated* and risk-*reducing*, and it is the second property that decides the class. |
| **`ExposureReduction`** | `Safety` | Removes a naked leg; §7.6 names a flatten in the `Safety` row verbatim. |
| **`PackageDelever`** | `Safety` | Its trigger is a liq-distance breach **after §7.1's top-up path failed**, and that path is itself in §7.6's `Safety` row. |
| **`EmergencyClosePackage`** | `Safety` | The kill-switch flatten. |

**The `Opening` class therefore contains exactly ONE command, and that is the checkable form of the rule.** Every other §5.3 command is risk-reducing, so a mapping that put any of them under the back-off ceiling would shed a *reduction* to preserve budget for *exposure* — the inversion §7.6's ordering paragraph already refuses one class further down. The table is **total over the command set** for the same reason §3.6 rule 10 requires a switch to be: a command added later with no row here would otherwise take whichever class the caller nearest to hand was already passing. **`Routine` never appears**, because it is read traffic and no order is issued under it; the type an adapter accepts is narrowed to the two rows above (§4).

## 6. Trade lifecycle (foundation, strategy-agnostic) `[→ X1, X2]`

1. **Ingest → state.** `marketdata` normalizes with venue-seq + source/receive timestamps; `engine/state` latest-value cache; **per-data-class freshness** (sub-second books for execution) `[→ X4]`.
2. **Signal.** `Strategy.Evaluate(MarketView)` emits Intents.
3. **Pre-trade risk.** `risk.Gate` re-validates edge, free margin, position state, kill-switch, rate-limit budget, concentration, the funding-boundary guard using `Clock.ServerNow(venue)` `[→ X8]`, and a **fresh account-posture snapshot** (`AccountPostureSource`, §4.1) — versioned, **fresh within a max-age TTL *and* re-verified by the pre-trade REST read**, *not* anchored to "the last account event": margin-mode changes do surface on the private WS (Binance `ACCOUNT_CONFIG_UPDATE` for leverage/multi-asset, `ACCOUNT_UPDATE`+`MARGIN_TYPE_CHANGE` for isolated/cross), but **position-mode changes emit *no* venue event on either venue, so a TTL + REST re-verify is the only reliable guard** — never event-presence `[→ R1b-5, R2b-5]`. A stale or wrong posture — margin mode changed out-of-band, spot-hedge/borrow re-enabled, auto-add-margin on, **position mode flipped to Hedge, or configured leverage off the pin** — **blocks the trade** `[→ Codex, R2b-5]`.
   - **The TTL is an ADDITIONAL UPPER BOUND on a cached snapshot, never a way to SKIP the read `[v0.9.51, task #198, record §73c-2]`.** *"Fresh within a max-age TTL **and** re-verified by the pre-trade REST read"* admits two parses, and only one of them is safe. Under the permissive one — *the read may be skipped while the snapshot is inside the TTL* — a position-mode flip inside the window is undetected, which is the exact case this step's own next sentence says the re-verify exists to catch: position-mode changes emit **no** venue event on either venue. So **every trade performs the full posture read regardless of snapshot age**, and the TTL merely caps how old a snapshot may be even when a read did occur. The conservative parse is correct under both readings of the `and`; the permissive one is correct only under one. The cost is affordable for a structural reason rather than a hopeful one — cash-and-carry opens are hours apart, not sub-second — and the per-read weight is recorded per venue at the probe definitions rather than asserted here.
   - **One use case, two callers, and the second lands with the trading loop `[v0.9.51, task #198, record §73b F6]`.** §4.1's guard is a single use case: §7.5's boot calls it today, and this step's caller lands when a trading loop exists to call it — nothing in this system sizes or dispatches a strategy trade yet (§12 item 4). It is deliberately **not** a second, speculative code path built with no caller, and the debt is recorded rather than left to be rediscovered: until that caller exists, *"boot **and** before each trade"* is half-delivered, and the half that is missing is the one that catches an out-of-band change made while the process was already running.
4. **Sizing.** `min(per-trade cap, per-venue headroom, fillable-within-slippage, margin-for-target-liq-distance)`; liq distance from the **live tier MMR** `[→ C4]`; quantize both legs to the lot-size intersection + residual tolerance `[→ X7]`; budget the naked-leg price gap + reacquisition slippage over the **whole unhedged window — including the ambiguous-order resolution window *and its deadline-exceeded branch*** (a counter-leg with remaining executable quantity, whose finality contract may not complete within ≤30 s, §6.7), not only a ≤5 s determined-flatten `[→ P3, X2, R2b-B1]`.
5. **Plan & journal (OMS).** Mint **deterministic `ClientOrderID`s** — a pure function of `(TradeID, leg index, attempt)`, so nothing is stored for the OMS to re-derive them after a crash, and the attempt advances for the **whole plan** rather than per leg (§5.3 forbids reuse within the recoverable window, so the unsafe mistake is advancing a subset). Persist **and fsync** the trade's intents to the write-ahead journal **before any submission**, and journal **every** leg before dispatching **any** `[→ X1]`. Every planned order is a **marketable-IOC limit** — the pattern step 6 fixes, applied at minting so no other combination is expressible on the dispatch path.
   - **The trade-level `TradePlanned` record awaits §5.1's `Trade` aggregate**, which has no domain type yet; the journal holds **one record per intent**, and the grouping is recoverable without it because `ClientOrderID` is reversible and embeds the `TradeID` (§5.3).
   - **What makes that sufficient is the all-legs-before-any-submission rule, not the id format.** Every state a partially-journaled plan can reach is one in which *nothing was sent*, and §5.3 says what such an order is worth: "a `Planned`-only order was never dispatched (no venue order can exist) → safe to replan or discard". So the question a `TradePlanned` record would answer — *was this trade's leg set complete?* — has no consequence attached to it under this ordering.
   - **The change that would break the argument, named because it is the one a later slice might make without noticing:** a planner that dispatches leg 0 before journaling leg 1. A crash between them leaves a **filled leg whose package reads as single-legged**, with nothing in the journal to say otherwise — at which point the trade-level record becomes required rather than deferred.
   - **Dispatch (step 6) reads the order it sends from the write repository this step fills**, never from a caller — so an order that skipped this step cannot be submitted, and an order mutated after planning cannot be submitted in place of the one that was journaled.
   - **§2.4's trading filters are verified per leg HERE, before anything is journaled `[→ M3 record §62]`:** lot step, min quantity, tick and min notional, each against the leg's own venue's published values, an absent entry refusing by name — so a wrong quantity is a plan refusal citing the filter, not a venue rejection arriving after the sibling leg was sent. One shared conformance implementation serves this step, step 6's preflight and §7's ladder, deliberately: two statements of "on the venue's grid" is how a plan-time pass and an execute-time refusal come to disagree by one lot step. **The two ADMISSION-time enforcers — the preflight and the ladder — additionally share one filter POLICY value (the map and its row-age bound together), held by the dispatch path they are both constructed from `[v0.9.58, task #184]`**, so that no composition root can give one of them a grid the other would refuse against. This step's Planner deliberately does NOT share it: plan time and admission time are different enforcement points, and the whole reason admission re-verifies is that the planning revision may differ.
6. **Execute (OMS via `OrderGateway`).** Immediately before the single `Place`, **fsync `DispatchAuthorized`** (the commit to call `Place` exactly once — the crash boundary, §5.3), so recovery *queries* rather than assumes; then submit **once** per order (no transport retry); parallel marketable-IOC limit orders (never raw MARKET), identical base quantity, unique client IDs. A timeout/5xx moves the order to `SubmissionUnknown`, resolved by `OrderByClientID`/`Fills`, never resubmitted (§5.3). **The ack's venue order id is PERSISTED — journaled as its own record kind (`acked`) and applied to the projection — and the acked record lands BEFORE the result-state record `[→ task #174, record §63]`:** a crash between the two writes then leaves `authorized`+`acked`, which recovery can still join on Binance, where that number is the **only** key a trade sweep has (Profiles §8); the reverse order leaves exactly the lost-ack world the record exists to shrink. A venue that returns no id gets **no** record — the absent id has one spelling, the record's absence. An id that **contradicts** the store — this order already recorded under a different id, or another order on the **same instrument** already recorded under this one — is refused at the apply, **holds new trading** (the executor's fan-in latches, as for a stale projection), and is durable in the worse way: the journal holds both acked records, and §7.5's replay refuses to compose them, so the boot that would have built a poisoned rule-out index fails first. Under the banked non-reuse fact neither contradiction has an innocent reading. A DROPPED ack write (journal or apply, without contradiction) holds nothing: it degrades §5.3's gate 3 back to refusal-to-conclude, which is safe and late, and is reported per leg for the operator. Applying each fill, advancing the REST recovery cursor, updating `PositionAllocation`, and appending events happen in **one transaction**; the outbox exports at-least-once `[→ X1, Y1, Y2]`.
   - **The package rule `[→ M3 slice G3]`:** step 5's plans are multi-leg and this step's word "parallel" is about the PACKAGE, so the fsync-side rule extends from the order to the package: **every check that can refuse ANY leg runs before ANY leg's authorization fsync** — a package is refused whole, with nothing sent, or fanned out whole, one goroutine per leg, each leg's fsync immediately before its own single `Place`. After the first authorization the package is **no longer refusable, only reportable per leg**, because a sent IOC cannot be un-sent and a composite error would invite the `if err != nil { return }` reflex over legs that are live at a venue. The package-level checks are this step's own clauses read off the ids and records: one trade and one attempt (step 5 advances the attempt for the whole plan), distinct legs, every record at its expected version and in a dispatchable state, marketable-IOC only, **identical base quantity** — compared asset-checked, so "identical" includes "in one base asset" and a package sized in two bases is a refusal, never a mantissa comparison — and **§2.4's trading-filter conformance re-verified per leg against THIS process's filters**, as a second pass after the package-shape checks (so a mixed-base package keeps its sharper diagnosis): a replayed `Planned` record was conformed by whichever revision planned it, §5.3 says replan-or-discard for such records, and this check is that doctrine made structural for the package path.
   - **Reserve before fan-out `[v0.9.47, task #188, record §68]`:** after the package checks admit and BEFORE any leg's authorization fsync, the executor acquires **one all-or-nothing rate-limit reservation for the whole package** (§7.6's reservation clause) — a refusal refuses the package whole, with nothing occupied, nothing journaled and nothing sent, exactly as the other pre-fsync checks do. On admission each leg carries its hold through the widened `Dispatch`/`Place` arguments (§4), the transport converts that leg's occupancy to a charge at the last pre-send instant, and a blanket cancel releases unsent occupancy on **every** exit while consumed charges stay counted. The ordering closes the gap this step's own concurrency opened: legs fanned out in parallel each acquired capacity independently AFTER their authorization fsyncs, so a package admissible leg-by-leg but not in sum produced a durable authorization for a leg the governor then refused — §5.3's post-fsync recovery episode, by configuration, on the venue's own arithmetic.
   - **Dispatch takes the §7.6 shed class from its caller, and MUST refuse an invalid one ABOVE the fsync `[→ M3 slice C2a]`.** §4 records why the class cannot be read off the order and §5.3 holds the command→class mapping; what this step fixes is **where** a bad one is rejected. The `DispatchAuthorized` fsync *is* the commitment to call `Place` exactly once, so a refusal after it would leave a **durable authorization for an order nothing ever sent** — which §5.3 then resolves the only way it may, by querying a venue that never heard of the id, and which recovery may never resubmit. Every check on the dispatch path that can fail for a reason the caller controls belongs on the same side of that fsync, and the ordering is normative rather than stylistic: the two sides differ in whether a rejected call costs nothing or costs a recovery cycle.
7. **One-leg-failure handler.** On **every** fill/position event **and every hedge-group order-lifecycle/finality event**, recompute net delta from the fill ledger and **classify the residual as *determined* or *ambiguous* before acting** — this classification, not the raw delta, gates the compensating trade `[→ Z2, R2b-B1]`. **The classification is only sound over a current-state projection that ACCEPTED every write, and the failure direction is the unsafe one, so it is a refuse-to-trade condition rather than an alerting one `[→ FM-5-family]`:** §6's write path is journal-then-apply, and an apply that fails after its `Place` has run leaves the order at `Planned` in the projection while the venue holds it — and `Planned` is the one non-terminal state contributing **no** possible-delta interval. A sent order therefore reads as contributing nothing, which turns an **ambiguous** residual into a **determined** one and unblocks precisely the immediate compensation the ambiguity existed to hold. The journal is unaffected (it is written first and is what §7.5 replays), so the condition is recoverable rather than lost: an apply failure on an order whose dispatch reached the venue **holds new trading** until that order's state is re-derived from the journal. This is the `FM-5` shape at the projection layer — a quantity read from a store that a *different* store is the authority for — and, as there, no invariant computed **from** the projection can detect it. **Classification is a function of THREE inputs, and re-runs when ANY changes `[→ R1d-3, FM-6]`:** fills/position events move the *realized* delta; order-lifecycle/finality events — ack, reject, **cancel acknowledgement, terminal order status, an executions-sweep/watermark completion, a stable-not-found finality timer (a `Clock` timer, not a venue event), a resolving-query result** — collapse an order's *possible-delta interval*; **and a change to `outstanding_reserved_reductions` moves the SUBTRAHEND `[→ FM-6]`** — an entry created, amended or retired by any of its producers (a `PackageDelever` generation opening, amending as its perp leg confirms, completing, terminal-flattening, or being superseded; an `IntervalFloorReduction` retiring; a protective order's leg reservation released). **The third input is the one a reader most easily loses, because the classifier's own arithmetic hides it: the residual is `realized_delta − outstanding_reserved_reductions`, so the subtrahend changes the verdict exactly as the minuend does, and every producer moves it on events that are NOT order events.** Ambiguity therefore resolves through **any** of these, and the machine MUST NOT wait for the next fill/position event when order state alone became conclusive (a cancel confirmed with **zero** executions emits no fill and no position event, yet fully collapses that order's interval) — **nor for an order event when the LEDGER alone changed the residual, which is the same argument owed to the third input: a generation ending emits no fill and no order event, yet moves the residual by the whole reserved amount `[→ FM-6]`**:
   - **Determined residual** — the exposure is **fixed because no exposure-changing order on the hedge group has any remaining executable *or unobserved* quantity**: e.g. a `ForcedCloseReason` (ADL/liquidation) event definitively closed a leg with no pending counter-order, or every leg has reached a **venue-terminal state with its cumulative execution reconciled**. Here the handler **immediately** (≤5 s, §9) issues an `ExposureReduction` (§5.3) sized from **`realized_delta − outstanding_reserved_reductions`** (which **includes reserved *generations*** — a `PackageDelever`'s in-progress reserved second leg, a protective order's leg reservation — so an intentional in-progress transient is **not** misread as a naked residual). **Because that subtraction is unconditional, every ledger entry MUST be *backed at the instant it is counted*: an entry is the exposure change its reserving action has already COMMITTED and not yet REALIZED — never a target it merely intends `[→ FM-5]`.** The three producers commit at *different moments*, and the rule is the same for each: a `PackageDelever` generation's reserved spot leg carries the **confirmed perp reduction not yet matched by that sale**, so it is **zero at `Planned`** — where the perp leg has committed nothing — and is amended as the perp leg confirms; an in-flight `IntervalFloorReduction` carries **its own dispatched reduction not yet realized**, its full size from dispatch, because that order is genuinely working and that is exactly what stops it being re-read as fresh naked exposure; an `Armed` protective order carries its **reserved leg allocation**. What is forbidden in every case is booking an amount the reserving action has not yet committed. **And an entry's SIGN is the EXPOSURE IT REMOVES, never the reducing order's own exposure change `[→ M4 #177]`** — the sentence above fixes the *amount* and was silent on the *direction*, and the two readings differ by a sign on every entry. Because the residual is a **subtraction** whose stated purpose is that an in-flight reduction is not re-read as fresh naked exposure, only the exposure reading closes: a group realized net **long 1.0** with an in-flight sale of 0.4 carries **+0.4**, leaving 0.6 — what is still genuinely naked; the order's own change is **−0.4**, which yields 1.4 and makes this branch **sell 1.4 against 0.6**, landing the group short — a naked leg minted by the rule that exists to prevent one. It is the same reading that makes the `PackageDelever` arithmetic close (a buy-to-reduce of `x` is `+x` of realized exposure and an entry of `+x` nets it to zero), so **under the order-change reading the two producers would need opposite signs from this one sentence** (mechanism: [mechanism: State-Machines §2]; model-checked, `docs/formal/` — and, as with the amount, no invariant phrased over this ledger can see a sign error in it). An entry booked ahead of its commitment is indistinguishable here from a real short, so a still-**neutral** package reads as short by the reserved amount and this branch **buys back exactly the exposure the reserving generation is itself about to buy**; and the overshoot reasoning that would object is phrased over quantities *computed from* this ledger, so a corrupt ledger corrupts the check too (mechanism + the amended FLAG-3 ruling: [mechanism: State-Machines §7]; model-checked, `docs/formal/`). It is tracked as a **fenced reduction generation** — coalesce / amend / cancel-replace it, never a fresh command per event `[→ Z2]`. For a determined residual, reconciliation is never a precondition for flattening, so the ≤5 s budget is not held hostage to the resolution budget.
   - **Ambiguous residual** — **any counter-leg exposure-changing order still has remaining executable quantity or an unresolved state** (`DispatchAuthorized` / `Submitted` / `SubmissionUnknown` / `Acknowledged` / **`PartiallyFilled`** / `CancelPending` / `CancelUnknown`), so the **sign *or size*** of the true net exposure is not yet fixed — each such order contributes a **possible-delta *interval*, not a point** `[→ R2b-B1]` — **derived from its REMAINING EXECUTABLE quantity and signed by its own side, so one order's interval always has zero as an endpoint and never straddles; straddling is a property of the SUM `[→ M3 slice E]`** — acting on the *observed* delta is then **wrong in at least one reachable venue state**, and `outstanding_reserved_reductions` dedups *reductions* but does **not** represent this pending exposure. The handler MUST therefore **quiesce every such order to finality first** via a **per-venue finality contract** (integration-proven, §8/§9), because a point-in-time `not-found` cannot collapse an in-flight order — a `DispatchAuthorized` send may land *after* the query, and §5.3 admits late fills — never a synthetic stable-not-found alone (the contract's four steps: [mechanism: State-Machines §2]). Only when every possible-delta interval has collapsed to a **fixed** residual does it issue the state-dependent `ExposureReduction`. If the contract **cannot complete within its deadline** (queries unavailable/rate-limited), the order stays in a **deadline-exceeded *ambiguous* state that does NOT blind-compensate** — it holds new trading, alerts the operator, and permits **only provably-safe action** — the **interval floor** where one exists, else **de-minimis** (safe here because the bot is the **sole writer**: this is an ambiguous *order*, not an ambiguous *writer* — contrast the §7.4 fence-unavailable branch, where writer identity is in doubt and `$1K`+ stays read-only). **Interval-floor rule `[→ R1c-4]`:** each unresolved counter-leg contributes a possible-delta *interval* `[a, b]`, so the group's net exposure lies in a summed interval; if that interval **does not straddle zero** (`a ≥ 0`, guaranteed net-long — or `b ≤ 0`, guaranteed net-short), the endpoint **nearest zero** is naked in *every* reachable state, so reducing exposure by **exactly that magnitude** can never overshoot into the opposite sign under any resolution. If the interval **straddles zero** (`a < 0 < b`) no nonzero compensation is safe in all states → **de-minimis only**. **The interval-floor action is a distinct, reserved fenced generation (`IntervalFloorReduction`), not a plain `ExposureReduction`** (whose precondition requires a *fixed* residual, above): the floor is **never issued twice** (**defence in depth `[→ FM-7]`** — reservation-aware sizing already prevents a second floor reaching the opposite sign, checked over the full state graph; this rule is what survives a defect in *that* mechanism, and State-Machines §2 records why the historical `[0.4, 1.0]` counterexample states what the rule protects against rather than a hazard reachable under the sizing mandated here), it **never blind-retries**, and **its own ambiguous result (timeout / partial fill) routes through this same §6.7 finality contract**. It is the **sole** exception to "no compensation before finality," and only for the reachable-state-**invariant** floor, never the uncertain part. This applies **only in the deadline-exceeded branch** (normal operation waits for finality and compensates the exact residual); the §6.4 gap budget still MUST cover the un-compensated **`max(|a|, |b|)` ceiling — the interval's *worst-magnitude* endpoint, not `|b|`**: for a net-*short* interval (`b ≤ 0`, e.g. `[−1, −0.4]`) the worst exposure is `|a| = 1`, and budgeting `|b| = 0.4` would materially underfund the naked-short gap; only *after* the nearest-zero floor executes does the residual uncertainty shrink to the interval width `(b − a)` `[→ R1d-2]` — interval-floor compensation shrinks the *realized* window, it does not loosen the conservative budget, and does not assume the ≤30 s target always succeeds. "Reconciliation is never a prerequisite for flattening" holds for a *determined* residual, **not** an ambiguous one.
   **An OVER-EXECUTED order's remaining quantity is negative, and the two consumers of that number want OPPOSITE treatments `[→ M3 slice E]`.** §5.3's ledger reports `ordered − cumulative` signed, and refuses to clamp it, because the overshoot is realized exposure and clamping it "would report a package as flat while it holds reverse exposure". That is right for the **residual**, which is the minuend this section subtracts reservations from, and **wrong for the interval**: an execution cannot be un-executed, so an over-filled order's remaining *executable* quantity is zero and its future contribution is the **point zero**. Unclamped, a buy over-filled by `x` contributes `[0, −x]` — an inverted interval handing a buy a *short* endpoint it can never reach — which widens the summed range toward straddling and turns a compensable residual into "de-minimis only". Neither reading fails loudly and both produce a plausible number, so the split is normative here rather than left to the arithmetic.
   The reduction's order type is the **single state-dependent function of §5.3** — `reduceOnly` set **only** when the order reduces an existing position on that instrument (a perp short ADL'd to zero is re-hedged with a *non*-reduce-only short, never a rejected reduce-only; a naked short perp is flattened with a reduce-only buy), all exempt from `stop-opening`. During the ambiguous-resolution window, directional risk is bounded by any **pre-placed venue-native protection** (§7.4) and by the **naked-leg-gap sizing budget over the resolution window** (§7.1), **never** by a blind compensating trade. Stop new *strategy* orders; if the resolving query is unavailable/rate-limited, hold new trading and reserve rate-limit budget for recovery — the resolving queries are `Safety` traffic on §7.6's priority ladder, and holding new trading is what frees the `Opening` band they are reserved above. Escalate via the pre-authorized ladder (§7.4), operator alerted in parallel `[→ S4, X6, Y3, Z2, R2b-B1]`. **This classifier is the *single* gate for *every* compensating trade** — one-leg-failure, ADL/liquidation (§6 step 8), kill-switch / panic-MARKET (§7.4), protection-disarm (§7.4), `PackageDelever`/`EmergencyClosePackage` (§5.3), and actuator takeover (§7.4) all route through it; **no path compensates the *uncertain part* of an ambiguous residual before the finality barrier** (only the deadline-exceeded **interval-floor generation** may compensate the reachable-state-invariant floor, §6.7) — the ADL/panic "immediate" path is the *determined* branch (no pending exposure-changing order), and a forced close *with* a still-live/partial counter-leg order is ambiguous and quiesces first. The §6.7 **finality contract is the *one canonical* boundary**: protection-disarm's sweep, the takeover's reconcile, and `PackageDelever`'s generations all reconcile through *this* contract **and its watermark**, never a weaker cancel-ack-only variant.
8. **Monitor (OMS process-manager).** Driven by **private account/ADL events**, and — via an **OMS-owned mark-risk read port over `engine/state`** (not by importing `marketdata`; the read port keeps the §3.6 hexagonal boundary) — the **perp mark** (not just polling): **liq distance is recomputed on every mark update the port surfaces (adverse-preserving, §3.4) *and* every margin/position/tier-change event** — it is a function of **mark**, which moves continuously (Bybit ticker ~100 ms; Binance `markPrice@1s`) with no account mutation, so a mark-only rally toward the short's liq price MUST trigger recompute → rebalance; a **stale mark past its §3.4 max-age (timer-detected) blocks openings and escalates open positions** — the defined §7.1 escalation: REST-mark failover, then the `T_blind` pre-authorized de-risk `[→ R1d-9]` (never a silently-frozen trigger) `[→ R2c-1]`. Also: basis divergence, funding **audit** (vs realized) and **attribution** (vs signal) kept distinct, interval-change detection. A `ForcedCloseReason` (ADL/liquidation) event fires an immediate `ExposureReduction` (§5.3) **when the residual is determined — no pending exposure-changing order on the group**; if a counter-leg order is still live/partial it routes through the §6.7 **finality barrier first** — never a next-tick reaction either way `[→ C7, C8, X2, Y3, R2b-B1]`. **The per-venue evidence deriving `ForcedCloseReason` is normative, not folklore `[→ R1d-7]`:** Bybit carries **no `closeType`** — classify from execution **`execType` (`BustTrade` = liquidation / `AdlTrade` = ADL; authoritative — carries qty + `execId`, deduping through the standard fill ledger)**, corroborated by order `createType` and position `positionStatus`/`adlRankIndicator`; Binance from the system client-ID prefixes (`autoclose-` / `adl_autoclose`); **downtime recovery sweeps Bybit `GET /v5/execution/list` (by `execType`) and Binance `GET /fapi/v1/forceOrders` (by `autoCloseType`) from the recovery cursors** (Bybit closed-pnl cannot distinguish ADL); **no cross-topic arrival order is assumed** — Bybit documents none; fills↔position joins use `seq`+symbol. Field lists + dated sources: (Profiles §1/§4).
9. **Close.** Same parallel-IOC pattern; realized PnL decomposed per leg from actual fills + settled marks; journaled + exported. On close finality the OMS invokes the idempotent `EmergencyPlanStore.Deactivate` (a terminal tombstone); **only its *persisted acknowledgement* releases the hedge-group lease or admits a successor trade**, and a crash between close and ack is recovered by **reconcile-only boot re-driving the pending `Deactivate`** (§7.5) — the lease is **never** released with a plan still active, so a closed trade leaves no plan an actuator restart could re-action, even under `Replicate`↔`Deactivate` reordering or a mid-close crash `[→ Codex]` [mechanism: State-Machines §6].
10. **Crash recovery (boot).** Reconcile-only boot rebuilds from journal ⋈ venue truth (`OrderByClientID`/`Fills`/`Positions`/`FundingLedger`); **auto-recovers known journaled client IDs**; only genuinely foreign orders or unexplained position deltas require operator clearance `[→ A3, X1]`.

## 7. Risk, custody & security (real-capital bar)

### 7.1 Sizing for survival & the margin top-up protocol `[→ C4, C5, P3, X2, R1b-1]`
Liq-distance policy is single-sourced (§5.2) and post-Oct-2025 stress-inclusive. MMR is always the live tier value (`leverageBracket`). Effective leverage 2–3× on BTC, 1.5–2× on alts. **Stress sizing budgets the naked-leg price gap + reacquisition slippage** for the unhedged window after a forced close. Report yield on full bankroll (`C_allocated`, §2.2).

**Rescue margin under *Isolated* is an active top-up, not a passive buffer `[→ R1b-1]`.** The §4.1 posture pins **Isolated** margin on both venues — so the liquidation engine sees **only the position's posted isolated margin**, *not* free wallet balance. 'Pre-funded rescue margin' is therefore capital **staged at the venue but *outside* the position**, applied by an **explicit API top-up** when liq distance breaches the rebalance threshold — **not** a wallet buffer the engine draws on automatically (that is Cross semantics, which the posture prohibits, and `auto-add-margin` is OFF precisely to stop silent pulls). Concretely:
- **Trigger:** the §5.2 `liq_distance` **rebalance** threshold (<20% BTC; tighter for alts), **recomputed via the OMS-owned mark-risk read port (adverse-preserving coalescing + `Clock`-timer staleness, §3.4/§6) on every mark update *and* every margin/position/tier-change event** — liq distance is a function of **mark**, which moves continuously with no account mutation, so the trigger MUST NOT be account-event-only (a pure rally would otherwise go undetected until liquidation); a **stale mark feed blocks openings and escalates — and the escalation is defined, not a bare verb `[→ R1d-9]`:** on a **timer-detected stale mark**, the liq-distance input **fails over to the venue's REST mark/position surface** (Binance `GET /fapi/v1/premiumIndex` mark; Bybit `GET /v5/market/tickers` `markPrice`; plus `AccountSource.MarginStatus` — available margin, maintenance, live liq price) polled at a bounded cadence from the **reserved rate-limit allocation**, so the trigger stays live on a secondary source; if **both** WS and REST mark are stale past a configured blind budget **`T_blind`** (§5.2) with an open position, a **pre-authorized de-risk executes within a bounded response time (§9)** — `PackageDelever` toward reduced notional (raising liq headroom) or `EmergencyClosePackage`, per the configured `mark_blind_action` policy, each §6.7-routed — **never an alert alone**, and never silently freezing the trigger `[→ R2c-1]`.
- **Actuator (per venue):** Binance **`POST /fapi/v1/positionMargin {type:1}`** (add isolated margin; `type:2` reduces); Bybit **`POST /v5/position/add-margin {margin:+}`** (positive adds). Both act on the isolated position directly.
- **Budget + reservation:** the top-up has a **bounded latency budget** (alert-on-miss) and a **reserved rate-limit allocation** so it is not starved by trading traffic during the very stress that triggers it — concretely, it is `Safety` traffic on §7.6's priority ladder, whose reserve is the band above `Routine`'s ceiling and whose own ceiling is capacity.
- **Every margin op is a durable target-state machine, not a fire-and-forget delta `[→ R1d-6]`.** A top-up/transfer is a **non-idempotent external write with no venue-side operation identity** (Bybit's add-margin returns only a position snapshot; Binance's `positionMargin/history` rows carry no id; only Bybit *transfers* have a client-supplied `transferId` UUID — Profiles §4), so it gets the **§5.3 crash-boundary discipline**: journal + fsync a **`MarginOp` record** (local op ID, intended delta, **before-state snapshot + venue watermark**) *before* the call; an ambiguous result (timeout, success unknown) or a crash mid-op is resolved by **`ResolveMarginOp` evidence reconciliation** — Binance: `positionMargin/history` matched on symbol + type + amount + time-window, plus the position-risk margin delta; Bybit: the **`positionIM` delta** vs the journaled before-state (the transaction-log documents **no** margin-adjustment type — never rely on it); Binance transfers: read-back `GET /sapi/v1/asset/transfer` **before any retry** (server-side `tranId` only — a naive retry can double-transfer); Bybit transfers: re-query by the client UUID (same-UUID retry is safe). **Blind delta retries are prohibited** — the dangerous direction is assuming a top-up applied when it did not, and the ladder below is robust to that by re-reading *live* state. A doubled top-up is capital-allocation drift, not naked exposure — still an incident (alert + reconcile the float), never silently absorbed. **Evidence is not causal identity, so `Ambiguous` is a first-class outcome and same-position ops are serialized `[→ Cx5-4]`:** at most **one margin op in flight per position** (serialization removes the self-inflicted confound of two same-amount candidates in one evidence window); `MarginOpStatus ∈ {Applied, NotApplied, Pending, Ambiguous}`; on **`Ambiguous`** (a coincident manual adjustment, position mutation, or duplicate same-amount history row inside the window) the op is **never delta-retried** — safety actions continue from **live** liq distance (the trigger's actual input, indifferent to attribution), **new openings are blocked**, and the staged-float ledger is reconciled by explicit accounting / operator action, a §9 case.
- **Escalation on failure:** if the top-up fails or misses its budget (rate-limit, venue lag, insufficient staged margin), the ladder **escalates to a `PackageDelever`** (§5.3 — a **perp-short-first-sequenced** both-leg reduction that **never transits through a naked short**, bounded and terminal-escalating, dropping notional/margin requirement) rather than waiting; because a lost timeout may mean the top-up actually applied, it **re-queries margin + position first** (target-state, not delta — a lost ack can never fake a restored liq distance `[→ R1d-6]`). This is deliberately **not** an `ExposureReduction` — the package is still neutral, so reducing a single leg would *create* a naked leg during the rally. A slow top-up under stress is the same failure class §7.1 warns about for spot→futures transfers, recreated one level down, so it gets a pre-authorized fallback. This is a §9 chaos case.

Rescue margin **counts against the per-venue concentration cap** (§7.2 — committed venue capital, not free headroom) and is part of `C_allocated`.

**Isolated vs Cross is a recorded trade-off, not a free win `[→ R1b-1]`.** Isolated buys **blast-radius containment** (a per-position loss cap; the spot leg is unreachable) but pays with **(a)** this active top-up dependency — an API call under stress, versus a passive wallet buffer that absorbs a rally automatically under Cross — and **(b)** an **earlier liquidation point at equal posted margin** (Cross would lend the position the whole wallet). On **Binance**, spot-safety comes from the **spot≠futures wallet split**, *not* from isolated futures margin — so there isolated-vs-cross is a pure trade-off between containment and a passive buffer; the segregation property holds either way. MVP chooses **Isolated** for containment and accepts the top-up dependency with the fallback above.

### 7.2 Custody & settlement — **on-exchange for MVP** `[→ S1]`
- **Decision:** on-exchange collateral and on-exchange spot, deliberately, at **small size**, in **isolated per-venue subaccounts** with **hard collateral caps** and per-venue concentration caps (≤~20–30% of bankroll/venue); USDT/USDC-only margin. A conscious, documented acceptance of exchange-custody risk to ship — not an oversight.
- **Sub-account availability is a verify-item, not an assumption `[→ R1c-3]`.** Isolated per-venue subaccounts here — *and* the Binance master-key exchange-side `Fence` (§7.4) — presuppose the account **has** sub-accounts, historically a **tier-gated** Binance feature (corporate/VIP). **Confirm sub-account availability for the actual account before relying on it.** If unavailable: fall back to a **single account per venue** with the **per-venue concentration caps carrying more of the containment**, and **signer isolation as the sole `Fence`** (§7.4, now the primary mechanism anyway) — the segregated **spot-wallet ≠ futures-wallet** posture (§4.1) still holds on a single Binance account, so the spot-seizure safety property is not lost; only the exchange-side fence backup and the per-subaccount cap granularity are.
- **Why not OES yet:** no single OES rail spans Binance + Bybit (Binance → Ceffu MirrorX; Bybit → Copper ClearLoop / Fireblocks). Crossing rails needs two custodians — the documented scale-up path, gated on size.
- **OES is necessary-but-not-sufficient anyway:** it removes custody/counterparty risk but not exchange-margin/mark-price risk (Oct-2025 liquidated OES users too). Keep liq-distance buffers + mark-price sanity checks regardless.
- **Spot leg (cash-and-carry):** held on-exchange in MVP under withdrawal-disabled keys (§7.3); cold/hot split + qualified custodian documented as the same scale-up step. `treasury` owns balances, the concentration cap, inventory-drift monitor, and the rescue-margin float — which **counts toward the per-venue concentration cap** (it is capital committed at the venue, not free headroom) `[→ R1]`.

### 7.3 API-key security & blast radius `[→ S2, X10]`
- Trade-enabled keys have **withdrawal permission disabled**; separate read-only monitoring keys; keys in Vault/KMS, per-subaccount, IP-allowlisted, rotation policy.
- **Realistic blast radius = the entire funded subaccount.** A compromised trade key from an allowed host can bleed the subaccount via deliberately adverse trades even with withdrawals disabled; an IP allowlist does not protect a compromised allowed host, and software risk caps are void if the bot/signer is compromised `[→ X10]`. Therefore: hard-cap collateral per isolated subaccount; disable internal transfers + every nonessential permission; **isolate the order-signer from the trading process**, restrict its egress and the order schemas it will sign; run an **independent read-only watcher** enforcing venue/account-level exposure limits out of band.
- **The emergency `Fence` credential is a distinct, higher-privilege key — and the reason signer isolation is *preferred* `[→ R1b-2, R2b-3, R1c-2]`.** An **exchange-side** fence credential *manages keys*, so it is **hotter than any trade key**, and on Bybit hotter still: the venue's permission model **forces** the `update-sub-api`/`delete-sub-api` caller to **hold a transfer/withdrawal-class authority** (`Account Transfer` / `Sub Member Transfer` / `Withdrawal`) — so the credential is **not, and cannot be, "key-disable-only"**; it inherently *can move money* even though the actuator only ever *uses* it to disable keys. That is an honest blast-radius fact, not a scope we can assert away: where the exchange-side path is used the spec MUST **grant the narrowest qualifying authority — `Sub Member Transfer`, never `Withdrawal`** — disable every other permission, isolate it on the actuator host with its own egress limits, and **never** make it the trade key or the watcher's read-only key. **Because that money-moving grant is unavoidable for the exchange-side path, signer isolation (§7.4) is the *primary* `Fence` on both venues** — it needs **no *additional* key-management/transfer-class credential** (it signs with the trade key, so it is within the §7.3 subaccount blast radius, but never holds the hotter money-moving fence key), is **account-tier-independent**, and is under the operator's own control; exchange-side disable is the **backup**. **The actuator's execution authority is its *own independent trade credential* (never the bot's signer) `[→ R1d-4]`** — a second trade-class key inside this same blast-radius analysis: subaccount-capped, IP-allowlisted to the actuator host, withdrawal-disabled, and **never** the fence credential or the watcher's read-only key; its validity is continuously health-checked (`ActuatorReady`, §7.4). This blast radius is part of the analysis, not outside it.
- **Operator control-plane security — part of the real-capital boundary, not frontend polish `[→ R2b-6]`.** The operator API (§3.2) can trip the kill-switch, edit emergency policy (loss bounds / ladder), promote capital tiers, and — with the actuator fence (§7.4) — disable venue credentials, so it is a **privileged surface** and MUST enforce: **mutual-TLS or an authenticated + authorized operator identity** (no anonymous or localhost-implicit trust); **least-privilege authorization per action** (trip-kill vs edit-policy vs promote-tier vs fence are distinct grants); **replay protection** (nonce + signed timestamp on every mutating call); **CSRF protection** for the browser-dashboard flows; a **network-exposure policy** — bound to a private network / VPN / IP-allowlist, **never public-internet-exposed**; and an **immutable per-actor audit** of every control action (who / what / when, appended to the tamper-evident log, §5.1). This is the §7.4 approval kernel enforced at the *transport*, so a stolen dashboard session cannot do what a stolen key cannot.

### 7.4 Kill-switch modes & pre-authorized escalation `[→ A5, S4, X6, Y3]`
- Modes: **(a) stop-opening**, **(b) flatten-if-feasible** (**`EmergencyClosePackage`** for a neutral package + `ExposureReduction` for a naked residual, §5.3; respects slippage cap), **(c) hard-halt-and-alert**. `KillSwitchMode` is a typed VO owned by `risk`.
- **Policy is armed under the approval kernel before trading; it does NOT gate emergency *execution*.** The approval kernel (`platform/foureyes`) is **solo-honest by default** for the MVP: policy edits (loss bounds / escalation params) require a **time-delayed self-approval** — a mandatory cool-off before the change takes effect — plus an **out-of-band confirmation channel**. True two-person four-eyes is the documented scale-up, not an MVP assumption; a control that presumes a colleague who doesn't exist has no integrity value `[→ R1-meta]`. Whichever mode is configured arms/edits emergency *policy* **before** exposure; once exposure exists, pre-authorized loss bounds execute **automatically** — a 03:00 naked residual cannot wait for a human `[→ X6]`. Ladder (each step pre-authorized): stop openings → **concurrently { reconcile-to-truth ∥ bounded `ExposureReduction` }** (for a **determined** residual, reconciliation may refine it but is **never** a prerequisite for flattening; an **ambiguous** residual — **any counter-leg order with remaining executable quantity** — is first quiesced to finality, §6.7/§5.3 `[→ R2b-B1]`) → **pre-authorized panic-MARKET / venue-native stop** (**which does *not* bypass the §6.7 finality barrier for an ambiguous residual**) → revoke key or allowlist. Operator alerting runs in parallel, never as the terminal action.
- **Actuator authority & failure domain — mandatory `[→ Y3, Z3, R1-F2, Codex]`.** Three components across separate failure domains: (i) the in-process OMS runs `ExposureReduction` on the hot path; (ii) a **read-only watcher** (§7.3) — observes, alerts, trips policy; no trading key; (iii) an **emergency actuator** that MUST act after the bot host *and its local journal* die. Because the allocation cap lives in that journal, the actuator relies on **host-independent coverage** (next bullet), never on selling from **coarse venue balances** (forbidden — it can hit unrelated inventory). A **replicated `EmergencyPlan`** — carrying, for **both legs**, everything the takeover needs *without* the host-local journal — is pushed to the actuator **before exposure opens** (actuator **ack required before the entry submits**), with watcher→actuator auth and independent key/IP; later protection/reduction generations are replicated **as they are created — asynchronously: generation replication is a freshness optimization, never the coverage mechanism `[→ R1d-5]`. Coverage-completeness MUST NOT depend on the latest generation having replicated:** every order the bot ever submits for a trade MUST carry a client/algo ID **deterministically derivable from the entry-generation plan's replicated order namespace/prefix**, so a takeover holding only an older generation still discovers **every** bot-owned order and execution by **venue-side enumeration** (`ProtectionGateway.EnumerateResting` for resting orders, and the **`HistoricalOrders` port** — normal *and* algo history surfaces, server↔client ID mapping, end watermark — for anything already filled/cancelled; resting-only enumeration cannot associate a *filled* later-generation order `[→ Cx5-3]`) **plus the §6.7 executions sweep from the replicated cursors** (an older cursor widens the sweep; it never narrows coverage **within venue retention**) — a §9 case. **The completeness claim is retention-bounded and the plan closes that bound `[→ Cx5-3]`:** venue history expires (Binance ≈90-day order/algo history, some unfilled-cancelled orders purged in days, ≈6-month trade history; no server-side prefix filter — prefix matching is client-side over enumerated pages; Profiles §4), so the plan MUST also receive a **periodic acknowledged checkpoint generation** (cadence a config param, e.g. daily) carrying the accumulated server-order-ID↔client-ID map + fresh cursors — bounding the un-checkpointed discovery window to days, far inside the shortest retention; **discovery never depends on expired venue history**. Two deliberate asymmetries: **handle-bearing** generations (new order IDs minted on the hot path) replicate async under this completeness guarantee — requiring a replica ack before every external write was considered and **rejected**, because it would couple an *emergency reduction* to plan-store availability (the §6-step-9 hold-the-lease fail-safe is correct for a *close*, where waiting is safe; blocking a reduction is not); **policy-changing** generations (loss/slippage bounds, fencing-generation edits — approval-kernel operations at human timescale) DO require the replica ack **before taking effect**, so the actuator can never hold *looser* bounds than the bot is trading under. The plan's content (the full handle set), generation semantics, the actuator's reconcile-only boot, and `Deactivate`-tombstone behavior: [mechanism: State-Machines §6]. Without the plan's handles the actuator can't associate fills once the journal dies, and coarse-balance fallback is forbidden `[→ Codex]`.
  - **Takeover is a fence-first protocol, not a fire-and-forget sell `[→ Codex]`.** The actuator is a *second writer*, so before it trades it MUST **fence the bot's trading credential/signer** (via the venue-specific **`Fence` capability** defined below) — single-writer is preserved by *transferring* the writer, never by running two. Fencing stops *new* submissions but does **not** cancel orders the venue already holds, so the takeover then **quiesces every bot-owned exposure-changing order to finality across both product families** — entries, reductions, and **all resting protection**, which are **separate cancel surfaces** — a **finality barrier `[→ Codex]`**. Skipping it re-creates the exact hazard: an armed stop fires *after* the reduction and leaves a naked leg. Only after that barrier does it **reconcile executions/positions via the §6.7 finality contract (same watermark)** and act on the reconciled state — **the terminal action is state-dependent, exactly branch 1's verb selection `[→ R1d-1]`:** a reconciled **fixed residual** → the state-dependent `ExposureReduction`; a reconciled **neutral / near-neutral package** → a **two-leg `EmergencyClosePackage`-equivalent close within the plan's loss/slippage bounds** — an `ExposureReduction` would **no-op at delta≈0**, and the quiesce barrier has just **cancelled all resting protection**, so leaving a neutral package open would leave it **unprotected and unmanaged** (no margin top-up, no liq monitoring, no ADL response — the host is dead). **The takeover's terminal state is *flat*** — and **completion is evidence-gated, never issuance-gated `[→ Cx5-1]`:** it reports complete only when every close/reduction order has reached **§6.7 finality** and post-close reconciliation proves **zero per-leg allocations + final order surfaces** (exactly the evidence gating the plan-lifecycle tombstone, SM §6 — one gate, no gap); if the close **cannot execute within the plan's loss/slippage bounds** (a zero-fill IOC in a gapping market), it enters a **held incident state — fence latched, plan active, operator escalated — never a false "flat", never an unbounded dump**; re-attempts consume the plan's **replicated close-attempt budget (`max_close_attempts` + total `T_close`, plan fields — SM §6)**, and **exhaustion of either transitions to the held incident unconditionally** — the aggregate bound is a consumable budget, never a per-attempt adjective `[→ Cx5-1]`. **The takeover runs only with its execution capability `[→ Cx6-2]`:** `ActuatorReady` (the `Fence` bullet's monitored dimension) gates the protocol end-to-end, not just the branch-2 hand-off — the **watchdog activation path latches only with it confirmed** (fencing the bot while the actuator cannot itself trade would transfer the writer to **nobody** — the same rationale that makes signing-down-without-`ActuatorReady` branch 3; with it failed the latch attempt times out to the fence-unavailable floor below), **every actuator venue write requires execution readiness — the quiesce *cancels* included** (they are venue writes on the actuator's own credential), and a **mid-takeover `ActuatorReady` loss enters the held incident state** (fence latched, plan active, operator escalated — never a silently stalled takeover presumed to be executing; SM §4). **Engagement is a durable obligation, not a delivered message `[→ FM-3]`:** an actuator that boots — or stands back down — into an incident whose §3 branch is **`TakeoverTransfer`** with an **active plan and no latched epoch** MUST **re-attempt the fence latch**, keying off that durable branch record rather than any received hand-off signal (so a lost hand-off and a crashed actuator are the same case, and the re-attempt is the un-latched sibling of the reconcile-only boot's latched re-entry, SM §4/§6); the re-attempt is bounded exactly as the watchdog path is — a `T_fence` miss routes it to the fence-unavailable floor below, and `ActuatorReady` gating the latch means a failed-ready re-attempt lands on that floor rather than never happening. Without this rule the branch transfers the writer to **nobody**: the one-way rule forbids a restored signer from aborting a started branch `[→ R1d-F6]` — the bar on the bot is scoped to the *branch*, not to the dimension that failed — so the healthy bot stays barred for the whole branch while the un-engaged actuator waits on a hand-off that already happened, leaving **unprotected exposure with both writers alive and idle, indefinitely** (model-checked counterexample: `docs/formal/`; the automated-convergence property had been certifying that stall as "resolved"). **Completion evidence terminalizes the trade `[→ FM-1]`:** once the durable `ActuatedFlat` record exists (equally: once any flatten of the trade reaches §6.7 finality with flat evidence), the trade **re-admits no exposure-opening order** — its plan lifecycle may only proceed to the §6-step-9 tombstone (re-driven across actuator restarts, SM §6), and fresh exposure is admitted **solely as a successor trade through the hedge-group lease**, which only that tombstone releases; operator clearance (SM §3) restores trading for successors, never for the terminated `TradeID`. Without this rule the composition breaks: R1d-F6 clearance requires flat/reconciled but *not* the tombstone, so a clearance inside the `ActuatedFlat`→`Deactivate` crash window would let the bot re-open exposure under the still-`Active` plan — and the stale re-driven tombstone would then revoke host-independent coverage under live exposure (model-checked counterexample: `docs/formal/`, NC4). The tombstone-as-clearance-precondition alternative was **rejected** — it would couple operator clearance to plan-store availability, the same coupling R1d-5 rejects for hot-path generation acks. Any resulting one-leg residue routes back through the §6.7 classifier; it reduces/closes the **reconciled live** state, *not* the pre-allocated qty (which may be stale: an entry leg can still have filled, or a partial reduction already run). A bot that recovers mid-takeover finds itself fenced and stays in reconcile-only until an operator clears it. `Place` isn't a venue idempotency key (§5.3), so the fence — not "idempotent command IDs" — is what prevents a double-reduce. Protocol phases + per-surface cancel mechanics: [mechanism: State-Machines §4]. Network-partition, late-fill-after-takeover, partial-fill, and bot-recovery-during-takeover are §9 cases.
  - **The `Fence` capability is per-venue, verify-and-pin, with a failure branch `[→ R1b-2, R2b-3, R1c-2, R1c-3, R2c-2]`.** Fencing = guaranteeing single-writer by making the bot unable to trade; it has **two mechanisms**, and **at least one MUST be available and propagation-tested per venue before that venue reaches `$1K`**. **Signer isolation is the *primary* mechanism on both venues** (the *fence action* is a local revoke/starve needing **no venue credential or venue call** — the signer of course holds the *trade* credential, but no additional key-management/transfer-class credential `[→ R1d-4]`; no money-moving blast radius, account-tier-independent, §7.3); exchange-side disable is the **backup**:
    1. **Signer isolation (primary, §7.3):** the order-signer runs in **its own trust boundary the actuator can fence independently of the bot host**, reached by the bot over an **authenticated signing protocol**, with a **health test** (feeding `FenceReady`) and a defined **revoke/starve** mechanism. A signer that merely lived on — and died with — the bot host would **not** be re-fenceable when the bot *restarts* mid-takeover, so **co-location with the bot is not signer isolation**. It holds the **trade** credential (within the §7.3 subaccount blast radius) but **no additional key-management/transfer-class credential** and has **no account-tier dependency** — that, plus the actuator's independent control, is why it is preferred over the money-moving exchange-side path. Deployment shapes + the signing-protocol internals: [mechanism: State-Machines §4].
    2. **Exchange-side credential disable (backup):** **Bybit** sub-key modify/delete (set read-only / drop trade permission / lock IP) — but the caller **must hold a transfer/withdrawal-class authority**: a money-moving credential, so grant the **narrowest — `Sub Member Transfer`, never `Withdrawal`** (§7.3). **Binance** has **no REST way to disable a *regular* account's own key** (UI + 2FA only); it is API-automatable **only if the bot runs on a *sub-account*** and the actuator holds a **master key** with sub-account management — **which presupposes the account actually *has* sub-accounts, a tier-gated Binance feature that MUST be confirmed for the real account (§7.2 verify-item); if sub-accounts are unavailable the Binance exchange-side path does not exist and signer isolation is the sole fence** `[→ R1c-3]`. Endpoints + dated verification sources: (Profiles §4).
    **Tiering consequence:** because the primary mechanism (signer isolation) needs no venue credential *for the fence action* `[→ R1d-4]`, a working fence **binds at `$1K` on every venue**; the exchange-side path is a per-venue *backup* used only where it is available *and* verified (a Binance regular/sub-less account has none). The `Fence` MUST define **ack semantics + a propagation test** (prove the bot can no longer write) before it is trusted.
    **`FenceReady` — a continuously-monitored health gate, not a one-time preflight `[→ R2c-2]`:** a successful provisioning-time propagation test is **not** an availability guarantee during a later incident, so the primary `Fence`'s health (`FenceGateway.FenceStatus`, §4) is **polled continuously**. **`FenceReady` is a differentiated *state*, not one Boolean `[→ Cx4-5, Codex]`** — it tracks **signing readiness**, **primary-revoke readiness**, **backup-fence readiness** (exchange-side), and **actuator execution readiness (`ActuatorReady`) `[→ R1d-4]`**: the takeover's premise is that the actuator *can itself trade*, so its **own independent trade credential** (validity propagation-tested), venue reachability from its IP, and plan-store integrity are a **continuously monitored health input, not an incident-time discovery** — the same argument that makes the fence a health gate. (**Durably-fenced** — the **latched, monotonic revoke *epoch*** that `VerifyFence` validates, **not** a point-in-time snapshot — is an ***incident/takeover state*, not a normal-operation health dimension** `[→ R1d-4]`: nothing is latched while the bot is the healthy writer; its epoch semantics are owned by the takeover protocol, SM §4.) Loss of any dimension **except a backup-only loss** triggers an explicit **`FenceReadyLost` arbitration** that first **blocks `OpenTrade`** and **supersedes any active `PackageDelever` generation** (quiescing its reserved leg to §6.7 finality first), then **branches on *which* dimension failed** (a **backup-fence-readiness-only** loss — signing, primary revoke, and `ActuatorReady` intact — instead enters **`FenceDegraded`**: alert + bounded repair posture, **openings continue** because the `$1K` premise — ≥1 working, propagation-tested fence per venue — still holds via the primary; any *further* dimension loss enters the full arbitration `[→ R1d-F5]`) — because the naïve "bot winds down" path is **impossible exactly when the signer itself failed** (the bot is alive but cannot sign `EmergencyClosePackage`/`ExposureReduction`, since signing readiness feeds `FenceReady`): **(1) revoke-control lost, signing still works** → **bot-driven wind-down** through the defined verbs, each routed through the §6.7 classifier — this **overrides a configured `hard-halt-and-alert`** (halting while the fence is degrading is worse than a controlled exit — an explicit priority choice, not an arbitration conflict); **(2) signing unavailable, a durable revoke is latchable, *and* `ActuatorReady` is confirmed `[→ R1d-4]`** → the actuator **latches a durable, monotonic takeover epoch** that the signer **MUST honor across restart until explicit operator clearance** (a **point-in-time `VerifyFence` alone is insufficient**; a signer merely unreachable *without* a durable latch is branch 3) — only then does execution **transfer to the actuator takeover** (a takeover hand-off to an actuator that **cannot itself trade** would transfer the writer to nobody — signing unavailable with `ActuatorReady` failed is **branch 3**); **(3) fence state uncertain** (no durable revoke latch achievable, and signing cannot be confirmed — or the actuator's execution readiness cannot be) → **bounded pre-armed protection + operator manual kill only**, never a compensating trade *or an un-latched takeover* that could create **two writers**. **The arbitration is one-way per incident `[→ R1d-F6]`:** a restored dimension **never aborts a started branch** — a started wind-down runs to completion; **nor a *pending* one `[→ FM-4]`: the arbitration branches on the *recorded* failure — which dimension failed is snapshotted when the loss is detected — so a dimension that repairs inside the window between detection and branch selection does not cancel the arbitration**, and the incident still exits through its branch's terminal outcome + clearance (the health-driven return to `FenceReady` remains available **from `FenceDegraded` only**, SM §3). The 2-vs-3 choice still reads **live** capability, deliberately: "a durable revoke is latchable *and* `ActuatorReady` is confirmed" is a claim about whether the actuator can act **now**, and handing off to one that cannot would transfer the writer to nobody. Without the recorded-failure rule the branch guards all re-read live health, so a self-healed loss disables every one of them at once and the incident **strands in un-arbitrated `FenceReadyLost` — openings blocked, exposure open, no branch, and no automated exit** (model-checked counterexample: `docs/formal/`; found by the independent round-2 review of the formal model); branch changes may only **escalate** — **1→2 iff a durable latch is achievable *and* `ActuatorReady` holds, else 1→3** when signing fails mid-wind-down `[→ Cx5-2]`; 3→2 once a durable latch becomes achievable (with `ActuatorReady` confirmed); return to normal operation requires the branch's terminal outcome (**flat / reconciled**), **explicit operator clearance, and a fresh `VerifyFence` propagation test** — never health-flap re-entry. Dimension definitions, branch guards, verb selection, and epoch mechanics: [mechanism: State-Machines §3].
    Each branch carries its own §9 target — an **automated first-safe-action RTO** (block openings + confirm pre-armed protection) that always holds, a **composite wind-down / takeover RTO** for branches 1–2 (which may include a §6.7 finality step), and a **manual-kill escalation *target*** for branch 3 (not an automated RTO). The honest guarantee is a **bounded first-safe-action, then wind-down or takeover within the composite RTO** — *not* "never outlives its fence": an *ambiguous* residual still quiesces to finality first (which can delay closure), so what is guaranteed is "**exposure is reduced toward flat within the RTO, never knowingly grown while `FenceReady` is lost, and never left with two writers**." This closes the gap where "`$1K` requires a working fence" (§1.1) otherwise met only an incident-time **read-only + manual** fallback: exposure is wound down (or handed to the actuator) *before* an incident, rather than discovered fence-dead at host-death time.
    **Failure branch — fence unavailable at incident time:** fence-first is otherwise absolute (never two writers), so a *down* fence while the bot host is *also* dead would **deadlock the actuator while naked** — the precise failure the actuator exists to prevent. The resolution differs by tier, because **interval-floor safety proves only that a reduction cannot *overshoot the sign*, not that the actuator is the *sole writer*** — an unfenced actuator trade can still collide with a recovering bot:
    - **At `$1K`+ (single-writer guaranteed):** if **no durable fence latch** can be established (neither a latched revoke epoch nor a validated `VerifyFence`), the actuator stays **read-only** — **wait `T_fence` → on miss, alert + operator manual kill (venue UI/2FA) *only*; it does NOT automatically trade**, because a transient double-write is *not* acceptable where single-writer is promised. The prior `FenceReady` wind-down (run while the bot was alive) is what keeps a position from reaching this point un-fenced; read-only + manual covers the residual.
    - **In the pre-`$1K` canary only (§12):** *if a minimal actuator already exists during the canary* (its construction is an explicitly **canary-concurrent workstream**, §12 `[→ R1d-8]`; before it exists, canary host-death coverage is the **signed manual-recovery bound**, §12), the actuator MAY act on an **interval-floor / de-minimis residual** after `T_fence` — but this is the **separately-signed accepted bounded loss of the canary**, which **explicitly does *not* claim single-writer safety** (the fence/takeover is not yet §9-proven — possibly not yet built); it is never presented as a `$1K`+ guarantee.
    Fence-unavailable and fence-race are §9 cases.
    **Blast radius:** the **exchange-side** fencing credential (Bybit transfer/withdrawal-class key; Binance master sub-account-management key) is **hotter than the trade key it revokes** — it manages keys, and on Bybit **can move money** (the transfer-class grant is unavoidable, §7.3) — so it is added to the §7.3 blast-radius analysis, **isolated on the actuator host** with its own egress limits, **granted the narrowest qualifying authority (`Sub Member Transfer`, never `Withdrawal`) and no other permission**, and **never** the same credential as the trade key or the watcher's read-only key. **Signer isolation, the primary mechanism, carries none of this** — another reason it is preferred.
  - **Tiering (§1.1):** a *minimal single-node* actuator with the fence-first protocol above + a plan **integrity check** is the **`$1K` requirement wherever a venue leg lacks atomic attach** (always the Binance perp; either spot leg if not attachable) — the executor cannot be deferred, or host death is uncovered; **`$10K+` hardens it** (signed/versioned plan store, reserved capacity, multi-node replication, and signer isolation as general blast-radius hardening — noting signer isolation is **already pulled to `$1K`** as the `Fence` on any venue lacking exchange-side fencing, per the `Fence` bullet above). The watchdog escalates (i)→(iii) on host silence. **The host-silence threshold bounds the graceful-shutdown budget, and nothing in this spec previously joined those two numbers.** A process's **total stop budget** — the sum of its §3.2 phase teardown allotments — MUST be **strictly less than** the host-silence threshold, and a wiring that violates it MUST be **refused at startup**, not discovered during a deployment. At or above the threshold an **ordinary restart is indistinguishable from a dead host**: the watchdog escalates, the actuator fences the bot's signer mid-flush and latches a takeover epoch, and the process that comes back up finds itself fenced and — per this section — stays in reconcile-only until an operator clears it. A routine deployment becomes an operator-cleared incident, and the cause is a sum of durations in a wiring file that nothing was adding up. The bound is **allotted and accounted for, not enforced mid-shutdown** — the enforcement it lacks is the operator's second interrupt, and that is the correct side to err on: **host death is a covered state** (it is what this actuator exists for) while a process wedged in shutdown is **not**, because the watchdog reads liveness, not progress. A **false-positive fire that engaged nothing** — no epoch latched, no arbitration branch started, bot verified alive — is **operator-dismissed as an alert**, never "cleared": the branch-exit preconditions (flat/reconciled + clearance + fresh propagation test) are scoped to a **started** branch `[→ FM-2]` (SM §4; without this rule, acknowledging a false alarm would demand flattening a healthy trade — found by model-checking the incident-resolution liveness claim, `docs/formal/`).
  - **The off-host actuator is a bounded distributed-systems subproject — treat it as one `[→ R1-meta, Codex]`.** Three convergence rounds each surfaced a deeper takeover requirement (fence-first → reduce the *reconciled residual* → quiesce *all* resting orders to finality → replicate *full* recovery handles). The spec fixes the **invariants** above; the protocol itself MUST be **designed, prototyped, and chaos-tested as its own workstream** (host-death mid-`DisarmPending`, mid-reduction, partition, late-fill), not assumed correct from prose. Because building that before the *first* dollar is real cost, the **recommended de-risking path (§12)** is to go live first at **sub-`$1K` size** on the venue with the best venue-native attach coverage (Bybit perp attaches atomically), where a worst-case naked-window loss is de-minimis, **build + chaos-test the takeover protocol during that phase**, and promote to `$1K`/`$10K` once it passes — rather than gating the first live trade on a finished distributed protocol.
- **Host-independent coverage across the exposure-opening transition `[→ Z3, R1-F2, R2-#4, Codex]`.** Exposure begins the instant an entry leg fills — a *separate* venue op from any follow-on protective order, so it cannot share the fill's journal transaction. **Venue-native attached protection reduces the window** where the venue supports it. The attach is submitted atomically with the entry, but **acceptance is async — the fill *and* the armed protection are confirmed on the private WS, not the HTTP response** `[→ R2b-B2]`. Atomic attach is **not universal** — Binance USDⓈ-M has **none** — and whether a **spot IOC** can carry an attached bracket is **doc-silent on both venues → an integration-test item, not prose certainty**; per-venue attach facts: (Profiles §1/§3/§4). **Assume the spot IOC leg is unprotected until an integration test proves otherwise.** So the **two-leg pre-armed `EmergencyPlan` actuator is the universal host-death backstop on both venues, mandatory (`$1K`) for any leg lacking *verified* atomic attach**, armed **before** entry submission and covering **whichever leg fills first**. A live (non-host-death) protective order **reserves** the leg allocation, so a hot-path `ExposureReduction` **amends / cancel-replaces that same fenced protective order** rather than duplicating it. The residual first-fill→ack window is minimized, bounded, and a §9 acceptance case.
- **Protective-order disarm — the other half of the lifecycle `[→ R1-F2, Codex]`.** Entry-time leg-level protection exists only to bound the first-fill→hedge-complete window. **Once both legs are filled and the package is net-delta-neutral, an armed leg-level stop is no longer protection — it is a naked-leg generator** (a benign wick through the spot stop-sell leaves you naked short). Disarm is a **fenced state machine `Armed → DisarmPending → Disarmed`**, not a fire-and-forget cancel — a stop can trigger *during* cancellation, and §5.3's post-cancel-late-fill rule applies — completing only through the **§6.7 finality contract** (not a cancel-ack alone); partial-execution, reclassification, and reservation mechanics: [mechanism: State-Machines §5]. Ongoing protection is then package-level (the §6 monitor + this ladder), not leg-level. Absent an atomic package-level conversion, the acceptance claim is a **measurable bound on detect→re-neutralize**, not "a wick can never create a naked leg" — a §9 case.
- **Out-of-band trip caveat:** pulling the IP allowlist can also remove the connectivity you need to flatten — prefer venue-native stops and permission reduction; sequence any connectivity kill last.

### 7.5 Reconcile-only boot `[→ A3, D2, X1]`
On every cold start / kill-switch toggle / extended control-lane gap, `oms` runs a reconcile-only boot phase (`platform/boot`): signal + new execution disabled while state is rebuilt from the **write-ahead journal joined to venue truth** (`OrderByClientID`, `Fills`, `Positions`, `FundingLedger`). Known journaled client IDs are **auto-recovered**; only foreign orders or unexplained position deltas **alert for operator clearance** (they are not auto-corrected). The net-delta invariant is asserted before trading resumes. A journaled **`DeactivationPending`** (a close that had not confirmed its `EmergencyPlanStore.Deactivate`) is **re-driven to acknowledgement (idempotent, bounded backoff, alert) before its hedge-group lease is released** — a closed trade never leaves an active plan behind `[→ Codex]`. A journaled **in-flight `MarginOp`** (§7.1) is likewise **resolved by its evidence contract (`ResolveMarginOp` — history match / `positionIM` delta / transfer-id read-back) — never re-fired blind** `[→ R1d-6]`; an **`Ambiguous`** outcome blocks **new openings** (not safety actions, which read live state) until the staged-float ledger is explicitly reconciled `[→ Cx5-4]`. The **account & margin-mode posture (§4.1) is likewise asserted before trading resumes** — wrong margin mode, spot-as-collateral, enabled spot borrow, Portfolio/Unified margin, **a Hedge position mode, or configured leverage off the pin** is a **refuse-to-trade** condition, not a warning `[→ R1-F1, R2-#2, R2b-5]`. Posture is **not assumed to persist from boot** — it is re-verified before every trade (within a max-age TTL, §6.3) and on posture-changing account events *where the venue emits them*; because **position-mode changes emit no event**, the pre-trade REST re-verify is the backstop, never event-presence `[→ Codex, R1b-5, R2b-5]`.

**These preconditions do not all clear the same way, and the distinction is normative.** This section gives every one of them the same verb — *asserted before trading resumes* — while stating, in the same breath, two kinds that behave differently. Some are **self-clearing**: a journaled `MarginOp` resolves through its evidence contract, and a posture check that failed because the venue was unreachable may legitimately pass on the next attempt — a fresh report lifts it. Others **latch**: a foreign order and an unexplained position delta *alert for operator clearance* and are *not* auto-corrected, and a bot that recovered mid-takeover stays in reconcile-only until an operator clears it (§7.4). A **latched** precondition MUST NOT be lifted by a re-run of its own check — only by explicit operator clearance — and **clearance returns it to *unreported*, never to *passed*: clearance restores the ability to pass, not the pass itself**, so the check still has to run and succeed afterwards. A checklist that treated all of them uniformly would let a precondition that failed and then succeeded on its own retry re-admit trading, which is precisely the **"never health-flap re-entry"** §7.4 forbids for the fence, arriving through this section's door.

**Reconcile-only is a *posture*, not a boot stage.** This section names it as a phase of boot, but every escalation path in §7.4 puts an *already-running* process into it — a bot that recovers mid-takeover "stays in reconcile-only until an operator clears it", and the `FenceReadyLost` arbitration blocks openings on a process that was trading a moment earlier. What a process is permitted to do at a venue is therefore a **state it can occupy at any time**, on a ladder of four rungs: **halted** (no venue write of any kind) → **reconcile-only** (reads and reconciliation, no execution) → **stop-opening** (safety execution permitted, new exposure withheld — §7.4's mode (a)) → **trading**. Two properties are normative, and both are the default-deny direction §3.6 rule 4 argues for. The **zero value is the most restrictive**: a posture nobody populated permits nothing, because the alternative reads an unconfigured process as cleared to trade. And a process's posture is the **weakest of the postures its *required* gates yielded** — reduced over the gates that were **required**, not over the ones that happened to report — with **halted as the identity of that reduction**, so a boot that checked nothing refuses everything. Seeding the fold at *trading* instead (the natural way to write a minimum) makes **"nothing was checked" and "everything passed" the same answer** — the same defect this section's latching rule closes from the other side, arriving through the arithmetic.

**The replay is a rebuild THROUGH the write path, and its chain is verified per record `[→ M3 slice F1]`.** State is rebuilt by walking the journal in sequence order and applying each record through the same journal-then-apply write path the live system uses, so the recovered projection can only reach states a live process could have produced — §5.1's OCC version advances exactly as it did the first time, SM §1's edge set is checked on every replayed transition, and a log recording an impossible history is **refused rather than installed**. A record is verified **before** it is applied, not in a pass of its own: verify-then-replay reads the log twice and leaves a window between them, and replay-then-verify rebuilds state from records it is about to be told to distrust. Verification is three claims and each fails differently — the sequence is **dense from 1** (a primary key is unique and not contiguous, so a removed record leaves every remaining link verifying against its own predecessor, and a dropped *prefix* re-anchored to the genesis seed is caught by nothing else), each record's stored digest equals what its **typed columns** rehash to (never a stored preimage, which would verify its own output), and each `prev_hash` names its predecessor. The tamper-evidence has a **stated limit**: a chain proves nothing about records that were never seen, so **truncation at the tail is undetectable** without an independently durable head, which this milestone does not build. A **duplicate delivery is not a corrupt history** — §5.3 puts the same execution on two streams, so a state record restating the state an order is already in is a legitimate no-op and MUST be counted rather than refused. What the replay does **not** rebuild is cumulative executed quantity: no fill is journaled, so every replayed record carries zero, and after this phase an order's **state** is authoritative while its executed **quantity** is not yet a claim at all — which is why the venue join and the net-delta assertion are separate preconditions from this one, and why nothing may be sized from a residual until they have run.

**A journal that will not verify HALTS and LATCHES, and it is the one precondition that needs both `[→ M3 slice F1]`.** This section's preconditions vary on two independent axes — how restrictive the refusal is, and whether a re-run of the check may lift it — and treating them as one ladder loses exactly one case. Reporting a broken chain as an ordinary failure makes it **freely re-reportable**, so a replay re-run over bytes that cannot change could re-admit trading with nobody having looked: §7.4's *"never health-flap re-entry"*, arriving through a check whose retry is deterministic. Reporting it as an ordinary operator-clearance matter latches it but leaves the process in **reconcile-only** — which permits the reconciliation writes **computed from that same log**. That is the unsafe reading, and the reason is a claim this section makes elsewhere without qualification: a reconciliation action is exposure-neutral *by construction* because it re-drives what already happened, and what it re-drives is read from the journal. The `DeactivationPending` re-drive fires an idempotent `Deactivate`, and that call is **terminal with no reactivation**: after its ack, any `Replicate` for that `TradeID` is rejected and `ListActive` never returns it. A plan tombstoned for a trade that is in fact still open therefore leaves that position **permanently without a takeover path** — an actuator enumerating plans after host death finds none, and the handles it cannot rebuild from a dead journal (client order ids, allocated quantities, recovery cursors) are exactly what the plan carried — and it releases the hedge-group lease, so a successor trade may be admitted over live exposure. **Exposure-neutrality is a property of the act given trustworthy inputs, and this is the one precondition whose failure means they are not.** A latched precondition may be re-reported unchanged, and may be **escalated to a strictly more restrictive latching one**; it may never be moved to a non-latching outcome, however restrictive — a more restrictive non-latching report would launder the hold into one a later pass could lift, which is clearance by two reports with no operator in either.

**The join is an ENUMERATION of positions, and a per-instrument read cannot fail this section's own test `[→ M3 slice F2]`.** This section alerts on *foreign orders or unexplained position deltas*, and a position read keyed on an instrument can only ask about instruments this system already knows it traded — which is precisely the set that cannot contain a foreign one. So `Positions` is read **unscoped by symbol**, per venue, product family and settlement asset, and a symbol the account holds that this deployment does not trade is itself the alert; on a venue whose enumeration returns *"only symbols with a position **or open orders**"* it is also how a foreign resting order becomes visible, which no position quantity would have shown. The cost of the enumeration is that *flat* becomes an ABSENCE from a list, and two things bound it: the query names no symbol, so a symbol missing from the answer is missing because the venue says it holds nothing there rather than because the caller spelled it wrong; and an unanswered enumeration MUST be an error rather than an empty report, since §5.3's rule about never inferring an absence from an unanswered query is the same rule one surface over and costs more here — an empty report reads as a flat account, which is what the invariant passes on. **The version of an endpoint is part of this requirement rather than an implementation detail**: where a venue offers two, one returning a row for every symbol and one returning only symbols with exposure, the absence of a row means opposite things, and only the second's silence carries the conclusion (Profiles §9).

**A JOINED order's executed quantity is rebuilt from the venue, and the two surfaces are cross-checked against each other `[→ M3 slice F2]`.** The replay rebuilds state without quantity, so every recovered order carries a cumulative of zero — and zero is not a missing number here, it is a conclusion: §6.7 folds those cumulatives into a residual, and a group of zeroes is *Determined* and flat, which is the verdict that PERMITS a compensating trade. The join therefore reads each order the venue may hold (**every state but `Planned`** — §5.3's "a Planned-only order was never dispatched") and admits its executions into the fill ledger, attributing a row by client order id **or by the venue's own order id, which the same resolving query returns** — the second is the only key one venue offers at all, since its trade lists carry no client order id. The order surface's stated cumulative and the sum of the attributed rows are then **compared**, and a disagreement is reported rather than absorbed: it means an execution exists that cannot be named, and the exposure is real whether or not we can name its row. The admission needs no transaction and that is a property of this path rather than an exemption: it advances no recovery cursor — it re-sweeps from each order's authorization anchor on every boot — so it is **re-derivable**, and the fill ledger's dedupe on `(account, venue, product, symbol, execution_id)` makes the repeat a no-op. Idempotence is what the live path buys with a transaction and this one gets from the venue.

**The net-delta invariant covers BOTH legs, and the spot half is asserted against a RECORDED BASELINE `[→ M3 slice F2; v0.9.49, task #179, record §70]`.** Neither venue has a position surface for spot — a spot balance is not a position — and the balance that exists instead includes holdings this system never bought, so it is comparable to our own exposure only against a **recorded baseline**, which this spec now defines. A baseline is a per-`(venue, account, base asset)` quantity — the portion of the venue's spot balance NOT attributable to this system at a named instant, `baseline := B − ours`, where `B` is the venue's balance and `ours` is the fee-adjusted net this system's journaled spot orders account for. **It is recorded by an operator running `arblab baseline record` — never automatically, and never at boot**, because a boot that minted its own baseline would absorb any unexplained delta into it, laundering exactly the thing the invariant exists to catch; recording is deliberately TWO acts — the command writes a NEW dated document under `O_EXCL`, and the operator pins `{path, sha256}` in §5.2's config, the digest being what makes replacing the document without the config edit a named refusal. The document stores **inputs, not conclusions** — per-asset verbatim balance words, per-order rows — it is **bound to the journal's chain** by a head mark the boot loader verifies before the baseline governs anything (a journal restored from backup, reset, or truncated below the mark refuses by name), and the loader **recomputes** the baseline from the stored words rather than trusting a stored scalar. It is **invalidated by EVENTS, never by time**: a non-journaled balance change — deposit, withdrawal, transfer, dust conversion, a manual trade — is detected rather than enumerated, because the next boot's `B_now − baseline ≠ ours_now` is a **latched operator alert** on the same footing as an unexplained position delta, in both signs (inspect → re-record → re-pin; the re-record PRINTS the delta it absorbs against the prior). Granularity is the **asset**, never the instrument — two pairs sharing a base share one balance, and attributing the delta to one of them would become load-bearing the day a second pair lands — and `ours` is **fee-adjusted over all spot orders at the venue**, because a spot buy's fee is charged in the received asset, so the balance credits net of a fee the order surface states gross; equality is exact decimal arithmetic, no tolerance band. **A spot delta latches only when it is STABLE across a second look**: the balance read and the sweeps that fed the projection are independent calls a late-reporting fill can straddle, so on a non-empty delta the boot waits §5.2's `spot_settle`, re-runs the join (idempotent under the fill ledger's dedupe), and re-asserts — an identical delta latches, a changed one is the world still settling and reports incomplete rather than manufacturing an operator incident from a self-clearing condition, and a second join whose evidence moved — an order NEWLY absent mid-bracket — reports incomplete without re-asserting at all, because only §5.3's resolution may interpret an absence and the bracket does not run it (an order absent at BOTH looks was resolved before the first assert and is not motion). What is asserted is therefore "**every unit of the venue's *position* — and every unit of spot balance movement since the recorded baseline — is attributable to an order this system journaled**", per derivative instrument in the enumerated scopes and per baselined spot asset.

**A spot instrument WITHOUT a recorded baseline HOLDS the posture, and the exemption this paragraph once carried is RETIRED because its premise expired `[v0.9.49, task #179, record §70e]`.** An earlier version of this section ruled the opposite — the spot leg MUST NOT hold the posture — argued from a permanent, venue-imposed gap: no venue publishes a position surface for spot, no enumeration could ever cover it, and holding the posture on a gap no action could close would keep a correct system below trading for ever. The baseline construct closes the gap, so the permanence the argument rested on is gone: recording a baseline is a one-time operator act on the same footing as `spend_lock_dir`, and this section's own sentence had scoped the exemption "until a baseline is defined". A deployment that has not recorded one is **reported on every boot** (`UnassertedBaselineUnrecorded`) **and holds below trading** — its spot balance may be hiding exposure the journal does not explain, which is exactly the epistemic position of a derivative instrument outside every scope. The exemption's membership is now **empty**: every reason an instrument sits outside the invariant holds the posture. Coverage is answered from **configuration, never from the journal** — the join walks the configured spot roster, so every configured spot instrument is answered for on every boot, asserted against its baseline or reported unrecorded, whether or not any order ever existed; a virgin deployment cannot pass by having nothing to check. And the first-record flow is the deliberate consequence rather than a workaround: config without the pin boots and holds, **naming the gap**; the operator runs the record command off that same validated config; the pin is added — which is why `spot_baseline` is **optional in the schema and the optionality is load-bearing** (§5.2): a required field is circular on a virgin deployment, and a "dummy path" workaround would train operators to stage invalid configs.

**§6 step 7's hold is the SECOND empty cell of the same product, and one slice of the outcome vocabulary was fixed without tabulating the rest `[→ M3 slice F2]`.** The paragraph above finds *halted AND latching* missing and fills it; the row below it was left in exactly the same state. §6 step 7 requires that a dispatch which **reached the venue** and whose projection write **failed** holds new trading until that order's state is re-derived from the journal — and that condition is **stop-opening** rather than halted (the order may be executing, so the safety verbs must stay available) and **latching** rather than freely re-reportable (the check that would lift it is the net-delta assertion, which recomputes from the projection that is known stale — and the stale reading is the permissive one, since the order sits at `Planned`, the single non-terminal state contributing no possible-delta interval). A re-reportable outcome would therefore be lifted by an invariant agreeing with its own corrupted input, with no operator in the loop. Its discharge is the re-derivation §6 step 7 names — a journal replay, which in this architecture is a fresh process with a fresh checklist — so within a running process only explicit clearance lifts it. **The general rule this pair earns: an outcome vocabulary is a PRODUCT of the properties it decides, and a missing member is found by tabulating it, not by waiting for a producer.**

**§5.3's absence resolution runs BETWEEN the join and the assertion, and until it did the invariant was asserted over a quantity the join had DECLINED to rebuild `[→ M3 slice G1]`.** The join reads each order the venue may hold, and an order the *order* surface does not hold is deliberately **not swept** — §5.3 forbids inferring "no executions" from an absence — so its executed quantity stays at the zero the replay gave it and the order is handed to the stable-not-found rule. Asserting the net-delta invariant at that point reads exactly that zero as a fact, which is the inference the same use case has just refused to make, one paragraph apart; and the venue's own position is the other side of the subtraction, so the whole of any fill such an order took reports as an **unexplained position delta**. That is *alert for operator clearance*, which **latches** — and the boot it fires on is the one this section exists for: a dispatch that reached the venue and a crash seconds later, where §5.3's propagation bound has merely not elapsed and the refusal would discharge itself inside it. A self-clearing condition frozen into an operator incident is §7.4's *"never health-flap re-entry"* run backwards, and it costs the same thing: a human in the loop of something no human can decide. The order is therefore normative — **replay → join → resolve every absence through §5.3's rule → assert** — and the assertion runs **only where the rebuild concluded**, because an invariant computed over a store that is knowably short is not a weaker check but a wrong one. Where it does not run its gate stays **unreported** rather than failed: unreported is the honest value and it is *not* the permissive one, since the posture is reduced over the **required** gates. An absence whose reason can **never** be discharged by waiting — retention already exceeded, a surface publishing no retention with no assumption configured for it, a sweep that can neither attribute a row nor rule it out — is the **latching** refusal instead, because the next boot answers identically; that distinction belongs to the reason, not to the caller that reads it.

**A precondition can refuse without FAILING, and this section's outcome vocabulary had no way to say so `[→ M3 slice G1]`.** The two paragraphs above tabulate the outcomes on two properties — how restrictive the refusal is, and whether a re-run may lift it — and the table came out full. It was not: the *reconcile-only, re-reportable* cell held only **unreported** and **in progress**, and both of those mean the check has produced **no verdict at all**, while every other row has a member meaning *"it ran and it refuses"*. So the third property is the one the tabulation was missing — **whether the outcome reports a result** — and the missing member is a check that RAN, concluded, and left work a further attempt may finish: a sweep that did not prove coverage, an absence whose finality timer has not elapsed. It must be reconcile-only rather than halted, because halting forbids the reconciliation writes that finish the work — this section's own `DeactivationPending` re-drive among them — and it must not latch, because demanding operator clearance for a timer is the halts-itself-with-every-light-green failure. Reported as *in progress* instead, it is indistinguishable from a boot that hung: the process stays alive, audible and below stop-opening, so it may not reduce exposure, nobody escalates because the boot "has not finished", and §7.4's watchdog reads liveness and does not escalate either — the **alive-but-wedged** state that section calls an uncovered failure, reached through a vocabulary. **The general rule, one turn past the pair above: a product is only as complete as the properties it is tabulated on, so a cell filled by a member that answers a *different question* from its row-mates is the tell that an axis is missing — not that the cell is occupied.**

**The exemption for an instrument the invariant cannot cover was argued from ONE cause and the code collected TWO `[→ M3 slice G2]`.** The spot paragraph above once stated the exemption this paragraph polices: an instrument whose exposure cannot be compared MUST be reported on every boot and — as the ruling stood before `[v0.9.49]` retired it — MUST NOT hold the posture, because a leg whose invariant can *never* be asserted would keep a correct system below trading for ever. That reasoning is about a permanent, venue-imposed gap — no venue publishes a position surface for spot — and the predicate that implemented it was *no configured enumeration covered this instrument*, which a **derivative** reaches too: a scope the deployment did not declare, or one declared for another venue or family, or an instrument dropped from the configuration while the journal still holds an open order on it. That instrument is not one whose invariant can never be asserted. It is one whose invariant **did not run**, over an account that may be holding exposure on it, and a position surface for it exists and was simply never queried. Exempting it makes the net-delta precondition report **satisfied on a boot that issued no position query at all** — with the degenerate case being a deployment that configured no enumerations, where the invariant passes having read nothing. So the report MUST carry the REASON an instrument was left out, and the exemption belongs to the reason rather than to the field — an assignment that is also what made the exemption's later retirement a roster edit rather than a hunt: since `[v0.9.49, task #179]` the baseline construct has closed the one permanent gap, so **no reason exempts** — *no configured scope covers it* is the **latching** refusal, on the same footing as an unexplained delta (the epistemic position is identical, since in both cases the venue may hold exposure this system cannot account for), and a spot instrument without a baseline holds under its own name, per the paragraph above. A reason that cannot be classified holds, because the permissive default is an instrument silently outside the invariant. *The general rule: when a rule EXEMPTS something, check what else lands in the bucket the exemption is written over — a justification argued from one cause governs every cause that reaches the same predicate.*

**The journal's DURABILITY is a precondition of its own, and §13's condition is only one of the two ways to lose it `[→ M3 slice G2]`.** §11/§13 require the write-ahead journal to live on a **local filesystem — ext4/xfs with write barriers, never NFS/network FS** — and schedule the check to this section's list rather than to the adapter's constructor. It is a **gate of its own** (`GateJournalDurable`), not a condition folded into the replay's, for this section's own rule that a gate is reported about its OWN evidence: the replay's evidence is the records and this one's is the filesystem beneath them. It is asserted **before the journal is opened**, because a database created on a network filesystem is already the thing being refused, and its refusal is the **halted-and-latching** outcome — the same one a chain that will not verify gets, and for the same reason, since reconcile-only would permit the reconciliation writes that re-drive what an untrustworthy journal says happened. What it protects is the limit this section already states about the tamper-evidence: a chain proves nothing about records that were never seen, and a network filesystem is precisely the condition under which records go missing with every remaining link still verifying. **The condition is DURABILITY and locality is a proxy for it**: a journal on `tmpfs` is local, honours every fsync, and is gone at the next reboot — which is the boot this section exists for — so it is refused as well, under its own name. A filesystem the build does not recognise, and a host the build cannot inspect at all, are **refusals** rather than passes: an unverifiable claim about durability is not a verified one, and admitting the unknown is how a network filesystem arrives under a name nobody enumerated.

**A GENERATION the journal opened and never ENDED is REINSTATED, on a gate of its OWN, and the reason it cannot share the replay's is a QUANTITY `[v0.9.56, task #203, record §75; v0.9.57, task #204, record §76]`.** The replay paragraph above states that state is rebuilt *through the same journal-then-apply write path the live system uses*, so the recovered projection can only reach states a live process could have produced. That rule is about ORDERS, and §5.1's second journal scope has no write path of the same kind: a `PackageDelever` generation's recovered state is not a row in the order projection but a live entry in §6.7's SHARED reserved-reduction ledger, which is process memory a fresh process starts empty. So a journal holding a generation with no ending record leaves the boot in a stated position — it knows a bounded attempt was running and has not reinstated what that attempt was holding. **That was `Incomplete` while nothing rebuilt it, and the rebuild is now a PHASE with a gate of its own (`GateGenerationsReinstated`).** The two cannot be one gate, and the reason is arithmetic rather than tidiness: the entry a generation must re-`Reserve` carries its **confirmed perp reduction**, and that quantity is in NO journal — there is no fill record at order scope or at generation scope, and the replay leaves every executed quantity at zero. It reaches this process only from the VENUE, so the rebuild can run only **after the join and after §5.3's absence resolution**, which is a different phase of this boot from the replay. Rebuilding earlier is not merely premature: a generation whose log holds a spot authorization of `s` would be rebuilt against a confirmed perp reduction of zero and refused by [mechanism: State-Machines §7]'s own never-net-short cap. **The gate is a gate of its own for this section's stated rule that a gate is reported about its OWN evidence** — the same argument `GateJournalDurable` makes about the filesystem beneath the records, made here about evidence the replay does not have YET. The reinstatement itself is: rebuild the aggregate by driving [mechanism: State-Machines §7]'s own transitions through the recorded phases (so a log recording an impossible LADDER is refused exactly as one recording an impossible order history is), re-`Reserve` its entry and amend it to the generation's outstanding net intent as ONE act with installing it, and then discharge `FM-8`'s standing obligation by reassessing — because reinstating an entry MOVES §6.7's subtrahend, which is a classification-changing event by construction, and a premise that dissolved during the outage must fire the premise-lost row rather than wait for an event nothing is obliged to produce. **The rehydration drops exactly one guard: the PREMISE.** Every other check is about the RECORD and a stored value failing one is a log that does not compose; the premise is about the world at the instant of a decision that has already been taken and journaled, and refusing to rebuild over a dissolved one leaves the entry out of the ledger — which is the very hole this gate exists to hold. Refusing to rebuild and discharging the supersession look alike from one step away and are opposites. **The gate carries three outcomes.** `Passed` when every live generation is back with its entry, INCLUDING the ordinary case of a journal holding none — a boot that never delevers must not be held for ever. `Incomplete` when a reinstated generation's premise had dissolved while its reserved SECOND leg was still out, because all three supersession rows quiesce that leg to §6.7 finality FIRST and finality is the venue's to give, not the boot's. `Failed` when the rebuild could not run at all — including a deployment that wired no reinstatement and met a live generation, which MUST fail by name rather than pass, on the same rule the spot second-look bracket follows. It is never `Passed` while an entry is missing, and the failure direction is what forbids it. The failure direction is what forbids the last: a ledger missing an entry reads as **more** room, never less, so §6.7's determined branch would size a compensating trade against a residual too large by exactly the generation's outstanding net intent — buying back the exposure that generation's own perp leg had already committed to. That is `FM-5`'s shape reached through recovery instead of through a booking error, and it is invisible to every invariant for `FM-5`'s own reason: they are all computed FROM the ledger. **Liveness is decided by the phase's own predicate, never by a table mapping record kinds to phases** — a generation is live unless the log records an ENDING, and an ending is a phase [mechanism: State-Machines §7] already calls inactive — because such a table would be a second home for that machine's transition set, drifting the moment a kind's phase changed. **A supersession that does not resume the ladder is reinstated too, and it is a separate fact from the generations.** [mechanism: State-Machines §7] makes ladder resumption a property of the PATH; the two external arbitrations do not resume, so a boot that lost that fact would let §7.1's ladder open a generation against an arbitration that has taken the package away from it. It is derived from the ENDED generations — the half the live list discards — and the hedge group comes from the generation's own OPENING record, since a supersession record names only the generation. Where two arbitrations closed one package's ladder, the FIRST is the one reported: which arbitration closed it is the operator's question and there is no other record of it once the generations are gone. *The general rule: when a replay's rebuild rule is stated over one scope's records, adding a second scope does not extend it — the new scope needs its own answer to "and what is the process now permitted to do", its own gate if its evidence arrives at a different point in the sequence, and while nothing rebuilds it the honest answer is a refusal.*

**`GateAccountPosture` HAS A PRODUCER, and its two refusing outcomes sit on OPPOSITE sides of this section's latching rule `[v0.9.51, task #198, record §73k, §73l]`.** §4.1's posture check is one of this section's eight gates and had been declared with nothing to report it since the composition root existed; it now runs as a phase of its own, **after the OMS is constructed and before the journal reconciliation**, and it does **not** halt the sequence — a refused posture is a verdict, and an operator facing a wrong margin mode still wants to know what the join found, so halting here would answer one question by suppressing another. The paragraph above notes that *a posture check that failed because the venue was unreachable may legitimately pass on the next attempt*, and that sentence is correct about the half it names and silent about the other, which is the half that matters: **a posture that was READ and does not satisfy §4.1 LATCHES.** It must, because §4.1 forbids this engine from repairing a posture, so no retry can lift it and a freely re-reportable refusal would be lifted by a re-read of an account nobody changed — *"never health-flap re-entry"* arriving through a check whose retry is deterministic. A posture that could not be **established** — the venue did not answer, a pinned attestation would not load, the requirement could not be built — is the ordinary self-clearing failure, because a further attempt genuinely may answer. The two are not interchangeable and the direction that matters is one this section states elsewhere in its own words: a read that never answered must never decay into an account that was found clean, which is why a verdict that evaluated nothing is refused rather than agreed with (§4.1).

### 7.6 Rate-limit discipline
Header-aware governors **per `(venue, API family)`** (`platform/ratelimit`) — Binance **spot and futures report and enforce separate used-weight/order budgets** via their own `exchangeInfo`, so they are distinct **weight/order** buckets; but because **IP-ban-track separation is inferred, not documented** (review record §2), default to a **shared IP-ban safety envelope** per venue — bound combined request rate so maxing both product budgets can't trip a shared gateway ban — while keeping **separate product weight/order counters** `[→ R1-F5, R2b-10]`; back off at ~70% weight; treat 429 (Binance) / 403+10006 and the **unheadered IP ban ~600/5s retCode 10018** (Bybit) as hard pauses; surface 418 / IP ban as immediate operator alerts. Independent IPs per venue where possible.

**Traffic carries a priority, and each priority has its own ceiling on the same budget.** The "~70% weight" threshold above, §7.1's *reserved rate-limit allocation* for the margin top-up, and §6's *reserve rate-limit budget for recovery* are **one mechanism described three times** — each stated a threshold or a reservation without stating the priority ordering that makes them cohere. Three classes, in shed order:

| Class | Carries | Ceiling |
|---|---|---|
| **`Opening`** | requests that create new exposure — the same act §5.3 calls `stop-opening` | the ~70% back-off point |
| **`Routine`** | the reads that keep the risk view live — marks, books, account posture | the reserve boundary (~90%) |
| **`Safety`** | §6.7 ambiguity resolution, §7.1's margin top-up and REST mark failover, §7.5's reconcile, a flatten | capacity |

**The ordering is normative, and it is not the obvious one: monitoring outranks new exposure.** Shedding market-data and account reads to protect trading traffic would make the rate limiter itself the cause of a **stale mark** — which is §7.1's own escalation trigger, so the governor would fire the `T_blind` de-risk it exists to help avoid.

**The class has a CARRIER, and naming it is part of this rule rather than an implementation detail `[→ M3 slice C2a]`.** A priority ladder is only enforceable if every request can state which rung it is on, and for **orders** nothing in the data does: the class is a property of the §5.3 command that produced the order, and neither the `Order` aggregate nor its projection records that command. So the carrier is the **`Place` argument** (§4), fed from §5.3's command→class table by the caller that issued the command, checked before §6 step 6's fsync. Two consequences are normative. **No layer may default it** — the two defaults are unequally wrong, and the cheap one is the dangerous one: a flatten defaulted to `Opening` is shed during precisely the incident that motivated the reserve, while a mis-classified `Opening` only spends reserve that a second coincidence must then need. **And the order-carrying classes are `Opening` and `Safety` only** — `Routine` is read traffic, issued under no §5.3 command, and it maps to neither ceiling, so an adapter offered `Routine` for an order would have to round to one of its neighbours and both roundings are the silent form of the decision this ladder exists to make explicit. `Routine` is therefore refused at the order seam rather than translated. **For the read traffic the ladder was equally written for, the carrier is the call site**, which knows what it is asking for.

**Capacity is a ceiling for every class, `Safety` included: the reserve is an exclusive band, never a bypass.** Past capacity the venue is expected to **refuse**, so an issued flatten is not a flatten; on Binance repeat violations escalate a 2-minute ban toward **three days**, so pushing lengthens the outage being pushed against; and this spec already has a designed answer to "cannot act at the venue" — §7.4's pre-placed venue-native protection and the off-host actuator. A governor that spent past the budget would silently substitute wishful throughput for that ladder. Ceilings are **absolute counts, not percentages of a percentage**: a fraction of a count is a rounding decision this layer must not be making on its own.

**A governor MUST refuse a cost it cannot count, and the venue-published ZERO is what makes this load-bearing `[→ M3 slice C2a, Profiles §7]`.** A charge is applied by walking the budgets a profile declares and taking each one's dimension from the cost, so **a dimension the profile declares no budget for is silently uncounted** — no error, no refusal, no metric, and a governor that counts nothing admits everything. That is tolerable while every metered endpoint charges weight, and **Binance's `POST /fapi/v1/order` does not**: it is documented at **zero** on the IP weight budget and 1 on each order-count budget (Profiles §7), which makes it **the one call in this system whose entire cost rides on a single dimension**. A venue profile declaring weight budgets but no **order-count** budget therefore charges *literally nothing* for placing a futures order — admitted forever, against a venue that meters `X-MBX-ORDER-COUNT-10S` and `-1M` and bans on them. So a profile MUST be **rejected at construction** if any cost the venue's endpoints can present charges a dimension it does not budget, rather than admitting the request and counting zero. The direction is this spec's standing one: the failure of forgetting must be a **refusal that names the dimension**, not a running process whose order budget is a no-op. **Note the shape rather than only the case** — correcting the cost validator to accept a legitimate zero was right, and it moved the safety of that zero onto a claim about a *different object* (that the profile counts orders) which nothing checked. A validator cannot audit the thing it is validated against.

**Landed [v0.9.43, task #173, record §64] as two layers, and the runtime one is primary — construction cannot see the costs, only the adapters know them.** (1) The **governor** refuses, at decide time, any request whose cost charges a dimension its applicable budgets do not count — an *error*, not a budget refusal, because it is a profile-versus-adapter disagreement no waiting repairs. (2) **Construction** makes that refusal unreachable except deliberately: every family budgets weight and orders with **family-scoped** limits, or carries a written `Uncounted{family, dimension, reason}` declaration — the `//nofloat:allow` / §10-label shape: default deny, escape in writing, no wildcard family (an exemption generalizes over its predicate, so one written for the family where the claim holds would release the family where it does not). A declaration is a **claim about traffic, never a suppression**: a cost arriving that charges the waived dimension is refused by layer (1) anyway, as the claim's falsification, fail-closed before anything is sent. Three consequences are normative. **The venue request envelope is mandatory and not waivable** — family-scoped request counters are additive detail and never satisfy it, because each can sit inside its own capacity while their sum trips the shared gateway ban neither reports on, and the envelope's capacity is a *locally chosen* safety bound ("bound combined request rate"), not a venue fact somebody might lack. **Venue scope is reserved for the envelope**: the header fold addresses `(family, name)`, so a venue-scoped weight or order budget is a fold target nothing can reach — it validates, counts locally, and silently never receives the venue's own reading; the construction is refused outright. And **the truthful cost of a call metered per request alone** (Bybit's read surfaces, 50/s per UID per endpoint — each also charged against its own endpoint-scoped budget since `[v0.9.45, task #185]`, see the clause below) is `RequestOnly()`, a carrier the validator can tell apart from the zero value — the zero stays refused as the field nobody filled in. That last clause closed a **live defect**: those calls spelled the truth as the zero `Cost`, the signed client validates the cost *before* Acquire, and every Bybit position/order read through it failed at its own precondition — invisible because the builder suite and the governor suite each passed and nothing composed them.

**A declared budget must be a fold target the dialect can actually address, and composition refuses one that is not `[v0.9.44, task #186, record §65]`.** The observe seam drops fold errors by design — a mislabelled header must not fail a request the venue already answered mid-trade — and that bargain is only safe if the mismatch is caught where it is a configuration, not a request. Both dialects address a fold at `(family, name)` and at nothing else: no dimension, no interval. So at client construction, every family-scoped budget of a dimension the dialect reports via headers MUST bear exactly the name the reader derives — `weight_`/`orders_` plus the canonical spelling of the budget's own window (`10s`, `1m`, `1h`, `1d`) — and a budget of an unheadered dimension MUST NOT bear a derivable name, because the venue's reading of a *different* dimension would fold into it; the refusal names the declared name and the derived one. The reader's side of the same contract is that the derived name is a function of the **window, not the venue's spelling**: header suffixes are parsed and re-rendered through the same renderer the check uses (`60S` and `1M` are one fold target), with checked arithmetic so an unrepresentable suffix derives nothing rather than wrapping into a name it never meant. Two boundaries are deliberate: venue-scoped budgets are out of the check's reach (folds always carry a non-empty family, and venue scope is requests-only per the clause above), and **Bybit's fold names are checked against the dialect's closed endpoint registry since `[v0.9.45, task #185]`** — the profile-side vocabulary is the endpoint-scoped budget clause below, the names are path-derived rather than caller-supplied, and a non-roster endpoint name or a roster-squatting family name is refused at this same construction seam. Compatibility: config *syntax* is unchanged, but a pre-#186 profile with fold-unaddressable names now refuses at boot instead of running silently degraded — the refusal is the feature, and it found three live fixtures in this repo's own tree (the exercise and spot-only reconcile suites were dropping every venue reading). Limit names feed `Snapshot` and future §10 metric labels, so the renames change telemetry series identity; no deployed consumer existed.

**A venue that meters per endpoint gets endpoint-scoped budgets, and they are VENUE-level: one shared window per endpoint across product categories `[v0.9.45, task #185, record §66]`.** Bybit meters per endpoint, per UID, per second (Profiles §4's dated 2026-08-04 block), and before this clause that meter was inexpressible: a family-scoped `position_list` budget is charged by EVERY same-family call (an order burst exhausts the local count and refuses Safety-priority position reads during exactly the §7.1 incident that needs them), while an undeclared one loses the venue's own fold silently. `ScopeEndpoint` refuses a family — whether the venue splits its per-endpoint counter by category is an unverified inference, one shared window is conservative under EITHER reading (shared: exact; split: slight under-admission), and a family-keyed window plus any ownership rule makes a two-family package NON-ATOMIC: the executor fans legs concurrently with no governor preflight, so one leg sends while its sibling refuses deterministically — a naked leg by configuration. The limit's NAME is the endpoint discriminator and the fold address in one carrier, and the transport dialect DERIVES it from the call path through a closed `{path, name, required dimension}` registry — the caller-supplied name field is deleted, so the substitution class is inexpressible rather than checked. Three refusals in the governor, all errors pre-send that no waiting repairs: a request naming an endpoint no budget covers (**R1** — a call either has its declared window or is never sent, so a fold is never lost); a request naming NO endpoint against a profile that budgets per endpoint (**R2** — an unmapped path on a metering venue would be metered venue-side and uncounted locally); a matched endpoint window the cost would charge ZERO units (**R3** — a zero charge is always admitted, so such a budget could never do its job). The cannot-count rule counts a dimension the MATCHED endpoint window declares — Bybit's order meter IS the create endpoint's budget, so without this every Bybit create would be refused by the rule meant to protect it — while profile-level coverage stays family-scoped. At boot the dialect enforces the registry: an endpoint budget must bear a roster name, the registry's dimension, and EXACTLY the venue's 1s window (a shorter window over-admits multiplicatively and folds age out on the same wrong interval); a family budget may not squat on a roster name; and construction requires EVERY roster endpoint declared with its registry dimension, because request-time-only completeness strands recovery — a profile missing `order_history` boots and trades, then refuses the Safety-priority history fallback at exactly the §6.7 moment that resolves an ambiguous order. Where the venue publishes UNEQUAL per-category caps for one endpoint (create: 20/s spot vs 10/s linear, both account-upgradable), the shared window's ceilings are stated from the MINIMUM across the categories the profile enables — normative operator arithmetic, deliberately not machine-enforced: platform holds no venue numbers, and a transport cap table would refuse legitimately upgraded accounts. Two hardenings landed with the clause: the header fold moves to immediately after the transport response returns, BEFORE the body read (a body-read failure was discarding the reading on exactly the 429 that carried it), and `freeAt`'s early return is written in the non-underflowing direction (`used > ceiling` is a state the observe ratchet explicitly produces; the old subtraction wrapped and reported a false "retry immediately").

**Header-aware means the venue's reading is folded in one direction only: upward.** A governor that counted only its own sends would be guessing, so the reported consumption is folded into the local count — but **only when it exceeds it**.

**The two venues' headers report OPPOSITE quantities, and the fold rule is stated over only one of them `[→ M3 slice C1, Profiles §6]`.** Binance's `X-MBX-USED-WEIGHT-*` is consumption. Bybit's `X-Bapi-Limit-Status` is verbatim *"your **remaining** requests for current endpoint"* — the complement — with the cap in `X-Bapi-Limit`. An earlier wording of this paragraph named both as "the reported consumption", which is **wrong about Bybit**, and applying the upward-only fold to a *remaining* count fails in both directions: 90 remaining against a local count of 30 exceeds it and folds in, **inflating** the count on the venue reporting plenty of room; 2 remaining does **not** exceed 30, so the venue's warning that we are nearly banned is **discarded** — and that direction is silent, which is the direction that ends in the ban this rule exists to avoid. So the adapter MUST convert before folding — `used = X-Bapi-Limit − X-Bapi-Limit-Status` — and MUST derive **no observation at all** when `X-Bapi-Limit` is absent, because a remaining count with no cap beside it cannot be turned into a consumption figure and a guessed cap is a budget quietly rescaled. Nothing about the values distinguishes them: both headers are integers about the same limit, and only the venue's prose says which way they point. The asymmetry is the requirement, not an optimization. A reading is *always* stale: it describes the server at the moment it processed some earlier request, with others already in flight behind it. So a reading **below** the local count is exactly what staleness looks like, and adopting it would discard the record of every request sent after the one that carried the header; a reading **above** it is information available no other way — an endpoint whose weight was underestimated, or another consumer sharing the IP. The two failure directions cost differently: ignoring a legitimate decrease costs **throughput until the window rolls**, while adopting an illegitimate decrease costs a **ban**, and on Binance repeat violations escalate a 2-minute ban toward three days. The same direction governs a venue's own retry hint on a hard pause: it is a **floor, not a ceiling** — the pause is the **longer** of the venue's hint and the governor's own penalty, because a venue answering "60 s" while local policy says five minutes is stating its minimum, not granting permission for the remainder.

**A mapped response from which no observation could be derived is COUNTED, per endpoint, and the count is an operator fact `[v0.9.46, task #187, record §67]`.** The derive-nothing rule above is normative and stands — but it makes the correction channel's failure silent: the upward-only fold is the only mechanism that incorporates another consumer on the same account, so a stripped or malformed header stream lets the local governor admit its full allowance on top of a co-consumer's traffic while every response succeeds. So transport MUST count a **fold miss** — a call mapped to an endpoint budget whose response the API demonstrably handled (any 2xx not classified as the IP ban, or any response classified as a throttle, whose known-unheadered gateway ban shape is excluded on the recorded venue fact) yielding no usable observation for that endpoint — and the governor MUST carry the per-limit monotone count in its snapshot, where the roots render it beside this section's ban alert. The count is observability ONLY: admission state does not change, and the rendered line's contract is historical ("N responses carried no usable reading this run"), never a claim about now. The response policy is count-and-alert **exactly as long as one consumer spends the account at a time** — an operational premise, not a code-enforced one; the first deployment shape with a second concurrent spender reopens the policy question (record §67), and the live-execution decision must confirm single-spender deployment before any live Bybit spend. **Since `[v0.9.47, task #188, record §68]` the per-host slice of that premise is machine-checked rather than purely operational:** a credentialed transport cannot be *constructed* without holding the venue's spend lock (the clause below), so two lock-aware spending processes on one host cannot coexist — the premise stays operational only **across hosts** and against lock-unaware processes, and the live-execution decision's single-spender confirmation now names exactly that remainder.

**A package reserves its whole rate-limit cost before any leg's authorization fsync, and a reservation is OCCUPANCY, not a timed charge `[v0.9.47, task #188, record §68]`.** §6 step 6 fans legs out concurrently, and before this clause each leg acquired capacity independently after its own `DispatchAuthorized` fsync — so a package admissible leg-by-leg but not in sum manufactured, by configuration, a durable authorization the governor then refused: §5.3's post-fsync recovery episode on the venue's own arithmetic (the §66 endpoint clause had already removed the *deterministic* member of this family; this removes the capacity member). The mechanism: `Reserve(batch)` is **all-or-nothing under one lock acquisition** — request validation IDENTICAL to send-time admission via one shared prefix (the taxonomy cannot drift), mixed priorities refused, the batch summed per window with **overflow-checked** accumulation (never saturating: a wrapped sum lies twice, admitting the batch and then under-releasing it), admission on the sum at the batch priority against `ceiling − used − reserved`, and refusal naming the worst limit with nothing occupied. What admission creates is **untimed occupancy**: it never ages out (a TTL would re-open the gap on a slow leg), is **invisible to the header fold** (the venue's report can never include unsent reservations, so folding over them would double-count), and converts to a charge only at `Consume` — the last pre-send instant, which re-checks **only the venue's word** (a pause in force, or a fold that ratcheted `used` past absolute capacity on a window this entry actually charges; a zero-charged window admits, and re-running the priority ceiling would let an unrelated local spender invalidate the promise reservation exists to make). A blanket `Cancel` releases reserved-only entries on **every** executor exit — consumed charges are the venue's count, not ours to release — and `freeAt` stays **charges-only**: occupancy is cancellable, so the earliest instant a refused retry could succeed is the charges answer, and computing over `ceiling − reserved` would overload the documented zero. The hold is minted by the venue's ONE governor and refused pre-send when presented to a transport on another (`MintedBy`, pointer identity); the reserver and the placer are **one gateway surface**, so reserve-here-place-there is inexpressible rather than checked. `Snapshot` carries per-limit `Reserved` for the roots' report ("N unit(s) reserved for an in-flight package", rendered after the fold-miss lines). **And the venue's spending credential is under a ONE-SPENDER LOCK, required at construction:** `NewSignedClient` refuses to build without a `SpendLock` whose **domain** — a closed `SpendDomain` set answered by the *signer*, never the config's open venue alias, so `binance_prod` and `binance_testnet` contend on one lock — and **credential fingerprint** (SHA-256 of the key: identifies without revealing) both match the signer's own answers. The lock is an advisory `flock` on `<spend_lock_dir>/<domain>.lock` (the file persists — deleting a file another process may be flocking is the classic unlink race; the flock is the lock, and the OS releases it on process death), held for exactly the lifetime of the owned **reachable** spending capability: the wiring helper releases on every post-acquire construction failure, the root releases in the `oms.New` error arm with the close error joined into the recorded cause, and the success path's closer releases after the module closes, LIFO. Construction is also where the other boot-detectable post-fsync refusals of this family live — the canonical base-URL parse plus `WriteProxy` serialization dry-run (a config-derived Host that Go's transport would refuse AT SEND is refused at boot), the `checkServerTime` signing-readiness check (§5.2), and control bytes refused inside credentials at the carrier — because a failure every future send is guaranteed to hit is a construction fact, not a send fact.

- **Fidelity requirements:** live-estimate (not settled-rate) signal, no lookahead; discrete funding accrual at real settlement timestamps (fired by `TestClock` timers); spread/level **persistence model**; **adverse-selection fill model** (IOC fills preferentially when the book moves against you) — a **conservative bound is required at `$1K` `[→ R2b-7]`:** its *structure* is fixed (below), and its **numeric thresholds — adverse-move size, decision-to-arrival latency, rolling-window length + regime segmentation, standby benchmark, max-drawdown ceiling, confidence level + method, and expected utilization — are a *pre-registered, versioned calibration artifact***: a milestone-2 **predecessor deliverable** (produced *and approved before the promotion sample is scored*) carrying a **frozen dataset + holdout identifiers, a schema + content hash, the rationale, and an approval record — for a solo operator, **mechanically-derived thresholds are the default** governance (a named independent authority only if the operation is actually staffed, per the solo-honest posture of §7.4/§9) `[→ R1c-5b]`**; **any change forces a new version + a complete rerun**. **Milestone-2 authorization for the latency threshold `[→ the §2.4 modeled-tier shape]`: before milestone 3's OMS exists there is no order path, so no decision-to-arrival latency is *observable*; the calibration artifact MAY carry a *declared* upper bound for the `$1K` gate — informed by the capture archive's transport statistics with a stated multiplier, labeled declared-not-measured — and the consuming adapter MUST refuse at decision time any latency assumption *longer* than the declared bound, so a live system slower than the assumption refuses rather than flatters; a *measured* order-path latency distribution is a precondition of any capital tier** *(landed v0.9.18 — calibration design record §41b family 3, §41q)*. Two implementations agreeing on the same artifact proves *determinism, not independence* — the artifact's **governance** (independent, pre-registered, holdout-frozen) is what prevents tuning-until-it-passes. Structure: on captured + Tardis **BTC** data over **≥ the last 3 months including a negative-funding regime**, using **time-synchronized spot & perp books**, model each fill by **walking the actual order quantity through book depth** (not a flat 1-tick move) after a **measured decision-to-arrival latency**, taking the **worse of {the depth-walked fill after that latency + adverse move, the measured p90 slippage *conditional on order size and book state*}**. The pass condition uses **regime-appropriate criteria** (a single aggregate APY can hide a negative-regime drawdown, but demanding the hurdle *inside* a negative regime is unsatisfiable — a correctly standing-down strategy earns ≈0 there, §2.4): **regime classification takes precedence** — a **negative-classified** window uses the standby criterion **even when it is also a rolling window** (a rolling window falling inside a negative streak is *not* held to the hurdle): in **negative-funding sub-windows** the test is **correct stand-down + a bounded loss/drawdown versus a defined standby benchmark** (idle/deployable capital, *not* the hurdle). Only **non-negative / mixed** rolling windows **meeting a minimum-utilization threshold** — and the **full sample** — are held to a **utilization-adjusted lower-confidence-bound net return ≥ the `C_allocated` hurdle** (the LCB, not the point estimate), with a **bounded max-drawdown**. Optionally, model **deployable idle-capital yield + availability + transfer costs** explicitly rather than assuming 0. Full calibration at `$10K+`; **survivorship** (delisted/force-settled alt pairs) — `$10K+`, deferrable while the `$1K` universe is strictly BTC; real fee tiers (spot ≠ perp) + slippage + latency distributions; **replayed config/reference-data revisions + deterministic seeds**; replay all exit rules tick-by-tick, never fixed-N-cycle holds.

## 10. Observability & tax records
- **Metrics:** funding (per venue/symbol), spread/level, WS freshness + cross-leg skew, open positions, unrealized/realized PnL, fill rate, one-leg-failure rate, **unhedged-exposure duration**, error/rate-limit rate, inventory drift (isolated lossy lane).
- **Label cardinality is bounded by declaration, and the default is deny.** Every metric label MUST either declare the **closed set of values** it may take, or carry a **written reason** that its domain is genuinely open (a venue error code; a listing set that changes). A label that does neither is **refused at registration**. §3.4's lossy-lane isolation does not cover this — that guarantee is about a stalled *consumer*, and the way a metrics layer actually takes a trading process down is unbounded cardinality: a metric labelled by `ClientOrderID` allocates one time series per order, forever, inside the trading process's own heap, while **every scrape succeeds and the lane reports zero drops**. §3.4 holds perfectly for the entire duration of the outage it fails to prevent. Same shape as §3.6 rule 4's `//nofloat:allow <reason>` and §5.2's `config:"hot"`, and for the same purpose: the person taking on the risk writes down why they are entitled to.
- **The recording seam is integer-typed, and every sample carries its dimension.** A value crosses into the observability layer as a **scaled integer at `fixedpoint`'s canonical scale**, tagged with the **unit** it measures (count, bytes, seconds, ratio, money) and — for a money unit — the **asset** it is denominated in; a sample whose unit or asset disagrees with the metric it is recorded against is **refused at record time**, not coerced. §3.6 rule 4 bans `float64` under `internal/`, and the exporter boundary is the one place a `float64` seam would be reintroduced for the whole codebase's numbers on the argument that *it is only a metric* — but §12's kill-gate verdict is read off these panels, so "only a metric" is where the decision is actually made. The unit and asset tags are the part rule 4 does not give on its own: unlabelled, a duration recorded in milliseconds against a seconds metric, and a USD figure summed with a USDC one, both render as **plausible numbers on a dashboard** and fail nothing. Conversion to an exporter's wire format (Prometheus is `float64`-typed) happens **once, at that adapter**, under rule 4's annotated escape — and the exact range of the conversion is a stated bound, not an assumption.
- **Alerts:** control-lane gap, per-class staleness, liq-distance thresholds, basis divergence >0.5%, drawdown, kill-switch, rate-limit ban, inventory-drift threshold, watchdog miss.
- **Tax hooks `[→ 8 review, R1/R2]`:** the platform emits **raw, per-event USD-valued records** — funding receipts, fills, settled marks, cost-basis inputs, with valuation evidence — to the durable audit projection. **Classification is downstream policy, not asserted here:** whether a funding receipt is ordinary income vs part of a property disposition is jurisdiction- and entity-specific, so the platform provides the evidence and a tax layer classifies it.

- **Backend:** Go, single module.
