# Design record §61 — #170: §7.6's ban alert, and the exit class that was advising the harmful response

**Date:** 2026-08-03 · **Session:** 90 · **Docs:** v0.9.40 (no spec edit owed — see §61f) · **Tasks:** #170

Task #170 was slice C1's reading-pass finding: §7.6's "surface 418 / IP ban as
immediate operator alerts" is a MUST with a complete producer chain and no
consumer. `transport/venueerror.go` classifies Binance 418 and Bybit
10018/403 onto `ratelimit.PenaltyBan`, the governor counts it, and
`Snapshot.Bans`'s own doc names the division — "this package classifies the
penalty and the composition root delivers the alert" — written when no
composition root existed. G2 built the root and dropped the governor handle on
the floor at `newOrderClient`, so the fact was not merely unread: it was
unreachable. This slice hands the handle to the root and finishes the MUST.

---

## §61a — the finding: the missing alert was also a WRONG standing answer, not just a silent one

The reading-pass framing ("no code raises the alert") understates what the gap
did. A 418 during the join fails the position query, which reports
`GateVenueJoined`/`GateNetDeltaAsserted` as `OutcomeFailed`, which
`Report.ExitClass` reads as **ExitIncomplete — "a retry may lift it"**. For a
ban that advice is the harm itself: Binance escalates repeat violations from
two minutes toward three days, so the one condition §7.6 singles out for a
human arrived labelled with an invitation to automate the response that
worsens it. The absent consumer was not a blind spot beside a correct verdict;
it was a verdict pointing the operator at the venue with a stick.

## §61b — why consulting Bans in ExitClass is not the dead branch the method itself warns about

`ExitClass`'s own comment records why `Storage` and `Reconciliation.Cause` are
deliberately NOT consulted: every path that sets either also reports a
produced gate below Passed, so a second reading would be a branch nothing can
execute. The bans counter fails that test in the useful direction — **no gate
carries the fact**. The gate the banned call lands on says only "failed",
which is the wrong class (§61a), and there is a quieter shape with no failed
gate at all: a fallback (Bybit's history fallback is the standing example)
absorbing the banned call so every produced gate concludes clean. The counter
is the ONLY reading, so the branch is load-bearing, and the e2e test isolates
it by asserting `Latched` is empty when the verdict flips.

Placement: bans → ExitOperator, beside the latch check. The class already
means "a human acts before anything retries", which is precisely §7.6's
demand; a fourth class for bans would put two names on one operator
instruction.

## §61c — the exercise root: two snapshots, and the claim that keeps ExitClass out of the second

`exercise.Report` carries the ban facts twice, and each field earns its place:

- `Boot.RateLimit` stays the PRE-execute snapshot, because §59's ranking
  rationale still binds — re-deriving Boot post-execute would let a
  dispatch-time ban outrank ExitExecution and bury "THIS run dispatched".
  With the new branch it would also do it through the boot's class, which is
  the exact burying G3 rejected.
- `Report.RateLimit` is the POST-execute read, because `Bans` is monotone and
  the fan-out is venue traffic: a ban the dispatch itself earned is visible
  only here.

Exercise's `ExitClass` deliberately does NOT consult the new field. The
excusing claim: a ban during the fan-out IS a leg below StateSubmitted,
because the 418 that files the penalty is the same response that classifies
that leg's Place — `RateLimited` is `EffectNotApplied` + `ClassRateLimit`,
which `classifyEffect` sends to SubmissionUnknown (not Rejected: FLAG-2's
explicit-rejection evidence class is absent, §5.3's resolving query still owns
the order). So the leg loop already answers ExitExecution, and a second
reading would be the §61b dead branch on the other side of the line.
Per this repo's rule that a fix's correctness resting on a claim gets a check
rather than a paragraph, `TestABanDuringDispatchIsSurfaced` pins the whole
claim: forced ordering (the perp 418 answers only after the spot Place
completed, so exactly one leg is banned and by the venue rather than by a race
with the governor), exactly 1 banned / 1 clean leg, SubmissionUnknown with a
travelling Cause, class ExitExecution, `Boot.RateLimit.Bans == 0` against
`RateLimit.Bans == 1`.

A second consequence, free but real: the execute gate reads
`boot.ExitClass() != ExitClean`, so a boot-time ban now REFUSES to dispatch.
That is §7.6 becoming load-bearing above the governor's own pause — the pause
would have refused each Acquire anyway, but the gate refuses before the first
fsync, with nothing committed.

## §61d — the renderer draws §7.6's one line, and prints nothing as the default

One shared `writeRateLimitStatus` for both commands (G3's one-renderer rule):
`Bans > 0` prints the OPERATOR ALERT naming venue, count, "do not retry", and
the pause deadline; a throttle pause prints an informational line that says in
words it is NOT an operator matter; the zero snapshot prints nothing —
a standing "ratelimit: nothing" line is how an operator learns to skim past
the one that matters. The exercise renderer adds one post-execute call, gated
on `Executed`: when nothing executed the post-execute snapshot holds the same
facts the boot's line already rendered, and two counts for one venue makes the
operator work out which is real. `TestExerciseReportPrintsTheBanAlertExactlyOnce`
counts occurrences in both arrival shapes; "printed" alone cannot see a double.

## §61f — rejected alternatives, each with the reason

- **Alert from the transport or ratelimit at Penalize time** ("truly
  immediate"). Rejected on the recorded division: ratelimit is a §11 kernel
  package and its doc already assigns delivery to the caller; a kernel package
  holding an ops channel is the coupling kernelpurity exists to refuse. In
  these one-shot binaries end-of-run IS immediate — the process lives seconds
  — and the long-running engine binary's push delivery belongs to the §10
  exporter slice, whose deferral names its construct: the Prometheus adapter
  and the engine composition root, neither of which exists.
- **A ninth checklist gate / PermitsNow integration.** The in-process refusal
  already exists and is stronger than a gate: the governor's pause outranks
  every budget including PrioritySafety at Acquire, and now the execute gate
  refuses pre-fsync through the boot class. A gate would extend §7.5's
  normative roster — a spec edit §7.6 does not ask for — to duplicate an
  enforcement that exists; what was missing was only the human's copy.
- **A §10 metric now.** Nothing under internal/ emits a metric yet
  (observability's own recorded deferral); the first emission arriving as a
  side effect of an alert slice would be wiring no test exercises end to end.
  `Snapshot` remains the exporter's future source, unchanged.
- **Exercise ExitClass consulting post-execute bans.** §61c: dead branch,
  proven live-impossible by the leg-classification argument and pinned by the
  fixture instead.

## §61g — what this slice deliberately leaves out

- Alert TRANSPORT (pager, webhook): the operator channel for one-shot tools is
  the exit code and the report; anything richer is the engine binary's ops
  story.
- Bybit e2e at the root: #171's testnet credential owns live Bybit evidence;
  the offline mirror is the transport suite (§61e).
- The throttle pause as a verdict: §7.6 calls it a hard pause and nothing
  more; it renders as information and holds no exit class, and that asymmetry
  is the section's own.

No spec document changed: the slice implements §7.6 as written, so the set
stays v0.9.40 and the Georgian tutorial needed no regeneration. The reading
pass over what the slice asserts normatively found one prose surface — the
CLI usage text now describes exit 1 as "latched gate or IP ban", which states
the implementation, not a new norm.
