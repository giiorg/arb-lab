**Task:** #187 — a mapped Bybit response with missing/malformed rate-limit
headers is silent. Filed during #185's design review (round 2's
saturate-on-missing proposal was REBUTTED and this filed instead; round 3
classified missing-header semantics MAJOR and filed rather than absorbed —
§66a).

**The condition, precisely.** After #185, `BybitLimitReader.Endpoint(path)`
derives the endpoint-budget name from the call path, so transport can tell
"this call charges an endpoint budget" from "this dialect does not meter this
path". When such a mapped call's response yields no usable
`X-Bapi-Limit`/`X-Bapi-Limit-Status` pair, `Observations` deliberately derives
nothing (normative: Profiles §6 "no observation may be derived at all",
build-spec §7.6 — a guessed cap is a budget quietly rescaled). That ruling
STANDS. What is missing is observability of the broken correction channel: the
upward-only fold is the only mechanism that incorporates another consumer on
the same UID, so a stripped/malformed header stream lets the local governor
admit its full allowance on top of a co-consumer's traffic while every
response succeeds.

## §67a — the decision: count-and-alert

A monotone per-limit **fold-miss counter** in the governor, incremented by
transport when a response that Bybit's API demonstrably handled yields no
usable observation for the endpoint it maps to, surfaced in `Snapshot`
beside `Bans` and rendered by the roots' rate-limit status line. **No
behavioural response**: self-charging continues, admission is unchanged,
derive-nothing stands.

**Why counting is enough today — and the premise stated honestly.** The
proportionality argument rests on an OPERATIONAL premise, not a code-enforced
one: **exactly one consumer spends this UID at a time**. Today that is how
the system is run — single short-lived `arblab` processes, one credential,
no second deployment — but nothing structural upholds it: every root builds
a process-local governor (`wire.go`), so two concurrent Bybit-spending
processes would each hold a complete-looking self-charge account that is
each wrong. While the premise holds, the self-charge IS the complete account
of the UID's consumption, so the fold's only unique contribution — a
co-consumer's traffic — does not exist, and a lost channel that carries no
unique information does not justify halting trading (stop-opening would
convert a venue-side header rename into a self-inflicted outage while the
accounting that actually gates sends is intact and conservative). The "stale
projection lags toward the unblocked action — halt" lesson does not apply:
there the stale value itself gated the action; here the gating account is
the self-charge, which a missing header does not touch.

**The enforcement gap, recorded rather than papered over** (design review
round 1, finding 3): count-only is safe exactly as long as the one-spender
premise holds, and this slice does not make the premise checkable in code.
In-slice enforcement was considered and REJECTED with reason: credential
exclusivity across processes is a coordination mechanism, and its named home
is **#188** (package-level reservation is the first slice that must reason
about concurrent spenders); an observability slice that grew a cross-process
lock would be two designs in one record. The premise therefore rides on two
recorded controls: (1) the **live-execution decision** — already USER-gated
(the $20/$55 decision) — must confirm single-spender deployment before any
live Bybit spend, and (2) the revisit trigger below.

**The revisit trigger, corrected:** the first deployment shape with a second
concurrent spender of the UID — including two `arblab` processes running at
once, or a credential shared with anything else — REOPENS the response
question, with stop-opening the leading candidate (§66a round 2's closing
note: "the right conversation once a second consumer exists"). **#171 is not
that trigger** — its subject is signer validation against a real testnet
credential; its role HERE is the first empirical baseline of the miss rate.
The counter this slice adds is the instrument the reopened conversation will
need either way.

**What the counter does NOT claim.** The design deliberately does not rest on
"Bybit returns the three headers on every response" — a venue claim Profiles
§6 verifies the *meanings* of but not the *presence-on-every-response* of.
The counter counts responses on which the correction channel failed,
whatever the cause; a legitimate venue omission would show up as a baseline
rate, and #171's testnet run doubles as the first empirical measurement of
that baseline. No new venue fact is owed by this slice.

## §67b — the mechanism

**1. `ratelimit.Governor.FoldMiss(family, name) error`** — mirrors
`Observe`'s contract exactly: family must be applicable when non-empty,
`limitKey{family, name}` must be declared (`ErrLimitUnknown` otherwise — a
miss nobody can place is the same config mismatch as a reading nobody can
place). On success increments a monotone counter in a new
`foldMisses map[limitKey]uint64` on the Governor (beside `bans`/`throttles`,
NOT on `window` — never evicted, never reset, not a consumption).

**2. `LimitState.FoldMisses uint64`** — `Snapshot` copies the counter out
per limit, in profile order (stable metric series, §10's seam).

**3. Detection: one predicate, decided where each conjunct becomes known.**
A miss is

> mapped ∧ no usable observation for the mapped endpoint ∧ the API
> demonstrably handled the request — where "demonstrably handled" is
> **2xx not classified as the IP ban** (any 2xx, not 200; the ban
> suppression is round 2's finding — a 200+retCode 10018 is the gateway
> ban wearing a success status) **or classified as a throttle**
> (`PenaltyThrottle` — Bybit 10006 in both its spellings AND the bare 429
> arm, per `venueerror.go`/`envelope.go`; the decision reads the PENALTY,
> not the retCode spelling, so a throttle-shaped refusal without headers
> counts even when the meter's identity is unprovable — a lost correction
> at the moment it matters most, covered by §67a's baseline philosophy).

The status guard alone was WRONG (review round 1, finding 1): the repo's own
classification records that Bybit does not document which HTTP status
carries 10006, and a 403+10006 is the endpoint METER refusing — the one
response whose headers matter most (#185's fold-on-429 argument verbatim).
Scoping to 2xx would leave the counter at zero in exactly the co-consumer
exhaustion scenario the task names. The IP-ban track (10018, `PenaltyBan`)
stays OUT on a recorded fact, not a guess: the envelope classifier documents
it as "the unheadered ~600/5s gateway ban" — headerlessness there is the
gateway's known shape, and counting it would teach the operator to ignore
the line. Other non-2xx responses (auth 401 with no body, server errors)
stay out: no verified claim says their path traverses the endpoint meter.

Mechanically: `observe` returns whether an observation for the mapped
endpoint was folded (matched on `o.Family == "" && o.Name == name`), and
`Do` decides the miss ONCE, at the last point it is decidable (review
round 2, finding 2 — the header-time 2xx decision was WRONG: Bybit states
refusals in the body beneath HTTP 200, and the repo's own envelope test
proves 200+retCode 10018 classifies `PenaltyBan`, so a header-time arm
would count the IP-ban response the exclusion above names) —

- **Body read succeeded** (the overwhelmingly common path): after
  `ClassifyResponse`, miss iff
  `penalty == PenaltyThrottle || (2xx && penalty != PenaltyBan)`.
  The ban suppression is what keeps a 200+10018 out; a 200+10006 counts
  through the throttle disjunct; an ordinary 2xx (including a
  VenueRejected retCode under 200) counts through the status disjunct.
- **Body read failed or overflowed** (two early returns, both
  EffectUnknown): classification is impossible — no retCode was ever
  parsed — so the miss is decided on the status alone, `2xx` only.
  DOCUMENTED LIMITATION: a 200+10018 whose body was lost counts a miss it
  would otherwise suppress. Accepted deliberately: on those paths
  `Penalize` never runs either (the classified penalty is downstream of
  the body), so the ban is unrecorded too, and the miss line is the ONLY
  signal the run produces — a spurious-looking line on a genuinely
  anomalous response is the right side of that trade.

Standing bullets, unchanged from the first draft:

- **Mapped-only:** Binance's `Endpoint` is always `""`, so Binance can never
  miss — correct, its headers name their own folds and there is no
  per-endpoint mapping premise to disagree with.
- **Absent and malformed are one condition:** `Observations` already
  collapses missing-cap, missing-status, unparseable, and remaining>cap to
  nil (each pinned by #185's reader tests); the counter counts "no usable
  observation", which is the union, at the seam where it is decidable.
- **A transport error is not a miss:** no response, no headers, no observe
  call — the counter measures protocol disagreement on ANSWERED requests,
  not availability.
- The dropped `FoldMiss` error is unreachable at this call site: #185's
  boot completeness check (`NewSignedClient` over `Endpoints()`) guarantees
  every derivable endpoint name is declared. Same argument as the dropped
  `Observe` error above it, one clause stronger.

**4. Rendering** in `writeRateLimitStatus` (shared by reconcile and
exercise): one line per limit with `FoldMisses > 0`, in profile order,
printed INDEPENDENTLY of the ban/pause branches — a banned run must not
hide the miss line (the current early-return on `Bans > 0` would; the
function is restructured so both print). Zero misses prints nothing (the
standing-line argument, unchanged). **The line's contract is HISTORICAL**
(round 3's minor: a monotone counter cannot claim a current outage — one
miss followed by a thousand clean folds would render "corrections are not
arriving" forever): it states that N responses this process's lifetime
carried no usable budget reading, nothing about now. That contract is
honest for these roots because they are short-lived single-run processes —
cumulative-since-boot IS this run's history. A rate or recency signal
needs a denominator this slice deliberately does not add: #171's
measurement supplies the external per-endpoint request count, and the
long-running engine's health view is §10's, on the `LimitState.FoldMisses`
seam this slice provides.

**4b. The exercise report renders rate-limit health exactly ONCE** (review
round 1, finding 2 — verified live). Today `writeExerciseReport` renders the
boot's rate-limit line inside `writeReconcileReport`, then on the executed
path renders the post-execute snapshot AGAIN — its own comment admits the
duplication and excuses it because a boot-time ban rarely coexists with an
executed run; a monotone miss counter that does not gate execution makes the
double print the COMMON case, with two different cumulative counts an
operator cannot tell apart from two incidents. Fix: split the boot renderer
(`writeReconcileBody` + `writeRateLimitStatus`; `writeReconcileReport`
composes both, unchanged for `arblab reconcile`), and `writeExerciseReport`
renders the body, the execute half, then rate-limit status ONCE from the
final snapshot — `r.RateLimit` when executed (a superset of the boot's, same
governor, monotone counters), `r.Boot.RateLimit` otherwise.

**5. `ExitClass` is unchanged.** A fold miss is diagnosis, not a latched
gate nor §7.6's ban MUST. Recorded as part of the decision: eligibility for
exit-class weight is exactly the revisit trigger above.

## §67c — rejected alternatives (recorded so nobody reopens them)

- **Hold the endpoint until a valid reading arrives** — rejected in #185
  round 2 (§66a): contradicts the normative derive-nothing ruling and rests
  on a shared-UID premise that does not exist before #171. Not reopened.
- **Stop-opening on fold-miss** (refuse PriorityOpening while the channel is
  broken): rejected for this slice by the no-second-consumer argument in
  §67a. It is the leading candidate WHEN the revisit trigger fires, which is
  why the argument and trigger are recorded rather than the option merely
  dropped.
- **Saturate the window on missing headers** — rejected in #185 round 2: a
  guessed cap is a budget quietly rescaled, in the refusing direction; §66a.
- **Fail the request on a miss** — the venue already answered; failing the
  call would turn a header regression into a trading outage. Same argument
  as `observe`'s dropped errors, which is already recorded in code.
- **Counter on `window`** — the miss is not a consumption: it must survive
  eviction and has no interval semantics. It lives beside `bans`/`throttles`.
- **Counter keyed per venue, not per limit** — loses exactly the dimension
  the task names ("per endpoint in Snapshot"), and a per-limit counter is
  what lets #171's measurement say WHICH endpoint's channel failed —
  cross-sectional attribution; rate needs #171's external denominator
  (§67b-4).
- **Require retCode-10006 provenance for the non-2xx arm** (review round 2,
  finding 1's proposed fix) — REBUTTED. The proposal excludes a headerless
  bare 429 on the theory it may be a CDN hop that never traversed the
  endpoint meter; but that theory is itself an unverified venue claim, and
  the counter is a DIAGNOSTIC, not a gate — a false positive costs an
  operator glance, while a false negative is blindness during exactly a
  throttle storm, the scenario the task was filed about. Plumbing retCode
  provenance out of `ClassifyResponse` would add classifier surface to
  serve an exclusion whose factual basis nobody has verified. The penalty
  is the classification this repo already trusts for pausing; the miss
  counter reads the same fact. #171's baseline measurement is the recorded
  arbiter: if bare-429 noise materialises, the provenance refinement has
  its evidence and its trigger.

## §67d — evidence plan

Collapse checklist BEFORE mutations (the fixture-collapse lessons, run at
design time):

- Profile fixtures carry ≥2 endpoint limits, and every sibling's counter is
  asserted at exactly 0 when one endpoint misses (the #185 `Used == 40`
  lesson: the assertion must be able to see WHICH counter moved).
- Two misses assert exactly 2 (increment vs set-to-1 must be
  distinguishable).
- The positive control: a valid-header response asserts the fold DID occur
  (Used moves) AND misses stay 0 — the counter must not fire on success.
- **Status boundary fixtures 199/204/299/300** — the repo already has the
  199/200/299/300 precedent (`classifyStatus`'s table) and an implementation
  narrowed to `status == 200` must fail; 204 also pins "2xx with no body".
- A **403+retCode 10006 with no headers** asserts exactly 1 (the throttle
  arm), and a **bare 429 with no envelope and no headers** ALSO asserts 1 —
  `classifyStatus`'s 429 arm is `PenaltyThrottle` with or without a
  retCode, and a throttle-shaped refusal without headers is a lost
  correction at the moment it matters most; the design counts on the
  PENALTY, not on the retCode spelling. A 403+10006 WITH valid headers
  asserts fold-and-no-miss (re-banks #185's fold-on-refusal beside the new
  claim).
- The zero cells that make the predicate real rather than "any classified
  refusal" or "any 2xx": **403+retCode 10018 (IP ban)** asserts 0
  (`PenaltyBan`, non-2xx arm), **200+retCode 10018 with no headers**
  asserts 0 (the ban suppression on the 2xx disjunct — round 2's finding,
  and the fixture that separates "after classification" from "at header
  time"), and **401 with an empty body** asserts 0 (`PenaltyUnspecified`,
  neither disjunct).
- A **2xx whose body read fails** (Content-Length lie, the #185 trick) with
  no headers asserts 1, and a **2xx whose body exceeds ReadLimit** with no
  headers asserts 1 — the two early returns are separate paths and each
  carries its own miss call (round 2's minor).
- **Each early-return call site's ARGUMENTS are proved truthful** (round 3's
  major — a central helper test cannot see a call site hardcoding a status
  or passing `false` for folded): per early exit, **2xx + valid headers +
  body failure asserts 0** (the folded argument; extends #185's
  fold-before-body fixture with the new counter's zero) and **non-2xx + no
  headers + body failure asserts 0** (the status argument).
- **Never-reset across the read lifecycle** (round 3's minor): one miss,
  two consecutive Snapshots both report 1; advance the injected clock past
  the endpoint interval — `Used` decays to 0, `FoldMisses` stays 1. This is
  what makes the exercise render-once design safe: a reset-on-read
  implementation would lose every boot miss the moment the boot snapshot is
  suppressed.
- The match predicate's two conjuncts are isolated with a fake
  `LimitReader` emitting (a) an observation named differently from the
  mapped endpoint and (b) one with the right name under a non-empty family —
  each must still count a miss. (The real Bybit reader can produce neither,
  which is exactly why a fake carries the fixture.)
- Renderer: 0 → no line; >0 → the line; ban AND miss → BOTH lines (the
  early-return restructure's own probe).
- Exercise report: boot-miss-then-execute composes to ONE rate-limit
  section carrying the final count, including a case where dispatch adds a
  second miss; the not-executed path still renders the boot snapshot.
- `FoldMiss` on an undeclared limit → `ErrLimitUnknown`; on a non-applicable
  family → `ErrFamilyUnknown`.

## Appendix A — implementation spec (file by file)

**`internal/platform/ratelimit/governor.go`**

- Governor gains `foldMisses map[limitKey]uint64`, made in `NewGovernor`
  beside `windows`.
- `FoldMiss(family ids.ProductCategory, name string) error` — doc comment
  states the contract and the §67a decision (observability only, admission
  untouched). Body mirrors `Observe` verbatim: lock; non-empty family must
  be applicable (`ErrFamilyUnknown`); `limitKey` must be declared
  (`ErrLimitUnknown`); then `g.foldMisses[k]++`.
- `LimitState` gains `FoldMisses uint64` with a doc line naming §7.6's
  fold-health clause; `Snapshot`'s loop copies `g.foldMisses[k]`.

**`internal/engine/venue/transport/signed.go`**

- `observe` returns `bool`: whether an observation matching
  `o.Family == "" && o.Name == c.cfg.Limits.Endpoint(call.Path)` was
  folded. (Compute the name once; unmapped paths return false and the
  caller ignores it.) The dropped-error comment stays.
- New unexported `noteFoldMiss(call Call, folded bool, status int,
  penalty ratelimit.PenaltyKind, classified bool)`:
  return early when `folded` or the path is unmapped; `is2xx :=
  status >= 200 && status < 300`; miss when `classified` is
  `penalty == PenaltyThrottle || (is2xx && penalty != PenaltyBan)`,
  when unclassified `is2xx` alone. On miss,
  `_ = c.cfg.Governor.FoldMiss("", name)` with the unreachable-error
  comment pointing at the boot completeness check.
- `Do`: capture `folded := c.observe(...)` where the fold already happens;
  on the body-read-error return and the body-too-large return call
  `noteFoldMiss(call, folded, resp.StatusCode, ratelimit.PenaltyUnspecified,
  false)` before returning; after `ClassifyResponse` call
  `noteFoldMiss(call, folded, resp.StatusCode, penalty, true)`.
  The step-list doc comment gains the miss decision as part of step 6.

**`cmd/arblab/reconcile.go`**

- `writeReconcileReport` becomes composition:
  `writeReconcileVerdict` (posture, verdict, latched) +
  `writeRateLimitStatus` + `writeReconcileDiagnosis` (blocking onward).
  Output for `arblab reconcile` is byte-identical to today when no misses.
- `writeRateLimitStatus` prints, FIRST, one line per limit with
  `FoldMisses > 0` (profile order):
  `ratelimit: <venue> <limit>: N response(s) carried no usable budget
  reading this run (§7.6 fold-health — venue-side corrections were
  missed)`. Historical wording, deliberately — see §67b-4.
  The ban/pause branches follow unchanged; the ban early-return now
  guards only the pause lines.

**`cmd/arblab/exercise.go`**

- `writeExerciseReport` renders `writeReconcileVerdict(w, r.Boot)`,
  `writeReconcileDiagnosis(w, r.Boot)`, the execute half, then
  `writeRateLimitStatus` exactly once from the FINAL snapshot:
  `r.RateLimit` when `r.Executed`, else `r.Boot.RateLimit`. The
  "post-execute state" comment is rewritten to carry §67b-4b's argument.

**Tests** — per §67d. Transport cases live beside the existing composed
Bybit tests (`bybitTestGovernor`/`bybitTestClient`/`bybitReadCall`);
