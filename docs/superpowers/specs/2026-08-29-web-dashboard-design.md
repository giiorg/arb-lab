## 1. Why this record exists

`docs/HANDOFF.md` closed session 146 with a flag rather than a thread: *the
operator's stated next topic is a web UI, and nothing in the doc set covers it.*
§12's milestone roster has no UI item and no decision record discussed one. This
record is that scoping, taken as a fresh subject.

The requirement as stated: an elegant, comprehensive, responsive dashboard that
shows what markets are followed, which venues are available and their KPIs, what
the balances are, what the trends are visually and numerically, what positions
are open and what the PnL is — able to **monitor and control** funding-rate
arbitrage, and extensible to other strategies later.

The first thing exploration established is that the requirement, read literally,
describes a system that does not exist:

> **There is nothing running to monitor.** Every `arblab` subcommand is one-shot.
> `pair run` opens a package and exits; `reconcile run` boots, asserts and exits;
> `screen run` fetches and writes JSON. "Open positions", "balance" and "PnL" are
> not live state anywhere — they are SQLite journals under `run/pair/` after a
> command has finished, plus JSON artifacts under `research/`. There is no
> `serve`, no daemon, and no `net/http` server in the repo outside the venue REST
> client and test doubles.

So the dashboard needs a **subject** built alongside it. That is the expensive
part of this work, and it is why the classification is architectural rather than
bounded: there is no existing flow to modify.

The second thing exploration established is the opposite, and it is good news:
`internal/engine/venue/` is considerably further along than §12's milestone
prose implies. It holds `balances`, `positions`, `posture`, `marginstatus`,
`marginacts`, `marginwrite`, `order`, `orderquery`, `book`, `funding` and `mark`
— **each with both venues' codecs**. The credentialed half of this dashboard is
mostly wiring, not new engine code — which is what moves those panels from "needs
an engine" to "needs a session". §12 item 1's scope correction reads, in the
present tense, that account/order capability has *no code at all*; it is dated
and it names milestone 3 slice C as the destination, so it is not wrong — but see
§14.2.

```
  ui/dist/                       the embedded bundle (placeholder committed)

```

**`audit` is not "the dashboard's read side", and the distinction is load-bearing.**
Core §11 defines it exactly: *"audit = projection of the OMS journal."* An earlier
draft of this record put the whole dashboard read model there — artifact reading,
venue snapshots, capture coverage — which would have silently widened a context's
meaning to fit a screen. **That is a spec edit wearing a layout decision's
clothes**, and this repo's standing rule is that deviations are marked, not
absorbed. It is not taken.

So the work splits three ways:

- **`internal/audit/`** is built as §11 defines it — the OMS journal projection,
  which does not exist yet and which the Positions and Journal screens need. It is
  owed regardless of this dashboard. **Its journal-reading adapter is not its
  own** — see §4d.
- **Each context exposes a read port for what it already owns**: `strategy` for
  screening and signal judgment, `marketdata` for book and funding snapshots,
  `risk` and `treasury` for their own. A context's read side belongs to that
  context.
- **`internal/app/serve/` composes across them.** A dashboard view is a
  cross-context composition, and composing across contexts is what a composition
  root is *for*. Per CLAUDE.md's layout rule, a read model for a screen is
  supporting machinery, not a first-class business capability — so it belongs
  under `app/`, not beside the contexts.

**`serve` composes; it never judges** — and the first draft's example of that was
wrong. It said the entry classification `CANDIDATE` / `MARGINAL` / `BELOW COST`
*"is `strategy`'s, reusing what `strategy/domain` already computes."*
**`strategy/domain` computes no such thing.** `decision.go`'s `Verdict` is
`enter` · `decline` · `continue` · `close` · `refuse`; screening produces
eligibility and a positive-rank shortlist. **There is no `MARGINAL` anywhere in
the repository**, and §4b's own gate table already contradicts the reuse claim by
listing "entry verdict" among the subsystem's **new** enum-likes.

The principle stands; the instance was invented. So:

- Panels showing a **decision** render `strategy`'s actual verdict with its
  inputs and provenance. `serve` formats it and does not rename it.
- The signal board's three-way band is a **new judgment**, and if it is wanted it
  is defined in **`strategy/domain`** with its thresholds stated there — not in
  the read side, which is the drift §4's first *Rejected alternative* refuses.
- **Until such a rule exists, `MARGINAL` does not render.** A band with no
  domain rule behind it is a label the screen invented, which is the whole
  failure mode this paragraph is about.

Recorded as **F38**. The mockups keep the three-way chip as an *illustration of
the layout*; the record does not claim a rule produces it.

> *Rejected alternative:* reimplement the classification in the read side for
> convenience. Rejected because two implementations of "is this a good entry" is
> exactly the drift this repo has been burned by, and because the screening
> ranking and the live signal board could then disagree about the same symbol with
> nothing failing.

> *Rejected alternative:* a new top-level `internal/dashboard/` context. Rejected
> on CLAUDE.md's layout claim: the top level is for business capabilities, and
> "what the operator sees" is not one. It would also have become the god-context
> that reaches into every other, which is the shape the three-way split above
> exists to avoid.

> *Rejected alternative:* widen `audit` to mean the whole read side, and mark the
> §11 edit as owed. Legitimate under the marking rule, and rejected because the
> narrower reading is *better* — the OMS journal projection is a real, separable
> thing that other consumers will want, and merging it with view assembly would
> couple it to a screen's shape. **The cheapest deviation is the one you find a
> reason not to need.**

### 4a. The split moves logic toward the gates, not away from them

The obvious objection to composing in a composition root is that **`app/` is
outside two of the six gates**. `hexboundary` and `notimenow` both scope by path
**segment** — `domain`, `application`, `infrastructure` — verified in
`tools/lint/hexboundary/hexboundary.go:150` and `notimenow.go:121`. A bare
`internal/app/serve/` package matches none of them, so neither gate would see it.
That matters here because §5 rule 4 — every response carries an injected
`server_now` — is precisely a `notimenow` claim, and it would have sat in the one
package the analyzer cannot read.

**So the view assembly goes in `internal/app/serve/application/`, and the wiring
stays in `internal/app/serve/`.** Because the gates key on segments, that single
naming decision puts every view under **both** analyzers: `hexboundary` then
forbids the assembly from importing `engine/` or any `infrastructure/`, forcing it
through the contexts' read ports, and `notimenow` forbids an ambient clock read
inside it. The composition root keeps only what a composition root is for — wiring
adapters, which is exactly the code that *should* touch `engine/`.

The name is not a trick to satisfy a linter. Cross-context view assembly **is**
application-layer logic; the previous draft's mistake was housing it somewhere
that did not say so, and the gates noticing is the point.

**The hole is real and has never been exploited — which is why it is invisible.**
`grep -rn "time\.Now()" internal/app/ --include="*.go"` excluding tests returns
**nothing**, across all five existing roots (`capture`, `pair`, `reconcile`,
`exercise`, `sim`). They do import `engine/`, which is correct and is what a
composition root is for. So `notimenow`'s discipline currently holds in `app/`
**by convention rather than by enforcement**, and a rule obeyed everywhere it is
unenforced is indistinguishable from a rule enforced. `serve` is the first app
root where an ambient clock read would be genuinely *tempting* — a long-running
process rendering countdowns — which is what turns a latent hole into a live one.
Recorded as **F31**.

The remaining cost is honest and stated: **more ports across more contexts** than
the single-context draft, and a `serve` tree that must be kept to one file per view
so it does not become the thing the earlier draft was rejected for.

**The journals are opened read-only.** `run/pair/*.db` is a single-writer store
and CLAUDE.md records that nothing lifts a latch inside a running process. A
`serve` process that opened them writable would be a second writer to the
platform's most safety-critical file.

### 4d. The audit journal reader is on the wrong side of §3.6 rule 6

The layout above put a *"read-only journal reader"* in
`internal/audit/infrastructure/driven/`. §3.6 rule 6 carries a corollary that is
normative since `[v0.9.59, task #207, record §78]` and says otherwise:

> *"a **CONSUMER-OWNED READ PORT of `oms` gets its adapter in `oms`'s OWN
> infrastructure**, never in the engine subsystem holding the data … The gate is
> right even where the port carries no write authority: the rule is about the
> PACKAGE, and an exemption reading 'this one is only a read port' would have to
> be re-judged for every member added afterwards, by whoever added it."*

Building a second reader in `audit` would not merely misplace a file — it would
**duplicate the journal format**, and two protections are lost with it, both
visible in `internal/oms/application/ports/journalreplay.go`:

- **Chain verification is the adapter's, and it is not optional.** The port's
  contract says an implementation of `Replay` **MUST** verify the hash chain
  *"because the caller has no way to: the preimage is the adapter's own
  encoding, so a use case that wanted to check would have to hold a second copy
  of the format."* A bespoke SQL reader in `audit` is that second copy.
- **`JournalVisitor` is one method per record kind on purpose**, so *"a NEW
  record kind added by a later slice breaks every visitor in the system at build
  time."* A hand-rolled reader does not participate: when the OMS adds a kind,
  every real visitor fails to compile and **the dashboard keeps rendering a
  silently incomplete projection**. That is `exhaustiveswitch`'s argument
  expressed in the type system, and opting out of it is the whole hazard.

**So:** `audit` declares the read port and owns the projection model; the
journal-backed projector is constructed **inside the OMS package tree** over the
existing verified `JournalReplay`; `serve` consumes only the finished audit read
port. Recorded as **F33**.

## 5. The wire contract — five rules, each traceable to a finding

**Rule 1 — money and rates are decimal strings, never JSON numbers.** A JSON
number is a float64 on both sides of the wire. `nofloat` stops at `internal/`, so
without this rule every guarantee the dimensional types provide would end
silently at the network boundary, with the number still looking right. **No `//nofloat:allow` is written anywhere in this
subsystem**, and the reason is the rule's own second half: §3.6 rule 4 reports an
escape with nothing to suppress, because otherwise it survives the deletion of
the float it was written for and pre-authorises the next one. A JSON encoder
emitting `fixedpoint`'s decimal strings has no float to suppress, so an escape
there is either unused — and reported — or it is authorising exactly the
precision loss rules 1 and 2 exist to prevent. Prometheus is not precedent: its
wire format *is* `float64`-typed. JSON's is not.

**Rule 2 — the browser performs no money arithmetic.** Every derived quantity —
spread, net, break-even, annualised return — is computed in Go with `fixedpoint`
and shipped as a formatted string plus its raw decimal. The frontend formats; it
never computes. This is the rule that makes rule 1 worth having: a string parsed
into a JS number and multiplied by a position size is a float64 path through the
middle of the kill-gate calculation.

**Charts are the case the rule as first written did not survive**, and it is
named here rather than discovered at implementation. §9 ships ~1–2k downsampled
points per series for hand-written SVG, and placing them responsively means
scaling numbers in JavaScript — which the rule, read absolutely, forbids. The
resolution is that **the server ships completed geometry, not values to scale**:
each series arrives as **normalized integer coordinates in a fixed viewBox
space**, computed in Go with `fixedpoint`, together with its axis ticks and their
already-formatted labels. The browser places that geometry through an SVG
`viewBox` and CSS, which is layout arithmetic over unitless integers and touches
no money. **No money or rate decimal is ever an operand in the browser** — the
raw decimals still travel for tooltips and tables, where they are formatted and
never combined.

**Rule 3 — every ratio ships with its denominator, and every derived comparison
ships with its comparand.** A bare ratio is not encodable by the response type:

```json
{
  "value": "0.358",
  "denominator": { "amount": "2000.00", "asset": "USDT",
                   "kind": "deployed_capital_two_leg",
                   "size": "1000.00", "leverage": "1" },
  "at_least_c_allocated": true,
  "display": "+35.8 %/yr"
}
```

A **basis token is not a denominator.** Core §2.1 admits a denominator other than
`C_allocated` *"on one condition: the denominator is explicitly declared in the
artifact"* — and a label declares which *kind* of base was used, not **how large
it was**, which is the only thing that makes a hurdle comparison sound. So the
type carries the **amount, its asset, and the size/leverage that produced it**,
plus the proof obligation `at_least_c_allocated`. A ratio whose denominator is
smaller than `C_allocated` may be rendered as a diagnostic and **may not carry a
verdict**.

**The value above is `35.8`, and the number that stood here was `31.8`.**
`research/persistence/summary.json`'s LABUSDT row reads `annual_pct_on_2000` =
`35.8` at `0.0021`, and `0.71586586 / 2 = 35.79` independently. See §15.

This is **F30 as a type**. `ranking.json`'s `rank_score 0.71586586` is per *one
leg's* notional and declares that in no field, and the comparison core §2.1's
denominator rule exists to
protect was done at 2× by the two readers closest to it. A number that cannot
travel without its base cannot repeat that.

**The comparand clause is F45's, and it is the same disease one operand over.**
A rendered *comparison* — "4 of 56 clear the hurdle", "p50 run clears break-even"
— is a conclusion, and a conclusion whose threshold is not beside it cannot be
audited or recomputed. Rule 3 as originally written covered ratios only, and a
threshold comparison is not a ratio, which is exactly why `summary.json`'s
`verdict` block shipped `beat_hurdle_symbols` with the hurdle it was beaten
against nowhere in the file (§8c point 4). So the wire type for a comparison
carries the **comparand, its unit, and its provenance class**, on the same terms
the denominator is carried above — and a comparison whose comparand is marked
`illustrative` may be rendered and **may not carry a verdict**, which is the
`at_least_c_allocated` obligation transposed.

**Rule 4 — every response carries `server_now`.** Countdowns ("next settlement in
1h 12m") render against it, never against `Date.now()`. This is `notimenow`
projected across the network: a skewed laptop clock would shift every settlement
countdown on screen with nothing failing.

**Rule 5 — every live observation carries its watermark, and a stale input
removes the verdict rather than ageing it.** `server_now` is a property of the
*response*; it says nothing about how old the book behind a spread is. Core §3.4
is normative here and the wire contract has to carry it:

> *"Every published snapshot carries a **watermark**: source sequence, exchange
> timestamp, receive timestamp, and max cross-leg skew. **Cross-leg skew is
> measured over `RecvTime`, never over `SourceTime`.**"* (`build-spec.md:200`)

So every live-sourced field ships `{ source_seq, source_time, recv_time }`, every
two-leg derived quantity ships the **cross-leg skew over `RecvTime`**, and each
carries a freshness **verdict** against its class budget rather than a bare age
for the reader to judge. This is not decoration: `engine/state`'s cache
deliberately **discards stored freshness and requires the caller to recompute
both ages from the watermark at read time**, so a read side that merely takes the
latest value has bypassed the mechanism by design.

**And the failure direction is stated.** When any input to a derived signal
misses its budget, the derived field — spread, `entry_verdict`, break-even —
becomes **unavailable and explicitly stale**, never a last-known value with an
age beside it. A stale spread rendered next to a green `CANDIDATE` chip is the
§3.4 hazard reproduced on a screen: every panel populated, nothing failing.

## 6. The control surface, and why the browser is never the actuator

| | The browser may | The browser may not |
|---|---|---|
| **v1** | read; nothing else | anything |
| **v2** | run safe idempotent commands: `screen run`, `reconcile run`, `reference fetch` | place, amend or cancel orders; **record a margin reconcile** — see below |
| **v3** | **arm / disarm** a strategy per symbol; kill switch | compose an order — ever |

Order placement is the *engine's* job; the browser's job is to supervise it —
show what the engine is armed for, what it is about to do and why, what it did,
and carry an always-visible kill switch.

**`record a margin reconcile` was in the v2 row and does not belong there
(F44).** It was grouped with `screen run` and `reference fetch` as a *safe
idempotent command*, and it is neither half of that phrase. It is an **append to
§5.1's hash chain**, and `ReconcileMarginOp`'s own refusal set includes *"already
reconciled"* — so a repeated request is **refused**, which is not idempotence; it
is a second outcome the operator has to interpret, during the incident the act
exists to close. Its `MarginOpReconciliation.Actor` is *"free text and
self-asserted"*, which `marginop.go` argues correctly for §7.4's solo-honest
default **when a human types it at a terminal**, and which becomes *anonymous with
a label* when an HTTP request supplies it — against §7.3's *"no anonymous or
localhost-implicit trust"* and its *"immutable per-actor audit"*. The immutability
holds, because the value is inside the hash chain; the **attribution** does not.

So it is re-graded as **a control action with its own §7.3 grant**, and it does
not ship before §7.3's clauses do. §6a's ladder point 2 already said each rung is
a distinct authorization; this is the rung that was filed under the wrong one.

Arm/disarm is a write, but it is the right *shape* of write for this codebase:
it only ever changes a permission, and its safe direction is disarmed. That
matches the standing rule — when a default has two directions, pick the one that
is right when somebody forgets it. A "place order" button has no safe direction;
a disarm button's failure mode is that you trade less.

> *Rejected alternative:* full control including order placement from the browser.
> Rejected on F23: a *successful* `pair run` leaves a live position the root has no
> command to take off, latches `GateNetDeltaAsserted` on both journals, and no CLI
> lifts the latch. A button that can strand you needs more than a click, and the
> in-band close belongs with #241.

> *Rejected alternative:* permanently read-only. Rejected because it forces every
> action through a terminal even after an autonomous engine exists, and a kill

### 6a. What actually keeps the browser away from the OMS — and what §7.3 requires

### 8a. The cost assumption becomes a control

F26: the verdict is a function of an assumption whose span covers the whole
answer. So the assumed round-trip cost is **an input on screen** — 21 bp / 29 bp /
90 bp / custom — and every verdict, break-even and annualised figure on every
screen recomputes against it. Server-side, in `fixedpoint`, via a query
parameter; rule 2 makes this safe by construction.

This converts F26 from a caveat someone has to remember into an instrument.

**But a scenario is not a verdict, and the first draft let it become one.** §8a
said the control recomputes *"every verdict"*; §8c says the dated revision is the
source of truth and a revision without provenance is **refused, not defaulted**.
Both cannot hold. Core §2.4 settles it — the decision path reads the governed
revision *"as-of the decision instant, never by a scoring-time venue call"* — and
an arbitrary number in a query string is a scoring-time input with no provenance
at all, which a bookmarked `?cost=0` would turn into a screen full of green
verdicts.

So the two are **separate fields with separate types**:

| | Produced from | May carry |
|---|---|---|
| **`verdict` / `entry_verdict`** | the dated cost revision + measured book-derived cost, both with provenance | the gate reading |
| **`scenario`** | any of 21 bp / 29 bp / 90 bp / custom | a *modelled* figure, labelled **not gate evidence** (§43g), never an `entry_verdict` |

The instrument survives intact — F26's whole point is that the operator can sweep
the assumption and watch the answer move. What it may not do is **come back
wearing the verdict's clothes**. Recorded as **F35**.

### 8b. The cost stops being flat — and the spec already required this

`RoundTripCost()` is `0.0021` for every symbol at every size: four taker legs and
nothing else. But fees are per-venue-per-tier, and crossing and slippage are
computable from the **live book at the configured size**. The dashboard therefore
shows a per-symbol, per-size cost decomposition instead of one constant.

**This is not an improvement invented here.** Core §2.4 already requires it, in
terms that describe the panel almost exactly:

> *"**One source of truth for cost.** Round-trip cost MUST be computed from
> programmatically-fetched, per-leg, per-venue maker/taker fees plus a measured
> slippage model. **No hardcoded fee constants; no second copy of the number in
> another module.**"*

`screening/params.go` holds `BinanceTakerFee = 0.0005` and
`BybitTakerFee = 0.00055` as package-level constants. **That is not asserted here
as a breach** — the values are sourced and dated in the comment above them
(`venue-profiles.md` §280 block, observed 2026-07-31), the harness deliberately
"charges the worst published path", and §43g says step 1 is not gate evidence.
But it is a second copy of a number that has a dated revision-controlled home,
and the clause exists so a third copy is never made.

**So the dashboard does not read `screening.RoundTripCost()`.** See §8c.

The book-derived half needs **no credentials and no new venue contact beyond
public books**, and it is a large fraction of the handoff's stated next action —
arriving as a side effect of rendering the cost honestly rather than as a
separate measurement campaign.

**It is not the realized cost.** F24 and F25 leave that open, §98's 0.90 % stays

### 8c. Where the cost and hurdle inputs come from — and where they must not

`configs/reference.*.json` already carries exactly the shape core §2.4 demands:
per-venue, per-product `maker`/`taker` rows with `tier`, `class`, `observed_at`
and `source`; `lots` rows with tick, step and min-notional; and a `hurdle` block
with `annual_rate`, three haircuts, `as_of`, `class` and `source`. `arblab
reference fetch` writes them. **These revisions are the dashboard's cost and
hurdle source of truth.** Three consequences:

1. **Fees are never fetched at render time.** Core §2.4: the decision path
   *"reads the fee (and lot-rule, and hurdle) revision **as-of the decision
   instant**, never by a scoring-time venue call."* The dashboard reads the dated
   revision. Books and marks are a different category — instantaneous market
   state, not a governed input — and are read live.
2. **The hurdle is displayed from the revision, with its provenance.** The
   committed revisions all carry `annual_rate 0.0369` with the T-bill source and
   an `as_of`; §99's verdict table compares against **4.6 %**, which core §2.1
   labels illustrative and which §99 §5 also labels illustrative. Both statements
   are correct in context, and a reader meeting either number alone cannot tell.
   Rendering `as_of`, `class` and `source` beside the figure is what makes the
   difference visible — the same disease as F30, treated the same way.
3. **A revision with no provenance is refused, not defaulted.** Core §2.4 says a
   revision missing writer class, observed-at or document revision is refused.
   The read side inherits that: an unpopulated cost reads as free and an
   unpopulated rate reads as zero fee, and both compute the gate in our favour.

**4. A stored comparison must carry its comparand, and `verdict` does not (F45).**
Point 2 above is the right treatment for a *figure*, and §8's Persistence table
sources the hurdle **comparison** to a different artifact where the treatment
cannot be applied. `summary.json`'s `verdict` block holds `beat_hurdle_symbols`
per cost level and **no hurdle field**. The threshold is
`research/persistence/summarise.py:139`'s `HURDLE_PCT = D("4.6")` — annotated in
place as *"illustrative and … NOT a calibrated constant"* — and the script
**prints** it and does not **write** it. Rendering the hurdle from the revision
per point 2 therefore puts **3.69 % beside a count computed at 4.6 %**: every
field with correct provenance, and the comparison still incoherent, because a
comparison's base is unrecoverable from a file that does not hold it.

So `summarise.py` writes `hurdle_pct` and its `class` into the `verdict` block
before any panel reads it. **This is the ninth fixture collapse and it is in the
artifact rather than in a test**: no golden generated from `summary.json` can
fail on the hurdle, since the hurdle is not in `summary.json` — §11's
*"generated from real committed data, never hand-written"* rule is what hides it,
because the golden faithfully reproduces `4` at any threshold. It is F30's shape
on the other operand — F30 found the *return* had no declared denominator; this
is the *comparison* with no declared threshold.

> This is also the reason §5 rule 3 — **every ratio carries its denominator, and
> every derived comparison carries its comparand**; the second clause is F45's,
> because a threshold comparison is not a ratio and that is exactly why rule 3 did
> not cover it — is not mere hygiene. Core §2.1 **requires** the first: a gate may report on a denominator other
> than `C_allocated` *"on one condition: the denominator is explicitly declared in
> the artifact."* Rule 3 makes that condition structural instead of editorial.

## 10. Build integration

`web/` is a **third build unit**, documented exactly as `tools/lint` is: outside
`go.mod`, so no JS toolchain enters the engine's dependency graph and a local run
still resolves identically to CI.

- `make web` builds into `internal/app/serve/ui/dist/`.
- **A placeholder `index.html` is committed there**, so `go build` never requires
  node. It renders a page naming the make target — the zero value is unusable, and
  the failure is a refusal that names the fix rather than a blank screen.
- `make ci` gains `web-check`: `tsc --noEmit`, lint, `vitest run`.
- `make ci`'s Go half is unchanged and still runs without node.

> Without the committed placeholder, `//go:embed` fails at **compile** time on a
> missing directory, which would make `make ci` depend on node having run first.
> The two-module discipline exists precisely so that does not happen.

**⚠ But "the zero value is unusable" is not satisfied by a page that says so.**
As first written, the placeholder makes an ordinary Go-only release **compile,
boot, serve HTTP 200 and return the instructional page** — a healthy process
rendering a sentinel, with nothing refusing. That is a *rendered explanation*,
not a refusal, and this repo's rule is that the failure you get from forgetting
should be a refusal that names the field. Two additions make it one:

1. **Startup refuses the sentinel.** The embedded bundle carries a build
   manifest; `serve` checks it at boot and **refuses to start** when it is the
   placeholder, naming `make web`. Compile-time success stays (the two-module
   discipline is worth keeping); run-time success does not.
2. **The release target builds the frontend and smoke-tests the embedded
   manifest.** `web-check` only runs `tsc --noEmit`, lint and `vitest` — it never
   produces a bundle, so it cannot tell a real one from the placeholder.

Recorded as **F40**.

**Tense.** §9 and §10 above describe the intended end state. **None of `web/`,
`.nvmrc`, `internal/app/serve/` or the committed `ui/dist/index.html` exists
today** — this record designs them and no code was written under it.

## 11. Testing

Go side follows the existing habits: golden JSON per endpoint generated from real
committed data by a script in the repo — **never hand-written**, because a
hand-written fixture lets a panel display a number no source can produce, and the
discovery would come at integration.

**⚠ And "generated" does not say *by what*, which is the seventh collapse — the
one hiding inside this rule's own remedy.** The natural implementation of
"generate the golden" is: boot the server, call the endpoint, save the response.
A golden produced that way **agrees with the server by construction**. It detects
*change* and can never detect *error*: every number in it is whatever the
handler computed, correct or not, so the check is fed only by the implementation
it is checking and no failing fixture can exist. **It would have caught nothing
in F36** — those numbers were wrong at the source, and a self-generated golden
would have frozen them.

So the rule needs its second half, and this repo already has it: *write the
oracle before trusting the implementation* — `fixedpoint` has a `math/big`
oracle, `ids` has one for its base32 codec, and real defects here have been found
by two implementations disagreeing rather than by review. **A golden's VALUES
come from an independent path** — read `summary.json` / `episodes.json` /
`ranking.json` directly and compute the expected figure without touching the
handler — and the golden then asserts agreement between two derivations. The
endpoint may shape the JSON; it may not be the authority for what is in it.
Recorded as **F37**. `tools/mutate.sh` on the classifier and the
encoder. Positive controls on every harness.

**The fixture-collapse checklist runs before the mutations.** **Twelve** collapses
are nameable and must be designed against — the count is stated because this
list's own count word was wrong (see below):

| Collapse | Why it hides a defect |
|---|---|
| A **one-venue** fixture | "this venue's" and "the first venue's" are the same value |
| A **one-leg** package fixture | per-leg and per-deployed-capital are the **same number**, so rule 3 — the whole F30 defence — would pass untested |
| `p50 run` **equal to** break-even | the two thresholds the signal board contrasts collapse to one |
